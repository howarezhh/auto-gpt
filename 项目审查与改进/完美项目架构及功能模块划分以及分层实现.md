# 完美项目架构及功能模块划分以及分层实现

## 1. 文档目标

本文描述的是 aotu-gpt 在完成架构重构后的目标形态。它不是推倒重写方案，而是在保留现有功能、现有数据库主体、现有页面、现有 `/v1/*` 对外协议、现有管理端和用户端能力的前提下，对项目进行分层、分模块、低耦合、无循环依赖、易扩展、易测试的结构化设计。

2026-06-08 同步口径：模型映射阶段只选择目标模型；端点协议、流式、视觉、工具调用、图片生成、容量、熔断、内容完整性和可信策略统一在提供商候选选择阶段判断。提供商和提供商模型挂载配置不再维护或对外暴露权重字段。内容防护已经开始拆成规则算法、运行时防护、预先可信探针三条服务线，目标重构应保留该方向并继续消除剩余反向依赖。代理入口日志已把 `unsupported_endpoint` 与 `v1_preflight` 从鉴权日志中拆出，图片生成能力只认显式 `supports_image_generation=true`，前端静态资源版本已同步到 `app.css?v=20260608-06` 与 `app.js?v=20260608-32`。

本文以当前代码为依据，已复核当前项目中的：

- 路由文件：`app/routers/*.py`
- 服务文件：`app/services/*.py`
- 数据模型：`app/models/*.py`
- Schema：`app/schemas/*.py`
- 前端模板与静态资源：`app/templates/*.html`、`app/static/js/app.js`、`app/static/css/app.css`
- 后台任务：`app/tasks.py`、`app/scheduler.py`
- 脚本和回归检查：`scripts/*`、`stage7` 到 `stage35`
- 迁移文件：`migrations/*.sql`

本文要回答的问题：

1. 改进后项目分为多少层。

4. 每个模块的职责边界是什么。
5. 每个模块输入、输出是什么。

7. 每个模块如何实现当前已有功能。
8. 每个模块关联哪些数据库表。
9. 模块之间如何依赖，如何避免循环依赖。
10. 后续重构时如何不丢失当前功能。

## 2. 总体结论

改进后的项目建议采用 **7 层架构、33 个一等功能模块**。

7 层为：

1. 表现层。
2. 接口适配层。
3. 应用用例层。
4. 领域层。
5. 基础设施层。
6. 后台任务层。
7. 工程治理层。

33 个一等功能模块为：

1. 管理端前端模块。
2. 用户端前端模块。
3. 前端基础组件与主题模块。
4. 对外 OpenAI 兼容 API 模块。
5. 管理端 API 模块。
6. 用户端 API 模块。
7. 页面路由模块。
8. 健康监控 API 模块。
9. 内部调试与压测 API 模块。
10. 代理调用用例模块。
11. 提供商管理用例模块。
12. 模型与映射用例模块。
13. API Key 与策略用例模块。
14. 用户账户与门户用例模块。
15. 日志观测用例模块。
16. 计费用量用例模块。
17. 运维治理用例模块。
18. 协议领域模块。
19. 能力领域模块。
20. 路由领域模块。

22. 模型领域模块。

33. 迁移部署测试治理模块。

核心依赖方向必须固定为：

```text
表现层 -> 接口适配层 -> 应用用例层 -> 领域层 -> 基础设施端口
后台任务层 -> 应用用例层
基础设施层 -> 领域层定义的端口或应用层定义的端口
工程治理层 -> 只读取或驱动应用，不被业务层依赖
```

禁止方向：

- 领域层禁止依赖 FastAPI、SQLAlchemy Session、Redis、httpx、aiohttp、Jinja2。
- 领域层禁止 import `app.routers`、`app.services` 的用例编排类。
- 基础设施层禁止反向调用路由层。
- 路由层禁止直接操作 SQLAlchemy 模型。
- 应用层禁止依赖具体 Redis client 或具体 HTTP client，应依赖端口接口。
- 日志、计费、健康、内容防护、路由、提供商、模型、API Key 模块之间禁止双向 import。

2026-06-08 代码同步口径：

- 模型映射阶段只负责源模型到目标模型的选择；提供商级协议、流式、视觉、工具调用、图片生成、容量、熔断、内容完整性和可信策略必须后移到提供商候选选择阶段。
- `weight` 只允许作为 `priority` 的过渡兼容属性存在，目标数据库、Schema、前端表单和路由策略均禁止重新引入真实权重字段。
- `trusted_providers_only` 已收敛到全局系统设置；API Key、批量授权、用户门户和模板层不再维护局部可信开关。
- `/v1/models` 与 `/v1/models/{model_id}` 必须作为同一模型发现接口族处理，日志、计费、Token 补全、监控积压和统计都复用同一判断。
- `request_logs` 已补充 reasoning/audio/prediction/cache usage 明细、`token_source`、`upstream_usage_missing` 和 `usage_details_json`；后续日志、计费和导出必须统一从官方 usage 结构读取。
- 模型选项缓存已升级为 `model-options:v2:list`，启动同步与写操作必须主动失效模型目录和 provider 运行时缓存。
- Chat Completions / Responses 端点协议支持的权威来源必须是管理员维护的 provider_model 挂载级协议配置；健康检查、端点测试、能力探针和内容探针只能记录观测结果，禁止自动改写或收紧协议支持。
- 内容防护可信检测必须至少覆盖固定答案、外链广告识别、流式污染检测三类必需探针；人工标记可信也要留下可追溯确认明细，但目标领域模型必须区分人工确认与真实探针。
- 日志中心类型化日志已扩展筛选、时间线和导出能力；后续必须拆成日志查询用例与导出用例，管理端和用户端复用时间线时必须保持用户拥有者校验。
- `RequestContentGuardEvent` 已存在并进入请求时间线，当前也已有独立内容防护事件列表、筛选、导出入口和前端 Tab；目标架构后续重点不再是“新增入口”，而是把日志事件模型、查询投影、详情证据和 CSV 稳定 schema 同步收敛。
- `ContentGuardRuleService`、`ContentRuntimeGuardService`、`ContentTrustProbeService` 是当前工作区已经落地的内容防护拆分起点；后续模块划分应以它们为过渡锚点，而不是回退到单一 `ContentGuardService`。
- Chat/Responses 自动端点互转 fallback 已禁用；Responses→Chat 只能作为显式开启的兼容适配插件存在，且默认会话存储为 database。
- API Key 余额已收敛到归属用户共享账户；目标架构中 API Key 只保存凭据、授权策略、所有者、QPS/RPM、偏好标签和成本累计，不再作为独立充值、扣费、总 Token 限额、日费用限额、默认 provider、局部候选数或局部无限重试主体。
- 计费账本必须完整保存 cache read/write token 与读写单价；`cache_write_price_per_1k` 是 provider_model 挂载级价格字段，不能再只把缓存写入当作普通 input token 隐式处理。
- 后台任务必须记录锁状态、跳过原因、processed/success/failed 计数；Redis 分布式锁不可用时定时任务必须跳过并写事件，禁止无锁执行。
- 后台任务观测必须区分“调度锁事件”和“队列消费状态”。`BackgroundJobEvent` 不能替代 request log queue、logging queue、token finalize queue、billing queue 的 backlog、重试、死信、消费延迟和 worker 存活观测。
- `/v1` CORS 预检和不支持端点兜底必须分别记为 `v1_preflight` 与 `unsupported_endpoint`，不能继续复用 `api_client_auth`。
- 图片生成能力必须来自显式字段，前端、路由和健康探针禁止从模型名、视觉能力或工具能力推断 `supports_image_generation`。
- 前端 shell 不再依赖顶部上下文标题块；后续页面模块化时必须保持左侧导航、移动端导航和资源版本更新逻辑独立。

## 4. 分层职责定义

### 4.1 表现层

表现层包括 Jinja 模板、CSS、JS、图片和页面交互逻辑。

必须做：

- 展示服务端返回的数据。
- 发起浏览器内 API 请求。
- 提供主题、导航、弹窗、Tooltip、Toast、表格响应式等交互。
- 保留管理端和用户端的现有页面。
- 遵守项目全局规范与前端设计规范。

禁止做：

- 禁止直接表达核心业务规则。
- 禁止在前端重新计算后端已有的费用、额度、健康、路由结论。
- 禁止在前端保存外部 Bearer API Key 用于内部调试。
- 禁止直接拼装正式 `/v1/*` 代理行为。

### 4.2 接口适配层

接口适配层包括 FastAPI route handler、HTTP 请求解析、响应序列化、Session 读取、Bearer 读取、表单读取、上传文件读取。

必须做：

- 接收 HTTP 请求。
- 校验请求形态。
- 调用应用用例层。
- 将应用输出转成 JSON、HTML、StreamingResponse 或文件下载。
- 统一处理认证依赖。
- 保留现有路由路径。

禁止做：

- 禁止直接写数据库。
- 禁止直接调用 SQLAlchemy 模型查询。
- 禁止执行路由排序、费用计算、内容检测等领域逻辑。
- 禁止把页面表单处理和业务命令混在一起。

### 4.3 应用用例层

应用用例层是系统的编排层。它知道一个业务用例需要调用哪些领域服务、仓储、外部端口和后台任务。

必须做：

- 编排完整业务流程。
- 控制事务边界。
- 调用领域服务做决策。
- 调用仓储读写数据。
- 发布领域事件或后台任务。
- 聚合页面或 API 所需 DTO。

禁止做：

- 禁止把纯业务规则写成散落的 if/else。
- 禁止直接依赖具体 Redis client、httpx client、aiohttp session。
- 禁止生成 HTML。

### 4.4 领域层

领域层是最稳定的业务核心。它只表达业务概念、规则、策略、状态机和决策。

必须做：

- 定义核心领域对象。
- 定义纯规则与策略。
- 定义端口接口。
- 定义领域事件。
- 处理路由、能力、鉴权、计费、内容防护、健康熔断等核心判断。

禁止做：

- 禁止 import FastAPI。
- 禁止 import SQLAlchemy Session。
- 禁止 import Redis。
- 禁止 import HTTP client。
- 禁止读写文件。

### 4.5 基础设施层

基础设施层是技术实现层。

必须做：

- 实现 repository。
- 实现 Redis 缓存、锁、限流、租约。
- 实现上游 HTTP 请求。
- 实现队列。
- 实现文件资产存储。
- 实现迁移执行器。

禁止做：

- 禁止承载业务决策。
- 禁止反向调用接口层。
- 禁止直接生成面向用户的业务响应。

### 4.6 后台任务层

后台任务层负责异步、定时、可重试、可幂等的任务。

必须做：

- 请求日志异步落库。
- 统一事件落库。
- Token finalize。
- 计费结算。
- 健康检查调度。
- 内容完整性巡检。
- 数据保留清理。
- Responses adapter 会话清理。
- 压测任务状态管理。

禁止做：

- 禁止复制应用层业务规则。
- 禁止绕过应用用例层直接拼业务流程。

### 4.7 工程治理层

工程治理层包括部署、迁移、回归测试、压测、mock 上游、架构依赖检查。

必须做：

- 版本化数据库迁移。
- 环境初始化。
- 部署脚本。
- 真实上游验证。
- 本地 mock。
- 回归测试。
- 架构依赖检查。

禁止做：

- 禁止被运行时业务代码依赖。
- 禁止把一次性手工命令写成业务逻辑。

## 5. 33 个模块完整划分

### 5.1 管理端前端模块

所在层：表现层。

对应现有文件：

- `app/templates/dashboard.html`
- `app/templates/providers.html`
- `app/templates/models.html`
- `app/templates/settings.html`

- `app/templates/alerts.html`
- `app/templates/audit_logs.html`
- `app/templates/users.html`
- `app/templates/user_detail.html`

职责边界：

- 展示管理员工作台、提供商、模型、设置、内容防护、调试、压测、日志、会话、告警、审计和用户管理。
- 只负责页面结构和交互触发。
- 不负责计算 provider 可用性、费用、路由策略、Token、内容风险。
- 日志页负责承载请求日志、类型化日志、高级筛选、详情弹窗、原始 JSON 截断展示和 CSV 导出入口，但不在前端计算日志归属、计费金额或 usage 口径。
- 压测页负责承载模型选择器、端点过滤、任务启动/停止、轮询进度、实时日志、稳定并发结果和 HTML/JSON 报告链接，但不在页面内实现压测调度算法。
- 提供商与模型挂载页面可以展示 provider 更多操作菜单、批量工具栏、能力标签和可信检测结果，但不能在前端推断图片生成能力或端点协议支持。

输入：

- 服务端模板上下文。
- 管理端 `/api/*` JSON 接口。
- 浏览器用户操作。

输出：

- HTML 页面。
- API 请求。
- Toast、Modal、Tooltip、表格、图表等 UI 状态。

接口：

- 页面入口保持现有路径：`/`、`/providers`、`/provider-models`、`/models`、`/settings`、`/content-guard`、`/playground`、`/benchmark`、`/operations`、`/docs`、`/api-keys`、`/api-keys/{id}`、`/logs`、`/conversations`、`/alerts`、`/audit-logs`、`/users`、`/users/{id}`。
- 调用管理端 API 模块暴露的 JSON 接口。

相关数据库表：

- 不直接访问数据库。
- 间接展示 `providers`、`provider_models`、`model_catalogs`、`api_client_keys`、`request_logs`、`user_accounts`、`alert_events` 等数据。

依赖：

- 依赖接口适配层。
- 不依赖应用层、领域层、基础设施层。

实现方式：

- Jinja 模板保留现有视觉结构。
- JS 拆分后由页面初始化器负责，例如 `admin/providers_page.js`、`admin/models_page.js`。
- 页面只消费 DTO，不消费 ORM 模型。
- `admin/logs_page.js` 应拆出日志筛选、请求日志表格、类型化日志详情弹窗、原始 JSON 截断、CSV 导出按钮和用户可见中文标签映射。
- `admin/benchmark_page.js` 应拆出模型加载、端点过滤、任务 payload 构造、job 轮询、进度条、阶段表和报告链接。
- `admin/providers_page.js` 与 `admin/provider_models_page.js` 应共用 `components/action_menu.js`，操作菜单采用全局 fixed 定位或等价顶层浮层，避免被表格、卡片或滚动容器裁切。

11. 构造上游请求。
12. 调用上游。
13. 对响应执行内容防护。
14. 写请求摘要和链路事件。
15. 入队 Token finalize 和计费任务。

- `README.md` 已明确 Chat/Responses 自动端点互转 fallback 禁用，正式路由要求上游原生支持请求端点；需要接入 Chat-only 上游时必须显式启用 Responses→Chat 适配。
- `app/config.py` 和 `ResponsesChatAdapterService._storage_type` 的默认值已从 memory 调整为 database，`responses_chat_adapter_sessions` 成为默认会话状态落点。
- `app/routers/proxy.py` 已将 `_log_unsupported_v1_endpoint` 的 `log_type` 改为 `unsupported_endpoint`，将 `_log_v1_preflight` 的 `log_type` 改为 `v1_preflight`，说明入口事件类型应进入协议/入口事件分类，而不是混在鉴权事件中。
- `stage31_responses_chat_adapter_regression_check.py` 已开始同时保护运行时默认值和 `Settings` schema 默认值，避免 adapter storage 默认值在配置层和执行层漂移。

目标内部结构：

- `EndpointRegistry`：登记每个端点的标准路径、HTTP 方法、请求体类型、是否正式计费、是否模型发现接口、是否允许流式。
- `PayloadNormalizer`：只做协议字段归一化，例如 `reasoning_effort`、`reasoning.effort`、legacy image 字段、Completions prompt 转 messages。
- `EndpointConversionPolicy`：只在显式启用兼容适配时判断 Chat 与 Responses 互转是否安全，输出允许、拒绝或降级原因；默认正式请求不做自动端点互转。
- `SseProtocolCodec`：统一解析 SSE chunk、提取 usage、生成 `event: error` 和 `[DONE]`。
- `ProtocolDiagnosticsBuilder`：为能力不支持、端点不匹配和协议转换失败生成结构化诊断。
- `ProviderModelProtocolPolicy`：只解释管理员配置的 `both/chat_completions/responses`，不读取健康探针缓存来修改协议支持。
- `V1EntryEventClassifier`：区分 CORS 预检、不支持端点、请求体结构错误、鉴权失败等入口事件类型，输出给日志领域和错误响应层。

拆分步骤：

1. 先新增协议领域纯函数，不改任何路由行为；把 `/v1/models` 接口族判断、endpoint 能力需求、SSE 错误构造迁入并由旧函数调用。
2. 再把 `ProxyService` 中的 endpoint path 归一化、Completions/Images 兼容判断和 include_usage 处理迁入协议模块。
3. 将 provider_model 挂载级协议配置抽成 `ProviderModelProtocolPolicy`，路由候选只读取配置结果；健康检查只写可用性观测。
4. 将 Responses→Chat 兼容适配注册为显式插件，禁用状态下只返回端点不支持诊断，不进入自动 fallback。
5. 把 `_log_unsupported_v1_endpoint`、`_log_v1_preflight` 的事件类型判断迁到入口事件分类器，路由层只传递分类结果。
6. 最后让 `proxy.py` 只负责读取请求、调用代理用例、返回响应；所有 endpoint 类型和协议错误都从协议模块拿结果。

验收标准：

- `/v1/models` 与 `/v1/models/{model_id}` 的模型发现口径在鉴权、日志、计费、Token 补全、统计中完全一致。
- Chat、Responses、Completions、Images、Files、Embeddings、Moderations 的路由入口不直接拼协议错误文本。
- Chat 请求只命中挂载级配置支持 `chat_completions` 的 provider_model，Responses 请求只命中挂载级配置支持 `responses` 的 provider_model；健康探针失败不得自动改写或收紧协议配置。
- Chat-only provider_model 在未显式开启 Responses→Chat 适配时不得自动承接 `/v1/responses`；启用适配后必须通过共享状态存储支持 `previous_response_id`。
- CORS OPTIONS 预检写入 `v1_preflight`，不支持 `/v1/*` 端点写入 `unsupported_endpoint`，二者不得计入 API Key 鉴权失败。
- `stage31` 必须保护 Responses Chat Adapter 的 runtime 与 settings schema 默认存储均为 `database`。
- SSE 已建立连接后的错误统一输出 `event: error` 并以 `[DONE]` 收尾。
- `stage18`、`stage21`、`stage26`、`stage30`、`stage35` 等协议相关回归通过。

- `CapabilitySet`：领域值对象，只表达支持、不支持、未知和来源，不包含数据库 Session。
- `CapabilityRequirement`：由协议模块和请求 payload 推导出来的本轮要求。

4. 将图片生成能力从历史模型名推断中剥离，只允许显式字段或管理员配置决定。
5. 清理历史 `text` 非流式测试选项，只保留当前规范允许的四类测试功能。

验收标准：

- 任一新能力只需要在能力模块登记一次，模型目录、provider 挂载、健康探针和路由筛选均自动可用。
- 模型映射阶段不读取 provider_model 能力；provider 候选阶段才判断挂载能力。
- 模型详情页、provider 模型挂载页、健康测试和正式代理对同一能力的展示与判断一致。
- `supports_image_generation` 未显式为 true 时，前端不显示生图能力，路由不把该 provider_model 作为图片生成候选，健康探针不把其推断为图片生成可用。

- 不依赖日志写入。

实现方式：

- 将现有 `RouterService.order_candidates`、容量过滤、失败率过滤、会话粘性、候选数限制抽成纯策略。

现有代码证据：

- `RouterService` 负责候选加载、候选排序、会话粘性、健康优先、容量过滤、失败率过滤、内容完整性过滤、候选诊断和近期路由记录。
- `ProviderCapacityService`、`ConcurrencyService`、`RateLimitService` 分别处理 provider 容量、全局/API Key/账户并发和短窗口限流。
- `ProxyService` 在每次上游尝试前后协调候选耗尽等待、可恢复错误重试、容量租约获取与释放。
- 最新代码已把 `ModelMappingService` 中的 provider 候选过滤移除，映射只返回目标模型，路由领域再选 provider。
- API Key 侧旧路由字段已退出，但全局 `SettingUpdate`、`SettingService` 和设置页仍保留 `route_mode`、`default_provider_id`、`manual_allow_fallback` 历史兼容面；目标路由领域需要把它们解释为兼容输入或迁移输入，用户可见主策略仍统一为健康优先。

目标内部结构：

- `RouteRequest`：包含目标模型、端点需求、流式需求、API Key 权限快照、会话键、强制 provider 调试标记、重试上下文。
- `CandidateSnapshot`：只读候选快照，来自仓储和 Redis，不在领域层查询数据库。
- `CandidateFilter`：执行硬约束，包含启停、授权、协议、能力、容量、QPS/RPM、熔断、内容完整性和可信策略。
- `CandidateRanker`：执行软排序，包含健康层级、当前负载、路由得分、近期成功率、延迟、成本和会话粘性；禁止把内容完整性分、可信等级和内容违规次数作为软加减分，避免同一治理事实既硬过滤又软排序。
- `RetryPlanner`：区分请求结构、鉴权授权、能力不支持等不可恢复错误与上游临时故障、限流、超时等可恢复错误。
- `RouteDiagnostics`：记录每个候选被排除的结构化原因，供日志和错误响应读取。
- `RouteSettingsPolicy`：把历史 `route_mode`、`default_provider_id`、`manual_allow_fallback` 兼容字段转换为目标路由策略；正式 `/v1/*` 只暴露健康优先、候选数、容量、重试等待、可信策略等仍有效配置。

拆分步骤：

1. 先让 `RouterService.order_candidates` 返回候选和排除原因，不直接写日志。
2. 把候选过滤和排序的输入改为 `RouteRequest + CandidateSnapshot`，由应用层负责加载 provider、provider_model、健康、容量和内容完整性状态。
3. 把候选耗尽等待从 `ProxyService` 中抽成 `RetryPlanner`，并在代理用例层执行等待和重试。
4. 删除所有权重排序入口，保留 `priority` 只作为配置顺序或次级排序字段。
5. 建立 `RouteSettingsPolicy`，把全局设置中的旧主策略字段从正式候选选择中剥离；若保留默认 provider 直连能力，只能用于内部 playground 或 provider 测试入口。

验收标准：

- 路由领域没有 SQLAlchemy Session、Redis client、LogService import。
- 候选排除原因能区分模型不存在、API Key 白名单、provider 未启用、端点协议不支持、能力不支持、容量满、熔断、内容完整性阻断和可信策略阻断。
- 模型映射命中某个目标模型后，provider 候选阶段仍可因为挂载能力或容量失败而切换其它 provider 或其它映射目标。
- `stage14`、`stage25`、`stage28`、`stage30`、`stage33` 路由相关回归通过。
- 设置页和对外文档不得继续把手动优先、默认 provider、权重分流、故障切换作为正式路由主策略；迁移测试必须证明旧字段残留不会影响正式 `/v1/*` 健康优先候选选择。

### 5.25 日志链路领域模块

所在层：领域层。

职责边界：

- 定义请求摘要、链路事件、错误事件、审计事件、会话回放和日志脱敏规则。

输入：

- 请求上下文。
- 代理链路事件。
- 异常。
- 用户操作。
- 查询条件。

输出：

- `RequestLogSummary`
- `TraceEvent`
- `AuditEvent`
- `ConversationReplay`
- `SanitizedPayload`

领域接口：

- `build_request_summary(context)`
- `build_trace_event(event)`
- `sanitize_payload(payload, policy)`
- `derive_conversation_turn(log)`
- `normalize_reasoning_level(value)`
- `derive_metrics(logs)`

相关数据库表：

- `request_logs`
- 所有 `request_*_events`
- `exception_events`
- `admin_audit_logs`
- `user_operation_audit_logs`
- `asset_events`

依赖：

- 依赖统一错误目录。
- 不依赖计费和路由应用服务。

实现方式：

- 将 `LogService` 的派生字段、脱敏、会话回放、指标计算拆成纯领域规则和查询用例。

现有代码证据：

- `LogService` 既写 `request_logs`，又做 usage 提取、派生字段、指标聚合、CSV 导出、会话回放、日志筛选和 Token finalize 入队。
- `app/logging/*` 已有 envelope、dispatcher、queue、sink、registry 和多类 adapter，是日志事件体系的雏形。
- `app/models/logging_events.py` 已包含请求鉴权、校验、模型权限、路由决策、provider 尝试、上游响应、流事件、错误响应、内容防护、计费、异常、健康、后台任务、用户操作和素材事件表。
- `logging_api.py` 提供统一日志子事件查询，`logs.py` 提供旧请求日志列表、导出、指标和清空能力。
- 最新代码中 `logging_api.py` 新增类型化日志导出 `/api/logging/export`、更细的时间范围与 trace/request_log 过滤、统一时间线构建函数 `build_request_log_timeline_payload`；用户端通过 `/api/user/logs/{log_id}/timeline` 复用该时间线，但先做拥有者校验。
- `app/routers/proxy.py` 已把不支持端点与 CORS 预检分别写为 `unsupported_endpoint` 和 `v1_preflight`；`app/static/js/app.js` 已为这两个日志类型提供中文标签。
- 前端日志详情已增加原始 JSON 截断、计费 token/价格分组、后台任务和素材事件展示，这些展示规则应从日志查询 DTO 或前端展示策略读取，而不是散落在页面脚本里。

目标内部结构：

- `RequestLogSummaryPolicy`：构建请求摘要、状态、模型展示、耗时、TTFB、TPS、模态和错误分类。
- `TraceEventPolicy`：把代理链路事件标准化为可查询、可展示的事件结构。
- `PayloadSanitizerPolicy`：统一请求、响应、metadata、usage、素材摘要的脱敏与截断。
- `ConversationReplayPolicy`：从请求日志中提取对话轮次，支持用户门户和管理员回放。
- `MetricDerivationPolicy`：从日志投影计算成功率、延迟、Token、费用、模型分布和错误分布。
- `LogQueryApplicationService`：承载筛选、分页、导出，不参与写入。
- `TypedLogExportService`：处理异常、健康、计费、后台任务、素材等类型化日志的 CSV 导出。
- `RequestTimelineQueryService`：根据请求日志 ID 和权限上下文查询链路事件，管理端可查任意日志，用户端只能查自己的日志。
- `EntryLogTypePolicy`：统一定义 `unsupported_endpoint`、`v1_preflight`、`api_client_auth` 等入口日志类型的含义、筛选标签和统计归属。
- `LogRawPayloadPresenter`：统一原始 JSON 截断、格式化和敏感字段保护，避免不同详情弹窗各自处理。
- `ContentGuardEventQueryService`：在当前 `/api/logging/content-guard-events` 和日志页 Tab 基础上独立查询 `request_content_guard_events`，支持时间、trace、request_log_id、guard_stage、guard_result、risk_level、action、provider/model、final_strategy 等筛选，并返回稳定 DTO，禁止路由控制器直接拼 SQL 和展示字段。
- `TypedLogCsvSchemaRegistry`：为每一种 typed log 定义固定表头、字段顺序、字段版本和空结果导出规则，避免由当前 items 动态推导 CSV 表头。
- `BillingTypedLogProjection`：把 token finalize 与 billing process 两类结构不同的事件分别投影，前端可合并展示但必须保留 event_family 和各自字段语义。
- `BackgroundJobLogProjection`：只解释调度任务锁事件，不把后台队列 backlog、死信和 worker 存活误混为任务执行结果。

拆分步骤：

1. 先明确 `request_logs` 是摘要事实表，`logging_events` 是链路事件明细表，二者通过 `trace_id` 和 `request_log_id` 关联。
2. 把 `LogService.create_log` 保留为兼容门面，内部调用 `RequestLogWriter`、`UsageExtractor`、`PayloadSanitizer`。
3. 把日志查询、指标、CSV、会话回放、类型化日志导出从写入服务中拆出，删除 adapter 到 `LogService` 的反向依赖。
4. 将当前已有的 `RequestContentGuardEvent` 独立查询接口、日志中心内容防护事件 Tab 和导出入口迁入正式查询/导出用例，保持用户可见功能不变。
5. 把 typed CSV 导出从通用 `_items_to_csv` 迁到 `TypedLogCsvSchemaRegistry`，先为异常、健康、计费、后台任务、素材、内容防护定义稳定表头。
6. 将计费日志合并展示改为“前端可合并、后端投影分开”，token finalize 与 billing process 的筛选、详情和 CSV 字段分别定义。
7. 将后台任务日志与队列观测拆开：后台任务日志只展示调度任务生命周期，队列页面或监控指标展示 backlog、消费延迟、死信、worker 存活。
4. 把 `logging_api.py` 中的 SQL 过滤、分页、CSV 序列化和时间线构建迁到查询/导出用例。
5. 把日志类型中文标签和前端筛选枚举从散落 JS 常量迁到共享展示配置或由 API 输出。
6. 统一日志队列和 request_log 队列的 envelope，后台 worker 只消费标准事件。

验收标准：

- 写日志、查日志、导出、指标、会话回放可以分别单测。
- request adapter 不再 import `LogService`，日志模块内部无循环依赖。
- usage 明细和敏感字段脱敏策略在旧列表、新事件详情、CSV 和用户门户中一致。
- 用户端请求时间线必须先通过 `UserPortalService.get_owned_request_log` 或等价拥有者校验，禁止仅凭 log_id 查询事件。
- 类型化日志导出必须复用列表筛选条件，避免页面看到的数据和导出的 CSV 不一致。
- 日志队列不可用时请求日志可回退同步落库，且不会影响统一事件 schema。
- `unsupported_endpoint` 与 `v1_preflight` 在日志筛选、详情、导出和统计中能独立识别，不再混入 `api_client_auth`。
- 原始 JSON 超过展示上限时必须截断并提示截断，不能直接渲染完整超大 payload。

### 5.26 内容防护领域模块

所在层：领域层。

职责边界：

- 定义内容检测规则、风险等级、URL 检测、结构检测、流式检测策略、处置决策。
- 定义预先可信探针、运行时防护、规则算法三类职责的边界。
- 维护 provider / provider_model 内容完整性状态的领域语义，但状态落库必须通过应用层或仓储端口完成。
- 为路由领域提供可复用的可信决策值，而不是让路由领域重新解释规则或同步执行高成本探针。

输入：

- 请求 payload。
- 响应文本或 JSON。
- SSE chunk。
- provider 信任等级。
- provider_model 内容完整性状态。
- 系统规则。
- 可信探针结果。

输出：

- `ContentGuardResult`
- `GuardDecision`
- `GuardAction`
- `ContentIntegrityStateChange`
- `TrustProbeDecision`
- `ContentGuardViolationEvent`

领域接口：

- `inspect_text(input) -> ContentGuardResult`
- `inspect_json(input) -> ContentGuardResult`
- `inspect_sse_chunk(input) -> ContentGuardResult`
- `decide_action(result, policy) -> GuardDecision`
- `update_integrity_state(current, violation) -> IntegrityState`
- `parse_rules(json) -> list[Rule]`
- `run_trust_probe(target) -> TrustProbeReport`
- `get_route_trust_decision(provider, provider_model, route_context) -> TrustProbeDecision`

相关数据库表：

- `app_settings`
- `providers`
- `provider_models`
- `request_logs`
- `request_content_guard_events`
- `alert_events`

依赖：

- 不依赖路由应用服务。
- 路由领域读取它输出的内容完整性状态。
- 代理用例层可以调用运行时防护接口，但内容防护领域禁止反向 import 代理用例层。
- 健康熔断领域可以调用预先探针计划或结果聚合接口，但禁止自行硬编码内容防护规则。

实现方式：

- 将 `ContentGuardService` 中检测和处置分离。
- 内容防护只输出决策，不直接切换 provider。
- 现有三段服务作为过渡起点：规则算法放入 `ContentGuardRuleService`，运行时检测和动作判断放入 `ContentRuntimeGuardService`，可信探针和路由可信决策放入 `ContentTrustProbeService`。
- 原 `ContentGuardService` 最终退化为兼容门面或被拆空，避免继续作为所有内容防护逻辑的中心。

现有代码证据：

- `ContentGuardService` 负责文本规则、JSON 响应、SSE 事件、URL 检测、风险等级、命中摘要和默认规则。
- `ContentGuardRuleService` 已新增为内容防护规则与算法入口，当前继承 `ContentGuardService`，实际复用原服务的确定性规则引擎；它是未来规则注册表、风险评分器、检测算法扩展的过渡落点。
- `ContentRuntimeGuardService` 已新增为请求过程中防护服务，负责非流式响应检测、流式首段预缓冲检测、后续 chunk 检测、`block` / `switch_provider` / `record_only` / `safe_error` / `async_review` / `allow` 等动作决策、运行时违规记录、高风险策略、流式模式和缓冲判断。
- `ContentRuntimeGuardService` 仍在 `inspect_stream_prefetch_buffer`、`inspect_stream_chunk`、`build_guard_error`、`record_runtime_violation` 中导入 `ProxyService`，用于 SSE payload 消费、字节缓冲、内容防护错误构造和违规落库；这说明当前拆分已经改善职责，但还没有彻底解除代理反向依赖。
- `ContentTrustProbeService` 已新增为预先防护服务，固定必需探针为 `fixed_answer`、`pollution_rules`、`sse`，负责 `run_trust_probe`、`run_capability_probe`、`update_provider_model_trust_status`、`get_trust_decision_for_route`、目标解析、端点解析、单探针执行、跳过探针、摘要聚合和内容防护结果聚合。
- `ContentGuardModuleService` 负责后台页面总览、配置保存、规则保存、规则重置、文本检测和 provider/providermodel 序列化。
- `ContentGuardProbeService` 负责外部渠道与内部 provider 的固定答案、外链广告识别、JSON、工具调用、SSE 等探针；其中可信状态必需探针收敛为固定答案、外链广告识别、流式污染检测。
- 最新代码中 `ContentGuardProbeService` 在探针结果为 `block` 时会立即把 provider_model 标记为 `blocked` 并打开熔断；若未出现单次 block，同一失败窗口内失败次数达到 3 次也会触发同类状态变更。
- `ProxyService` 在非流式和流式代理链路中执行内容完整性检测，并在高风险时记录日志、切换候选或返回错误。
- `SystemMetricsService` 会根据内容完整性高风险自动隔离 provider 并写入告警。
- `RouterService` 已通过 `ContentTrustProbeService.get_trust_decision_for_route` 在候选选择阶段读取可信决策，排除 blocked、低内容完整性评分或不满足可信要求的 provider / provider_model。
- `HealthService` 已调用 `ContentTrustProbeService.run_trust_probe` 和 `update_provider_model_trust_status`，并导入 `ContentGuardRuleService`，说明健康检查正在复用内容防护模块，而不是重新维护一套检测规则。
- 最新代码新增 `/api/content-guard/trust-probe`，由 `ContentGuardModuleService.run_trust_probe` 固定执行固定答案、外链广告识别、流式污染检测三类可信探针；`probe_pollution_rules` 会覆盖短链、外链、广告意图规则命中。
- `ContentGuardProbeService.build_health_phase_specs` 开始向健康检查提供内容完整性阶段计划，健康模块不再自己硬编码全部内容探针。
- 根目录 `内容防护模块问题全审查.md` 已归档 700 条内容防护问题，进一步证明该模块的重构必须同时覆盖配置缓存、规则引擎、运行时策略、可信探针、外部渠道安全、typed event 迁移、日志证据展示、前端交互和测试治理，而不能只停留在服务文件拆分。
- 根目录 `问题.md` 进一步补充了更细的当前缺口：内容防护 typed event 已有模型、迁移、时间线、独立列表、日志 Tab 和导出入口，但缺少稳定 `ContentGuardEventProjection`、详情证据一致性和固定 CSV schema；手动健康测试内容探针未完整展开到健康事件；`record_only` 或关闭高风险拦截仍可能污染 provider 治理状态；SSE 探针与文本/JSON 探针可能没有完全复用同一规则 JSON；规则基础校验已有推进，`image_url` 外链已开始进入扫描，外部目标已增加 DNS 解析私网拒绝，但规则 JSON 损坏提示、ReDoS 复杂度、工具参数/复杂 Responses 扫描一致性、DNS 解析到真实请求绑定和外部检测 API Key 生命周期仍需要作为重构验收项。

目标内部结构：

- `ContentRuleRegistry`：规则注册、解析、校验和版本化，替代散落硬编码。
- `ContentGuardRuleService`：当前代码中的规则算法过渡服务；目标状态下应迁移为 `ContentRuleRegistry + ContentInspector` 的应用门面，不再继承原巨型服务。
- `ContentInspector`：纯检测器，输入文本、JSON 或 SSE chunk，输出命中规则、风险等级、证据摘要和耗时。
- `ContentGuardPolicy`：根据系统开关、provider 信任等级、流式阶段、风险结果决定放行、阻断、切换候选、告警或隔离。
- `ContentRuntimeGuardService`：当前代码中的运行时防护过渡服务；目标状态下应只依赖 `ContentInspector`、`ContentGuardPolicy`、SSE 解析端口、违规事件写入端口和统一错误构造器，禁止再依赖 `ProxyService`。
- `IntegrityStatePolicy`：处理 provider 与 provider_model 的 `trusted/partial/untrusted/blocked/unknown` 状态变迁。
- `ContentProbePlanner`：定义内部 provider 探针和外部渠道探针计划。
- `ContentTrustProbeService`：当前代码中的预先可信探针过渡服务；目标状态下负责探针编排、结果聚合和路由可信决策值生成，但状态写入通过 `IntegrityStatusService` 或仓储端口完成。
- `TrustProbeDecision`：定义可信检测必需探针、聚合判断、人工确认来源、真实探针来源、失败次数、最近通过/失败时间、展示原因和是否允许持久化；内部目标只有本次 probe_keys 覆盖完整必需探针时才允许更新 provider_model 可信状态。
- `PollutionRuleProbe`：专门验证短链、外链、广告意图等污染规则是否能被当前规则集识别。
- `SseGuardEventParser`：从 `ProxyService` 中剥离 SSE data payload 消费和有限字节缓冲，供运行时防护与代理流式链路共同复用。
- `ContentGuardViolationWriter`：写入运行时违规记录、告警事件、request log 摘要的端口，避免领域服务直接写库或调用代理 helper。
- `ContentGuardConfigApplicationService`：统一保存内容防护设置、规则、URL 白名单、自动预检间隔和外部检测配置；负责触发 settings、provider runtime、route candidates、v1 models、模型选项等缓存失效。
- `ExternalContentProbePolicy`：在已有 `https`、localhost/内网/IP 地址、域名 DNS 解析私网拒绝和长度校验基础上，继续限制解析结果与真实请求不一致、响应大小、总超时、API Key 生命周期、base_url 脱敏和外部目标稳定 ID，避免 SSRF、明文 HTTP、内网探测、密钥残留或审计对象不可追踪。
- `ContentGuardEventProjection`：把 request_logs 摘要、request_content_guard_events、日志详情、内容防护页面最近事件、健康内容探针和 CSV 导出的字段统一为 stage、action、final_strategy、retry_count、buffer_wait_ms、matched_rules、matched_excerpt、state_change 等结构。
- `ContentGuardFrontendModules`：把内容防护页面拆为配置表单、规则表、规则编辑器、Tab 状态、治理列表恢复/隔离操作、探针选择、内部检测、外部检测、结果详情、危险操作确认和移动端详情披露组件。
- `ContentGuardActionStateMachine`：把 `guard_result`、系统开关、高风险策略、是否已发送 SSE、API Key 策略、provider 开关、历史 blocked 状态转换成唯一动作，明确 `record_only` 只写证据、不扣分、不熔断、不隔离。
- `ContentProbeStateTransitionPolicy`：专门处理健康内容探针、可信探针和运行时污染结果到 provider/provider_model 状态的转换，明确单次 `block`、连续失败 3 次、手动探针、自动探针、恢复探针和关闭开关时的状态写入规则。
- `ContentGuardRuleValidationService`：承接当前 schema 层已落地的 regex、枚举、动作语义、`allow`/`block` 约束和 `reason` 保留校验，并继续补齐规则 JSON 损坏错误、重复 ID、导入/重置预览、ReDoS 复杂度、文本/JSON/SSE/工具参数/复杂 Responses 输出等结构化字段的扫描口径；`image_url` 已开始进入扫描，目标要把它固化为规则引擎统一契约。
- `HealthContentProbeProjection`：把手动健康测试附带的 `content_probe_results` 投影为健康探针事件或内容防护事件，保证健康日志详情、导出、手动测试弹窗看到同一份内容探针证据。
- `ContentGuardRequestSummaryPolicy`：约束一次外部用户请求在 request summary 中只形成一个用户可见汇总；候选切换、运行时命中、SSE 中断等过程通过 typed event 表达，避免污染请求数和失败率。

拆分步骤：

1. 把规则解析和默认规则迁入 `ContentRuleRegistry`，后台页面只读写规则 JSON。
2. 把检测结果和处置决策分离：检测器不写库、不切换 provider、不发告警。

- `request_content_guard_events` 等 typed event 表已有正式迁移；从空库执行迁移后必须验证内容防护日志查询、详情 projection 和 CSV 稳定表头可用。
- 内容防护日志详情必须展示命中规则、匹配片段、分类、处置动作、最终策略、重试 provider 数和 provider/model 状态变化，不能只展示 result/risk 摘要。
- 内容防护页面必须通过浏览器 smoke：空 provider 状态、规则分页/筛选、规则编辑 reason 字段、非法 regex 提示、删除确认、恢复默认预览、探针选择说明、外部密钥清理和移动端规则详情均可用。

- SSE 探针、文本检测、JSON 检测、工具参数、复杂 Responses 输出和 `image_url` 扫描必须复用同一规则集；自定义规则保存后，各检测链路均能命中或明确解释为何跳过。

### 5.27 健康熔断领域模块

所在层：领域层。

职责边界：

- 定义健康状态、探针结果、熔断状态、恢复策略、失败率状态。

输入：

- 探针响应。
- provider 当前状态。
- route success/failure。
- 时间窗口统计。

输出：

- `HealthState`
- `CircuitState`
- `ProbeResult`
- `RecoveryDecision`

领域接口：

- `evaluate_probe_result(response) -> ProbeResult`
- `transition_health_state(current, probe_result)`
- `transition_circuit_state(current, failure_event)`
- `should_recover(state, now)`
- `compute_health_score(events)`

相关数据库表：

- `providers`
- `provider_models`
- `health_check_runs`
- `health_probe_events`
- Redis 健康桶。

依赖：

- 依赖能力领域模块。
- 不依赖代理用例。

实现方式：

- 将 `ProviderHealthStateService` 和 `HealthService` 的状态变迁规则拆到领域层。

现有代码证据：

- `HealthService` 负责单 provider、批量 provider、provider_model、文本流式、视觉、工具、图片生成、连接性和定时健康检查。
- `ProviderHealthStateService` 使用 Redis 记录 provider、模型、能力级状态，以及 route success/failure。
- `ProviderCapacityService` 与路由候选会使用容量、健康和失败率结果排除不可用 provider。
- `AlertService` 和 `SystemMetricsService` 会读取健康异常、后台积压和 provider 失败率生成告警。
- 最新代码中单模型即时测试通过 `normalize_test_features` 与 `phase_keys_from_test_features` 标准化测试功能，并以交互式短预算、并行阶段、单端点模式执行。
- 内容完整性健康阶段开始复用 `ContentGuardProbeService.build_health_phase_specs`；端点协议支持不再由健康探针结果反推，健康只记录可用性和能力观测。

目标内部结构：

- `ProbeResultClassifier`：把上游响应、异常、超时、内容异常归类为健康、降级、异常、未知。
- `HealthStateMachine`：定义 provider、provider_model、capability 三层状态变迁。
- `CircuitBreakerPolicy`：根据失败率、连续失败、时间窗口和恢复探针决定 open/half_open/closed。
- `HealthProbePlan`：根据能力模块输出探针计划，避免重复探测。
- `HealthProjection`：为前端提供健康、异常原因、可信原因和问号 Tooltip 摘要。
- `InteractiveProbePolicy`：定义后台单模型即时测试的最大 token、阶段并行、单端点选择和超时预算。
- `ProbeObservationPolicy`：把探针结果作为观测事件保存，禁止它反向改写 provider_model 挂载级端点协议配置。

拆分步骤：

1. 把 `HealthService` 中的探针执行和结果解释拆开，探针执行仍在应用层，结果解释进入领域层。
2. 将 provider 汇总健康、模型聚合健康和可信状态分别建模，禁止一个字段混用多个语义。
3. 将 Redis 健康桶读写封装为健康状态端口，领域层只接受快照。
4. 把内容完整性阶段计划交给内容防护模块提供，健康模块只编排执行顺序和保存观测。
5. 后台定时健康检查、手动测试、路由失败回写复用同一状态机。

验收标准：

- 模型聚合状态只展示健康或异常，只要存在任一可用绑定渠道即为健康。
- provider 可用性与可信属性分开计算，不再把“全部可用”解释为可信。
- 手动健康检查可以选择文本流式、视觉、工具调用、图片生成四类功能，且不会重复探测同一模型绑定。
- 健康检查不得自动收紧 Chat Completions / Responses 端点协议支持；协议支持只能由管理员挂载级配置决定。
- 单模型即时测试必须在短预算内返回已完成和超时结果，并且同一能力只执行一次。
- 路由失败、健康探针失败和内容完整性阻断能在日志和前端展示中区分原因。

相关数据库表：

- `LeaseStore`：并发租约、provider 容量租约和幂等释放原子脚本。
- `RateLimitStore`：滑动窗口或短窗口 QPS/RPM 计数。
- `QueueStore`：stream、processing、dead letter、队列长度和恢复。

3. 把模型目录、provider、API Key 鉴权等热路径缓存失效入口集中登记。
4. 在监控接口暴露缓存命中率、L1 命中率、队列长度、租约计数和 Redis 错误摘要。

验收标准：

- 生产多 worker 下并发、QPS/RPM、provider 容量计数一致。
- 租约重复释放不会导致计数为负。
- Redis 不可用时，本地开发可降级，生产正式路由必须按规范返回明确错误或禁用高风险降级。
- 写操作后相关缓存主动失效，不能靠硬编码极短 TTL 掩盖一致性问题。

### 5.30 上游 HTTP 客户端模块

所在层：基础设施层。

职责边界：

- 管理 httpx/aiohttp client。
- 执行上游 JSON、流式、multipart、文件请求。
- 处理连接池、超时、响应体大小限制、SSE chunk 读取。

输入：

- `UpstreamRequest`
- provider endpoint。
- headers。
- payload 或 form data。

输出：

- `UpstreamJsonResponse`
- `UpstreamStreamResponse`
- `UpstreamError`

接口：

- `send_json(request) -> UpstreamJsonResponse`
- `open_stream(request) -> AsyncIterator[bytes]`
- `send_raw(request) -> UpstreamRawResponse`
- `close()`

相关数据库表：

- 无。

依赖：

- 依赖配置模块。
- 不依赖路由、日志、计费。

实现方式：

- 将 `UpstreamClientService` 扩展为端口实现。
- `ProxyApplicationService` 只依赖上游端口。

现有代码证据：

- `UpstreamClientService` 管理 httpx、HTTP/1 client、aiohttp session 和上游连接池。
- `ProxyService` 直接构造上游 URL、headers、payload、multipart、流式读取、非流式响应读取和响应体大小限制。
- 健康探针、内容探针、playground 和真实上游测试也会走相似的上游 HTTP 调用逻辑。
- 流式场景需要首 token 超时、空闲超时、最大持续时间、客户端中断和 SSE usage 提取。

目标内部结构：

- `UpstreamRequestBuilder`：构建 base_url、path、headers、query、json、multipart 和 timeout。
- `UpstreamHttpClient`：发送非流式 JSON/raw/multipart 请求。
- `UpstreamStreamClient`：打开流式响应并暴露 async iterator。
- `ResponseSizeGuard`：统一上游响应体字节上限、流式日志缓存上限和截断策略。
- `UpstreamErrorMapper`：将 httpx/aiohttp/网络/超时/状态码异常映射为统一错误目录。

拆分步骤：

1. 从 `ProxyService` 中抽出上游请求构造，保持 payload 不被隐式重排，保护 prompt cache 命中率。
2. 将非流式和流式发送统一封装为端口，代理、健康、内容探针都依赖端口。
3. 将响应体上限、SSE 超时、客户端取消和上游异常映射放入客户端模块或错误映射模块。
4. 用 mock 上游端口替换大量 monkeypatch，降低回归脚本对内部实现的依赖。

验收标准：

- 代理用例不 import httpx、aiohttp。
- 非流式响应超过上限时停止读取并返回明确错误。
- 流式连接在上游错误、空流、超时、客户端取消时有明确终态和日志。
- 上游 client 关闭由应用 lifespan 和独立 worker 生命周期统一处理。

- `run_logging_event_job(payload)`

- `run_adapter_session_cleanup_job(payload)`

相关数据库表：

- `background_job_events`

- `billing_process_events`
- `request_logs`
- 所有日志事件表。

依赖：

- 后台任务层依赖应用用例层。
- 应用层只发布任务，不依赖具体 worker。

实现方式：

- 统一 `RequestLogQueueService`、`LoggingQueue`、`TokenUsageService` 中的队列协议。
- `app/tasks.py` 只保留 schedule 配置，具体任务调用 application job handler。

现有代码证据：

- `RequestLogQueueService` 负责请求日志可靠入队、processing 恢复、后台 worker、批量写库和本地降级。
- `LoggingQueue` 负责统一日志事件队列和数据库 sink。
- `TokenUsageService` 负责 Token finalize worker、队列入队、后台补全和计费触发。
- `app/tasks.py` 负责定时健康检查、数据保留、Token 补全、计费处理、日志队列刷新、告警刷新等任务。
- 部署规范支持 Web 进程和后台 worker 分离，`scripts/run_background_workers.py` 承接独立 worker 入口。
- 最新 `distributed_job_lock` 在 Redis 锁不可用时会跳过任务并记录 `skipped_lock_unavailable`；抢锁失败记录 `skipped_locked`；任务运行中、成功、失败、取消都写 `BackgroundJobEvent`。
- 定时任务返回值已开始携带 `processed_count`、`success_count`、`failed_count`，日志中心可按后台任务状态、锁状态、时间范围筛选。
- 内容完整性 L3 定时探针使用 `content_guard_probe_interval_sec`，且仅在内容防护总开关和预先防护自动检测开关同时开启时执行。
- 当前后台任务日志仍主要覆盖 `distributed_job_lock` 装饰器链路，独立 worker、请求日志队列、统一日志事件队列、Token finalize 队列、计费队列的消费状态没有完全进入同一观测模型；目标架构必须把调度任务生命周期与队列消费生命周期分开建模。
- 当前任务先写 `running` 再更新终态，若进程崩溃可能长期停留在运行中；目标架构需要心跳、超时、stale running 标记和人工修复入口。

目标内部结构：

- `JobEnvelope`：统一 job_type、payload、idempotency_key、trace_id、attempt、created_at。
- `QueueRouter`：按 job_type 路由到 request_log、logging_event、token_finalize、billing、health、retention 等队列。
- `JobHandlerRegistry`：登记每类后台任务的 handler。
- `RetryPolicy`：定义最大次数、退避、死信和可恢复错误。
- `SchedulerConfig`：只描述定时任务，不包含业务执行逻辑。
- `DistributedLockPolicy`：定义锁获取、锁不可用跳过、抢锁失败跳过、锁释放和状态事件。
- `WorkerRuntime`：启动、停止、排空、健康检查和积压指标。
- `QueueObservationProjection`：统一记录 backlog、oldest_pending_age、consume_lag、retry_count、dead_letter_count、active_worker_count、last_consume_error。
- `JobHeartbeatStore`：记录长任务心跳和最后活跃时间，用于 stale running 检测。
- `DeadLetterQueueService`：接收不可恢复失败或超过最大重试次数的任务，提供查看、重放和丢弃入口。
- `JobTriggerPolicy`：规范 `scheduler`、`manual`、`startup`、`system`、`worker` 等触发来源，禁止所有任务都落为默认 scheduler。

拆分步骤：

1. 先定义统一 job envelope，旧队列在消费前适配为 envelope。
2. 将 `TokenUsageService`、`RequestLogQueueService`、`LoggingQueue` 的 Redis stream 操作迁入 QueueStore。
3. 把 `app/tasks.py` 中的业务函数改为调用应用层 job handler。
4. 独立 worker 启动时只加载必要模块，避免 Web-only 依赖和前端模板进入后台进程。
5. 将锁状态、跳过原因、处理数量和失败数量纳入统一 job result schema，避免每个任务各自拼 `BackgroundJobEvent`。
6. 为所有长任务写心跳，后台任务列表按超时阈值把长期 running 标记为 stale，并允许运维查看最后心跳和最后处理对象。
7. 为 request log queue、logging queue、token finalize queue、billing queue 分别输出队列观测投影，监控页面和日志中心不要只依赖 `BackgroundJobEvent` 判断后台健康。
8. 为触发来源传递统一 `trigger_type`，手动触发、启动触发、系统触发、调度触发在查询和导出中可区分。

验收标准：

- Web worker 可通过 `ENABLE_BACKGROUND_WORKERS=false` 关闭后台任务，但请求日志仍可靠入队。
- 至少一个独立后台 worker 消费队列时，日志默认刷新实时性控制在 1-2 秒内。
- Token finalize 和账单处理具备幂等性，重复消费不重复扣费。
- 队列积压、处理失败、死信数量和最近错误能在监控页面展示。
- Redis 分布式锁不可用时定时任务不执行函数体，并产生可查询的后台任务事件。
- 后台任务列表、CSV 导出和监控指标中的 processed/success/failed 口径一致。
- 后台任务页面能区分“调度任务状态”和“队列消费状态”；队列积压、死信、消费延迟和 worker 存活不再混进普通任务成功率。
- 进程崩溃后长期 running 任务会在下一轮扫描中标记为 stale 或 failed_timeout，并保留最后心跳、锁键和错误摘要。
- 手动触发、启动触发、系统触发、调度触发在 `trigger_type` 筛选和 CSV 导出中保持真实来源。

- `providers.weight`、`provider_models.weight` 不属于目标结构；当前仅允许以 ORM 属性别名形式兼容旧调用，实际语义映射到 `priority`。
- `api_client_keys.trusted_providers_only` 不属于目标 API Key 策略；可信 provider 开关归属 `app_settings.trusted_providers_only`。
- `api_client_keys.balance_amount` 不属于目标余额事实来源；余额事实来源归属 `user_accounts.balance_amount` 和 `user_account_billing_records`，API Key 只保留 owner 与成本累计。
- `request_logs` 新增的 `reasoning_tokens`、`prompt_audio_tokens`、`completion_audio_tokens`、`accepted_prediction_tokens`、`rejected_prediction_tokens`、`token_source`、`upstream_usage_missing`、`usage_details_json` 归属日志链路和计费账本共同读取，但写入口径必须由日志写入/usage 提取模块统一提供。
- `provider_models.cache_write_price_per_1k` 与账单表 cache read/write 字段归属计费账本读取；模型管理只负责配置，计费模块负责解释。
- `request_logs` 中用于请求正文、响应正文、metadata 和 usage 明细的大字段必须继续受日志开关和字节上限控制，禁止为了排障绕过 payload 日志保护。
- 新增表必须先进入迁移治理模块，不能只在 `app/main.py` 启动期补 DDL。

表访问边界：

- 写模型配置只能通过模型用例或模型仓储，路由领域不得直接更新 `model_catalogs`。
- 写 provider 健康或内容完整性状态必须通过健康/内容防护领域事件，再由应用层调用 provider 仓储落库。
- 写账单流水必须通过计费账本模块，API Key 管理模块只读取余额和策略快照。
- 写日志事件必须通过日志写入端口或队列，业务模块只发布结构化事件。

## 9. 关键业务流程的目标实现

### 9.1 外部 Chat/Responses 请求流程

```text
ExternalOpenAIProxyAPI
  -> ProxyApplicationService
  -> ProtocolDomain 解析端点
  -> ApiKeyPolicyDomain 鉴权与权限
  -> CapabilityDomain 识别能力
  -> ModelDomain 解析模型映射
  -> RoutingDomain 选择候选
  -> RedisState 获取并发/容量租约
  -> ContentGuardDomain 前置策略
  -> UpstreamHttpClient 调用上游
  -> ContentGuardDomain 响应检测
  -> LoggingApplication 写 request_logs 和事件
  -> BackgroundQueue 入队 usage/billing
  -> 返回 JSON 或 SSE
```

此流程中，路由层不计算路由，路由领域不写日志，计费不反向调用 API Key 管理，健康检查不依赖代理主链路。

### 9.2 提供商创建或更新流程

```text
AdminProviderAPI
  -> ProviderApplicationService
  -> ProviderDomain 校验配置
  -> CapabilityDomain 规范化模型能力
  -> ProviderRepository 保存 providers/provider_models
  -> DomainEvent: ProviderChanged
  -> CacheInvalidationHandler 清缓存
  -> AuditEventWriter 写 admin_audit_logs
```

API Key 绑定同步通过事件处理，禁止 `ProviderApplicationService` 直接调用 API Key 管理服务。

### 9.3 模型映射选择流程

```text
ProxyApplicationService
  -> ModelApplicationService 或 ModelDomain
  -> 读取 model_mappings
  -> 读取目标模型目录快照
  -> 读取 API Key 模型白名单与同会话近期成功目标
  -> ModelDomain 按映射启停、目标模型存在性、全局启停、白名单、近期目标和配置顺序选择目标模型
  -> 返回 selected_model_name + trace
```

模型映射只做模型选择，不做 provider 请求，也不提前执行 provider 挂载级能力、容量、熔断、内容完整性或可信策略判断。选出目标模型后，再进入 RoutingDomain，由路由领域模块基于该目标模型加载候选提供商和挂载模型，并统一执行端点协议、流式、视觉、工具调用、图片生成、容量、熔断、内容完整性、可信策略、健康、负载和路由得分判断。

### 9.4 Token 和计费流程

```text
ProxyApplicationService 写 request_logs
  -> BackgroundQueue: UsageFinalizeJob
  -> BillingUsageApplicationService
  -> TokenEstimator / UsageExtractor
  -> RequestLogRepository 更新 usage
  -> BackgroundQueue: BillingFinalizeJob
  -> CostCalculator
  -> BalanceLedger
  -> BillingRepository 写账单
  -> ApiKey/UserRepository 幂等更新余额
  -> BillingEventWriter 写 billing_process_events
```

请求主链路不重复扣费。重复任务按 idempotency_key 跳过。

### 9.5 健康检查流程

```text
Scheduler or AdminAPI
  -> OperationsApplicationService
  -> HealthProbeRunner
  -> UpstreamHttpClient
  -> HealthDomain 评估 ProbeResult
  -> HealthResultWriter 更新 providers/provider_models
  -> HealthEventWriter 写 health_check_runs/health_probe_events
  -> AlertRuleEngine 生成告警
```

健康检查不调用 `ProxyApplicationService`，避免健康模块与代理模块循环依赖。

### 9.6 内容完整性防护流程

```text
AdminAPI / Scheduler
  -> ContentTrustProbeService.run_trust_probe
  -> ContentGuardProbeService 执行 fixed_answer / pollution_rules / sse
  -> TrustProbeDecision 聚合可信结果
  -> IntegrityStatusService 更新 provider_model 可信状态

RouterApplicationService
  -> ContentTrustProbeService.get_trust_decision_for_route
  -> 基于已沉淀 trust_level / content_integrity_status / content_integrity_score 过滤候选
  -> CandidateRanker 只按健康、容量、失败率、延迟、成本、优先级、会话粘性等排序，不再把信任等级或内容违规次数混入软分

ProxyApplicationService 或 HealthProbeRunner
  -> ContentGuardDomain.inspect
  -> ContentGuardPolicy.decide_action
  -> 若代理首段未发送且允许切换，返回 switch_provider
  -> 若已发送 SSE，返回 emit_error_and_done
  -> IntegrityStatusService 更新内容完整性状态
  -> ContentGuardEventWriter 写事件
```

内容检测只输出结果和动作建议，不直接调用路由服务。运行时防护可以由代理用例层调用，但 `ContentRuntimeGuardService` 不应反向导入 `ProxyService`；可信路由判断只能读取已有状态，不应在正式请求前同步发起真实探针。

## 13. 实施顺序建议

架构重构不能直接大规模移动代码。建议顺序：

1. 增加架构依赖检查脚本。
2. 引入 DTO 和端口接口，但保留旧服务调用。
3. 从 `ProxyService` 提取协议、能力、上下文对象。
4. 提取路由领域纯规则。
5. 解开 Responses adapter 与 ProxyService 双向依赖。
6. 提取日志写入端口，消除 request_adapter 与 LogService 循环。
7. 提取计费账本领域和后台任务。
8. 提取健康探针，不再依赖代理服务。
9. 提取内容防护决策和状态更新。
10. 提供商、模型、API Key 服务按 command/query 拆分。
11. 前端 JS/CSS 模块化。
12. 迁移体系标准化。
13. 回归脚本迁入 pytest 分层。

每一步都必须做到：

- 对外接口不变。
- 数据库不丢字段。
- 页面视觉不变。
- stage 回归至少覆盖受影响模块。
- 架构依赖检查只变好，不变差。

阶段交付颗粒度：

| 阶段 | 最小交付物 | 不允许做的事 | 必跑验证 |
|---|---|---|---|
| 1. 依赖检查 | import 图脚本、循环依赖报告、模块归属配置 | 直接大规模移动文件 | 架构检查脚本只报告、不阻断 |
| 2. DTO 与端口 | 核心请求上下文、路由请求、usage、billing、日志事件 DTO | 修改对外 JSON 字段名 | Pydantic/schema 兼容测试 |
| 3. 协议能力抽取 | EndpointRegistry、CapabilitySet、SSE codec | 改变 `/v1/*` 路径和错误结构 | stage18、stage21、stage30、stage35 |
| 4. 路由领域抽取 | CandidateFilter、CandidateRanker、RouteDiagnostics | 把 provider 判断重新塞回模型映射 | stage14、stage25、stage28、stage30 |
| 5. 日志计费抽取 | UsageExtractor、RequestLogWriter、CostCalculator | 重复扣费或从文本反推 usage | stage34、stage35 |
| 6. 内容健康抽取 | ContentGuardPolicy、HealthStateMachine | 关闭内容防护后仍告警或隔离 | stage33、健康检查回归 |
| 7. 仓储队列迁移 | UnitOfWork、QueueStore、JobEnvelope | 生产 Web worker 启动期执行 DDL | 队列排空测试、迁移 dry-run |
| 8. 前端模块化 | JS/CSS 按页面拆分、共享组件 | 重设计界面或改变操作流程 | 核心页面手工验收和截图比对 |
| 9. 测试治理 | stage 迁入 pytest、架构检查阻断新增循环 | 删除历史脚本入口 | 全量回归与架构检查 |

每个阶段完成后必须更新本目录下相关审查文档，说明真实代码已完成到哪一步、还剩哪些临时兼容层。

## 14. 最终目标状态

最终项目应该满足：

- 7 层边界清晰。
- 33 个一等模块职责明确。
- 路由层无业务决策。
- 领域层无框架依赖。
- 服务层无循环依赖。
- 基础设施可替换。
- 后台任务可独立运行。
- 前端模块化但界面不变。
- 数据库迁移可追踪。
- 回归测试可自动执行。
- 新增 provider、模型能力、端点协议、计费策略、内容防护规则、健康探针时，只需扩展对应模块，不需要横向修改多个超大文件。
