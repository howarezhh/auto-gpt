# aotu-gpt 功能分析

## 1. 审查范围与依据

本文件基于当前工作区代码审查生成，覆盖根目录、`app/`、`scripts/`、`migrations/`、`stage*_regression_check.py`、模板与静态资源。核心代码规模包括 166 个 Python 文件，主要实现集中在：

- 应用入口：`app/main.py`
- 路由层：`app/routers/*.py`
- 服务层：`app/services/*.py`
- 数据模型层：`app/models/*.py`
- 接口数据结构：`app/schemas/*.py`
- 前端页面与交互：`app/templates/*.html`、`app/static/js/app.js`、`app/static/css/app.css`
- 后台任务与调度：`app/tasks.py`、`app/scheduler.py`
- 运维脚本与验证脚本：`scripts/*`、`stage7` 到 `stage36` 回归脚本
- 数据库补丁：`migrations/*.sql` 与 `app/main.py` 内置迁移补字段逻辑

项目定位是一个基于 FastAPI 的个人或小团队多提供商统一管理与 OpenAI 兼容代理系统。它不只是简单转发服务，而是包含提供商治理、模型目录、API Key 权限、用户门户、日志计费、内容完整性防护、健康检查、监控告警、压测与部署的一体化平台。

## 2. 总体功能地图

项目功能可分为以下大类：

1. 对外 OpenAI 兼容代理入口。
2. 多提供商管理与模型挂载。
3. 模型目录与模型映射。
4. API Key 管理、授权、限额、余额与批量策略。
5. 用户账户与普通用户门户。
6. 统一请求日志、链路事件、会话回放与审计。
7. Token 统计、费用计算、余额扣减与账单。
8. 健康检查、能力探测、熔断、恢复与路由可用性治理。
9. 内容完整性防护与低信任 provider 管控。
10. 路由策略、容量租约、限流、重试与会话粘性。
11. Responses 与 Chat Completions 协议适配。
12. Playground、用户自检与素材上传。
13. 监控指标、告警中心与系统运维页。
14. 压测与真实上游功能验证。
15. 后台调度任务与独立后台 worker。
16. 数据库初始化、迁移补齐与部署脚本。
17. 前端主题、导航、页面交互与单文件静态控制器。
18. IP 管理、可信代理解析、来源 IP 规则与事件审计。
19. 回归测试脚本与质量防护。

## 3. 对外 OpenAI 兼容代理入口

### 功能是什么

项目提供标准 `/v1/*` 对外代理入口，用于让外部客户端以 OpenAI 兼容协议调用本系统，再由系统按配置转发到一个或多个提供商。已实现的入口包括：

- `/v1/chat/completions`
- `/v1/completions`
- `/v1/responses`
- `/v1/embeddings`
- `/v1/moderations`
- `/v1/files`
- `/v1/files/{file_id}` 及文件内容相关接口
- `/v1/images/generations`
- `/v1/images/edits`
- `/v1/images/variations`
- `/v1/responses/{response_id}` 相关管理接口
- `/v1/models` 与 `/v1/models/{model_id}`
- `/v1`、`/v1/{path:path}` 的 OPTIONS 和不支持端点兜底

### 怎么实现

- `app/routers/proxy.py` 定义所有 `/v1/*` 路由。
- `ApiKeyService.require_api_client_auth` 负责外部 Bearer API Key 鉴权。
- `_read_limited_v1_json_payload` 和 `_read_v1_multipart_payload` 在路由层读取请求体，并按系统设置执行请求体大小限制与结构摘要记录。
- `ProxyService.forward_json_request` 和 `ProxyService.forward_stream_request` 是核心转发入口。
- `ProxyService` 内部完成模型映射、能力识别、路由候选选择、Token 预检、内容防护、上游请求构造、非流式响应体上限、SSE 流式转发、错误分类、日志写入和后台 Token/计费任务入队。当前最新口径下，模型映射阶段只选择目标模型，端点协议、流式、视觉、工具调用、图片生成、容量、熔断、内容完整性和可信策略统一交给后续提供商候选选择阶段判断。
- 当前 `README.md` 已明确 Chat/Responses 自动端点互转 fallback 禁用；正式路由要求上游原生支持请求端点。若需要把 `/v1/responses` 单向接入 Chat-only 上游，必须显式启用 Responses→Chat 兼容适配，并使用共享会话存储保存 `previous_response_id` 状态。
- `/v1` OPTIONS 预检和不支持端点兜底会写入请求日志，但不再归类为 `api_client_auth` 鉴权日志；当前分别使用 `log_type="v1_preflight"` 和 `log_type="unsupported_endpoint"`，便于日志中心把 CORS 预检、不支持端点和真实鉴权失败区分开。
- 统一错误响应由 `OpenAIErrorService` 和 `ErrorCatalogService` 生成，外部返回 OpenAI 兼容的 `error` 对象。
- `app/main.py` 已接入 `GZipMiddleware(minimum_size=1024)`；全局 trace 中间件会优先复用 IP 管理中间件提前写入的 `request.state.trace_id`，并对 `/static/` 设置长期 immutable 缓存头、对 `/uploaded-assets/` 设置 1 小时缓存头。
- 代理侧新增多项安全护栏：上游错误体读取限制为 `UPSTREAM_ERROR_BODY_LIMIT_BYTES=65536`，远程图片 URL 自动转 data URL 时复用 `AssetService.MAX_IMAGE_BYTES` 和 `AssetService.IMAGE_CONTENT_TYPES`，采用流式分块读取并在超出大小或 MIME 不支持时返回结构化错误，避免一次性读取超大上游错误体或远程图片。

### 优点

- 协议覆盖面较广，支持 Chat、Responses、Embeddings、Moderations、Files、Images 等多类 OpenAI 兼容接口。
- 外部鉴权与后台 Session 登录分离，符合对外 API 与管理端隔离要求。
- 对请求体大小、Token 上限、长输出、上游响应体大小、流式超时做了防护。
- 对 SSE 异常有专门处理，尽量返回 `event: error` 和 `[DONE]`。
- 日志记录信息丰富，包含 trace、请求路径、API Key、模型、provider、费用、内容防护、错误分类等。
- 代理链路开始补充热路径资源护栏：`ProxyService.MODEL_CATALOG_LIMIT_LOCK_LIMIT=2048`，模型目录 limit 锁字典达到上限会清空，避免高基数 limit 参数长期堆积锁对象；`ProxyService.ROUTE_RETRY_TRACE_LIMIT=100`，候选耗尽和上游重试 trace 只保留最近 100 条，避免极端长等待或大量可恢复失败把请求上下文无限撑大。

### 缺点

- `app/routers/proxy.py` 超过 1800 行，`app/services/proxy_service.py` 超过 9300 行，入口读取、协议适配、路由、计费、日志、内容防护、错误处理大量聚集。
- Chat 与 Responses 非流式和流式路径有不少重复流程，容易出现修复一个路径但漏掉另一路径的问题。
- 图片接口、multipart、legacy image 转换、Responses 适配等逻辑混在代理主服务中，模块边界不清晰。
- 代理服务直接依赖 API Key、模型映射、路由、provider、日志、Token、内容防护、队列等多个服务，是最大耦合点。

### 改进建议

- 将代理主链路拆成独立步骤组件：请求解析、鉴权上下文、能力识别、模型映射、候选选择、上游适配、响应处理、日志事件、计费入队。
- 将 OpenAI 端点适配拆成 `chat_adapter`、`responses_adapter`、`images_adapter`、`management_adapter` 等端点级模块。
- 建立 `ProxyContext` 数据对象，避免在大量函数之间传递几十个参数。
- 为流式与非流式抽取共享的路由前置流程，并用端到端回归保证行为一致。

## 4. 多提供商管理

### 功能是什么

管理员可以维护多个 provider 或提供商，包括名称、Base URL、API Key、协议类型、提供商类型、分组、地区、优先级、超时、重试、容量限制、健康状态、熔断状态、信任等级、内容完整性状态、模型挂载等。当前规范已移除提供商和提供商模型挂载中的用户可见权重配置，避免继续沿用旧的权重分流口径；当前代码也已从 `Provider` ORM、Provider 创建逻辑和内容完整性自动隔离更新中移除 `low_trust_route_enabled`，低信任 provider 不再通过局部“允许低信任路由”字段放行，而应由全局可信策略、内容完整性硬过滤和路由诊断统一表达。

### 怎么实现

- 数据模型：`Provider` 和 `ProviderModel`。
- 管理接口：`app/routers/providers.py`、`app/routers/provider_models.py`。
- 核心服务：`ProviderService`。
- 页面：`app/templates/providers.html`。
- 前端交互：`initProviders()`、提供商测试结果弹窗、批量导入、模型发现、测试进度流等逻辑在 `app/static/js/app.js`。
- Provider 可批量导入，支持文本或 JSON 解析，支持凭据轮换、模型发现、连接测试、单提供商测试、批量测试、流式健康检查事件。
- 最新批量导入护栏：`ProviderService.MAX_BATCH_IMPORT_ITEMS=100`，单次最多导入 100 个提供商。批量导入创建 provider 时会暂缓模型目录同步和 API Key 自动绑定，收集本批创建的 provider id 后统一执行一次 `ModelCatalogService.sync_model_catalogs()` 和 `ApiKeyAdminService.attach_providers_to_auto_synced_keys()`，避免每创建一个 provider 就重复做全量同步。
- 最新熔断状态字段：`Provider` 新增 `circuit_opened_at`，与 `ProviderModel.circuit_opened_at` 一起记录熔断打开时间；健康恢复、内容完整性恢复或 provider 状态刷新时会清空该字段，内容高风险或 blocked 时会写入当前时间。路由恢复判断可以基于打开时间和恢复间隔，而不是只看 `circuit_state=open`。
- 最新提供商指标与列表护栏：`ProviderService.QUALITY_LOG_SAMPLE_LIMIT=10000`，质量指标只读取最近 10000 条正式路由日志样本；`AVAILABILITY_LOG_SAMPLE_LIMIT=10000`，可用性趋势只读取有限日志窗口后重新排序聚合；`RECENT_CONTENT_GUARD_EVENT_LIMIT=500`，provider 相关最近内容防护事件最多取 500 条；`PROVIDER_LIST_MODEL_CONFIG_LIMIT=500`，主列表每个 provider 最多返回 500 个模型配置，并通过 `model_config_count` 与 `model_configs_truncated` 告知前端是否截断，详情与编辑入口仍可读取完整配置。
- 最新轻量列表缓存：provider 选项、Playground provider 列表和 summary 使用 `provider-light-lists:*` 短缓存，TTL 为 15 秒，并在 provider 运行时缓存失效时同步清理。这降低管理端和测试页重复刷新成本，但仍需要目标 `ProviderLightListCachePolicy` 明确 key、TTL、写后失效和多 worker 一致性窗口。
- 最新轻量查询投影：`ProviderService.list_provider_option_dicts()` 与 `list_provider_summary_dicts()` 已改为复用 `_list_providers_for_model_name_lists()`，只读取 provider 摘要字段和 `ProviderModel.model_name`，不再为了下拉框或概览列表加载完整 provider 与完整模型挂载对象。`discover_models()` 对每个发现模型只执行一次 `_infer_model_capabilities()`，再复用能力结果生成 stream、vision、tools 等标记；`_build_recent_content_guard_events()` 也改为显式选择内容防护事件摘要和关联请求日志摘要字段。这说明 provider 查询正在继续从完整 ORM 对象树向 `ProviderOptionProjectionPolicy`、`ProviderSummaryProjectionPolicy`、`ProviderCapabilityInferencePolicy` 和 `ProviderContentGuardEventProjectionPolicy` 收敛。
- 最新 Playground 投影：`ProviderService.list_provider_playground_dicts()` 已改为复用 `_list_providers_for_playground_lists()`，只加载 Playground 需要的 provider 摘要、Base URL 和模型能力字段，不再复用完整 provider 列表。这说明 provider 轻量查询不只服务下拉和概览，也开始覆盖内部调试入口，目标应将其沉淀为 `ProviderPlaygroundProjectionPolicy`。
- 最新健康测试查询与流式稳定性优化：provider 状态汇总已改为 SQL 条件聚合；自动/批量连接检查通过 `_scheduled_enabled_providers(include_models=False)` 避免 L0 连通性测试预加载所有模型挂载；单 provider 模型健康测试直接按 `(provider_model_id, provider_id)` 查询 `ProviderModel`，不再为了测一个模型加载整个 provider 的所有挂载；指定 provider 连通性检查只查询选中的 ID 集合；`HealthService.check_all()` 在确实需要模型挂载时一次性预加载 provider models，避免全部健康检查阶段按 provider 懒加载产生 N+1；手动流式和非流式全部健康检查都受 `HealthService.MANUAL_PROVIDER_SCAN_LIMIT=200` 约束，避免一次性触发无限 provider 探测；流式测试进度队列使用 `HealthService.HEALTH_STREAM_PROGRESS_QUEUE_SIZE=200`，并通过非阻塞 `offer_event()` / `put_nowait()` 投递，队列满时丢弃最旧中间事件，不把慢客户端背压传给探测任务；`providers.py` 的流式生成器还会检测 `request.is_disconnected()`，客户端断开后取消后台健康任务并释放手动检查槽位。这些改动说明 provider/health 查询和 SSE 链路正在从“加载完整对象树 + 等客户端消费”转向“按场景投影 + 有界扫描 + 可取消流式任务”。

### 优点

- Provider 配置维度完整，支持容量、协议、健康、信任、内容防护等生产治理字段。
- Provider 与 ProviderModel 分离，允许同一 provider 下不同模型独立维护挂载启用、协议适配、渠道倍率、优先级、健康状态和可信状态；模型基础能力、基础价格和全局启停以模型目录为准。
- 批量导入和模型发现降低了提供商接入成本。
- 批量导入已从“循环内多次同步”向“批后统一同步”收敛，减少模型目录、API Key 自动绑定和 provider runtime cache 的重复失效。
- 熔断打开时间进入 provider/provider_model 状态后，后续恢复策略、页面展示和路由诊断可以解释“为什么仍处于熔断窗口内”。
- provider 质量、可用性和内容防护事件查询已有样本上限，列表也会截断超大模型配置，降低 provider 页面在大规模挂载模型或日志积累后加载变慢的风险。
- provider 轻量列表短缓存能服务多个下拉和测试入口，避免每个页面单独做相似查询。
- provider 选项、概览列表和近期内容防护事件都开始按页面所需字段投影，减少价格、健康、trace、payload 等无关字段进入高频列表响应。
- Playground provider 列表也开始独立投影，内部调试页刷新不再拖带完整 provider/model 配置对象。
- 模型发现能力推断只计算一次，降低批量发现模型时的重复字符串规则判断成本。
- 健康测试减少了 provider/model 关联对象的无意义加载，单模型测试、选中 provider 测试和自动 L0 扫描在大规模挂载场景下更稳定。
- 全部健康检查需要模型挂载时改为预加载，避免 provider 数量增长后出现 N+1 查询。
- 手动全部健康检查重新纳入 200 个 provider 扫描上限，避免管理员误触发大规模上游探测。
- 流式进度队列有明确上限，避免浏览器或网络慢消费时后台健康检查积压无限增长。
- 流式健康检查能感知客户端断开并取消后台任务，慢客户端也不会通过队列反压拖慢真实探测。
- 连接测试和模型测试接口丰富，便于后台验证。
- 低信任局部放行字段已退出当前模型和自动隔离更新路径，provider 风险治理更接近“状态硬过滤 + 统一策略”的目标方向。

### 缺点

- `ProviderService` 超过 1800 行，既处理 CRUD、序列化、批量导入、能力推断、价格同步、缓存失效，也反向依赖模型目录和 API Key 管理服务。
- `providers.py` 路由文件接近 600 行，包含流式事件、worker 并发测试、审计等较多业务细节。
- Provider 能力推断规则与模型目录同步规则散落在服务内部，未来增加新模型族或 provider 协议时风险较高。
- 批量导入上限和“批后统一同步”仍写在 `ProviderService` 里，目标架构应形成 `ProviderBatchImportPolicy` 与 `ProviderImportCoordinator`，把解析、校验、创建、批后同步、缓存失效、审计和部分失败报告分开。
- `circuit_opened_at` 已经被健康、内容防护、路由和 provider 状态刷新多处读写，目标架构应放入统一 `CircuitStatePolicy` 或 `ProviderStateTransition`，避免某个恢复路径只关 `circuit_state` 却忘记清空打开时间。
- `QUALITY_LOG_SAMPLE_LIMIT`、`AVAILABILITY_LOG_SAMPLE_LIMIT`、`RECENT_CONTENT_GUARD_EVENT_LIMIT`、`PROVIDER_LIST_MODEL_CONFIG_LIMIT` 和 `provider-light-lists:*` 仍直接散在 `ProviderService`，说明查询预算、列表投影和缓存策略还没有形成独立契约；后续重构若只拆文件不迁移这些策略，容易重新出现全量日志扫描或全量模型配置下发。
- `_list_providers_for_model_name_lists()`、`_build_recent_content_guard_events()` 和模型发现能力推断优化仍是 `ProviderService` 内部私有方法，目标架构尚未形成独立 query service 或 projection registry；后续新增下拉、概览、导出或事件摘要入口时，仍可能重新复用完整列表查询。
- `_list_providers_for_playground_lists()` 仍是 provider 服务私有查询，Playground 需要哪些字段、是否允许展示 Base URL、是否读取模型能力还没有成为独立 projection 契约。
- provider 健康测试的“是否加载模型”“是否只查选中 ID”“进度队列满了怎么处理”“客户端断开是否取消任务”“手动全部检查最多扫多少 provider”等策略仍散在 `HealthService` 与 `providers.py` 中，目标架构需要把查询投影、扫描预算、断开取消和进度流预算提升为明确策略，否则重构后容易重新回到 eager load 全对象图、无界手动扫描或无界 SSE 队列。

### 改进建议

- 将 `ProviderService` 拆为 `ProviderCrudService`、`ProviderImportService`、`ProviderModelMountService`、`ProviderCapabilityService`、`ProviderSerializationService`。
- 能力推断规则独立为可测试的规则表或策略类。
- Provider 写操作通过领域事件通知 API Key 授权、缓存和模型目录同步，避免服务互相直接调用。
- 建立 `ProviderBatchImportPolicy`：统一单次导入 100 个上限、dry_run、重复名称、部分失败、批后同步和错误摘要。
- 建立 `CircuitStatePolicy`：统一 provider/provider_model 的 `circuit_state`、`circuit_opened_at`、恢复间隔、人工恢复、健康恢复和内容完整性恢复。
- 建立 `ProviderMetricSamplePolicy`：统一质量日志样本 10000、可用性日志样本 10000、内容防护最近事件 500、统计窗口、正式路由日志过滤条件和截断提示。
- 建立 `ProviderListProjectionPolicy` 与 `ProviderLightListCachePolicy`：统一 provider 主列表模型配置 500 条截断、`model_config_count/model_configs_truncated` 字段、轻量列表缓存 key 前缀 `provider-light-lists:*`、TTL 15 秒和 provider 写操作后的失效。
- 建立 `ProviderOptionProjectionPolicy`、`ProviderSummaryProjectionPolicy`、`ProviderCapabilityInferencePolicy` 和 `ProviderContentGuardEventProjectionPolicy`：统一 provider 下拉/概览字段白名单、模型名列表加载方式、能力推断单次复用、近期内容防护事件摘要字段和关联日志轻量字段，避免查询端继续加载完整 ORM 对象。
- 建立 `ProviderPlaygroundProjectionPolicy`：统一 Playground provider 列表字段白名单、Base URL 展示、模型能力字段、缓存失效和权限边界，禁止内部调试入口复用完整 provider DTO。
- 建立 `ProviderHealthQueryProjection`、`ScheduledProviderLoadPolicy`、`HealthCheckModelPreloadPolicy`、`ProviderModelDirectTestPolicy`、`SelectedProviderConnectivityPolicy`、`ManualProviderScanLimitPolicy`、`HealthStreamDisconnectPolicy`、`HealthStreamNonBlockingQueuePolicy` 和 `HealthStreamProgressPolicy`：统一健康状态条件聚合、自动检查不预加载模型、全部检查需要模型时一次性预加载、单模型直查、选中 provider 精确查询、手动全部检查 200 个 provider 上限、客户端断开取消任务、非阻塞进度投递、流式进度队列 200 条上限与满队列丢弃中间进度的行为。

## 5. 模型目录与模型映射

### 功能是什么

系统维护统一模型目录，定义模型名称、显示名称、启停、流式、视觉、工具调用、Chat/Responses 协议支持、上下文窗口、最大输入输出、价格模式、价格 JSON、基础价格、速度标签等。模型映射功能允许把外部请求的源模型映射到一个或多个目标模型；当前最新实现中，映射阶段仅依据映射启停、目标模型存在性、目标模型全局启停、API Key 模型白名单、同会话近期成功目标和目标配置顺序选择目标模型，不再提前调用提供商候选路由做能力、容量、熔断或内容完整性筛选。

### 怎么实现

- 数据模型：`ModelCatalog`、`ModelMapping`。
- 路由：`app/routers/models.py`。
- 服务：`ModelCatalogService`、`ModelMappingService`、`ModelPricingService`。
- 页面：`models.html`。
- 最新资源护栏：`/api/models` 当前默认启用分页；若调用旧的非分页返回，也会最多返回 500 条，避免模型目录在管理端一次性全量下发。`ModelMappingService.list_mappings()` 新增 `LIST_LIMIT=500`，模型映射列表默认最多返回 500 条。`ModelCatalogService.test_all_models()` 批量健康测试最多取 50 个模型，并继续用 `MODEL_HEALTH_MAX_PARALLEL_MODELS=12` 控制模型级并发。模型列表缓存 TTL 继续读取系统设置，但 `model_list_cache_ttl_sec <= 0` 现在表示显式禁用缓存，正数最大 300 秒。
- 最新模型目录性能边界：`ModelCatalogService.MODEL_OPTIONS_LIMIT=500`，模型选项接口只加载最多 500 个目录；`MODEL_HEALTH_FILTER_SCAN_LIMIT=1000`，带健康状态筛选时只扫描有限候选窗口再做状态过滤；`model_summary()` 已使用 `model-catalog-summary:v2` 缓存，并在模型目录/运行时缓存失效时同步失效；`MODEL_MAPPING_NORMALIZE_BATCH_SIZE=500`，历史模型映射规范化按 ID 分批处理。这说明模型目录正在从“页面需要什么就完整序列化什么”转向“查询画像 + 缓存 + 分批维护”的结构，目标应把模型选项、健康筛选、摘要缓存和历史规范化分别纳入 `ModelCatalogOptionPolicy`、`ModelHealthFilterPolicy`、`ModelCatalogSummaryCachePolicy`、`ModelMappingMaintenancePolicy`。
- 最新模型映射维护边界：`ModelMappingService.NORMALIZE_MAX_BATCHES=100`，单次规范化最多执行 100 批，每批仍按 `MODEL_MAPPING_NORMALIZE_BATCH_SIZE=500` 处理。这能防止历史映射异常膨胀时一次维护任务长时间占用数据库。
- 最新授权范围轻量化：`ModelCatalogService._collect_user_route_scopes()` 已用 `load_only()` 限制 API Key 字段，并只加载绑定 provider id；`_remove_model_from_authorization_scopes()` 在删除或清理模型授权时，先用 `allowed_model_names_json.contains(model_name)` 过滤 API Key 和策略模板候选，再只加载需要改写 JSON 与失效缓存的字段。该改动说明模型目录不应直接遍历全量 API Key 或全量模板，而应通过 `ModelCatalogAuthorizationScopePolicy` 和 `ModelAuthorizationCleanupPolicy` 管理用户可用范围查询、授权 JSON 候选过滤和缓存失效。
- 回归覆盖：`stage22_model_family_compat_regression_check.py`、`stage23_provider_payload_adapter_regression_check.py`、`stage24_family_support_matrix_regression_check.py`、`stage28_routing_policy_regression_check.py`、`stage29_model_catalog_filter_regression_check.py`。

### 优点

- 模型目录与提供商挂载分层，能统一展示用户可用模型，也能表达各 provider 的实际能力差异。
- 支持健康优先路由和模型映射，降低客户端直接绑定单一上游模型的风险。
- 价格模型支持固定价格和更复杂的 pricing JSON，为计费扩展保留空间。
- 模型目录授权范围查询和模型删除后的授权清理已经减少全行读取、全表遍历和无谓 JSON 解析，大量 API Key 或模板场景下更稳。

### 缺点

- `ModelCatalogService` 与 `ProviderService`、`HealthService`、`ApiKeyAuthCache`、`SettingService` 直接互相影响，导致模型管理不是独立模块。
- 模型映射仍会读取 API Key 模型白名单和同会话近期成功目标，边界较旧实现清晰，但仍未完全领域纯化，后续应继续把权限快照和会话快照改为上层输入。
- 模型能力、provider 能力、健康探测能力三套概念存在重复判断，理解成本较高。
- 模型目录和模型映射已开始加列表/测试上限，但这些上限仍是服务内常量，不是统一的 `ModelCatalogQueryPolicy`、`ModelMappingQueryPolicy` 或 `ModelHealthBatchPolicy`，后续重构时需要防止被拆分时遗漏。
- 模型映射规范化已经有批大小和最大批次数两个边界，但维护任务摘要还不能稳定说明是否达到 100 批上限、剩余多少、下次如何继续。
- 模型目录对 API Key 和策略模板授权范围的读取仍在 `ModelCatalogService` 内直接处理，说明模型目录查询、授权策略、鉴权缓存失效之间的边界还没有完全拆开；目标架构需要避免模型目录 CRUD 继续直接理解 API Key JSON 结构。

### 改进建议

- 抽取统一 `Capability` 模型和 `CapabilityEvaluator`，让模型目录、provider 挂载、路由、健康检查共用能力定义。
- 模型映射应进一步收敛为纯领域决策：只返回目标模型选择结果和 trace，不直接依赖 API Key 服务或路由服务；API Key 白名单、同会话近期目标和排除列表由应用层作为快照传入。
- 将价格解析和展示口径继续保持独立，避免计费逻辑与目录 CRUD 混杂。
- 将分页默认值、非分页兼容上限、批量健康测试模型数、并发数和 TTL=0 禁用缓存语义抽成模型目录查询/批处理策略，写入单元测试，避免后续前端或脚本绕过分页重新拉全量。
- 将模型映射规范化 500 批大小和 100 最大批次数纳入 `ModelMappingMaintenancePolicy`，任务结果必须记录处理批次、处理条数、是否达到上限和剩余处理方式。
- 建立 `ModelCatalogAuthorizationScopePolicy` 与 `ModelAuthorizationCleanupPolicy`：用户可用模型范围查询只读取 Key 授权与绑定摘要；清理模型授权时必须先按 JSON contains 或等价索引筛选候选，再字段级加载、最小化改写并失效相关鉴权缓存。

## 6. API Key 管理、授权与限额

### 功能是什么

管理员可以创建、查询、导出、启停、删除、轮换、批量管理 API Key；可设置所有者、租户/项目/应用/环境、过期时间、QPS/RPM、授权 provider、允许模型、允许端点、来源 IP、偏好 provider、地域标签和自动同步 provider 绑定等。普通用户也可以在用户门户管理自己的 Key。当前最新实现中，API Key 不再作为独立余额、总 Token 限额、日请求限额、日费用限额、默认 provider、局部候选数、局部无限重试、局部路由权重或局部内容防护要求的配置主体；`migrations/2026-06-08_drop_api_key_legacy_route_quota_fields.sql` 已正式删除这些历史字段，余额事实来源收敛为归属用户共享账户。

### 怎么实现

- 数据模型：`ApiClientKey`、`ApiClientKeyProviderBinding`、`ApiKeyPolicyTemplate`。
- 管理接口：`app/routers/api_keys.py`、`app/routers/api_key_policy_templates.py`。
- 用户端接口和页面：`user_portal.py`、`user_api_keys.html`、`user_api_key_detail.html`。
- 服务：`ApiKeyAdminService`、`ApiKeyService`、`ApiKeyAuthCache`、`ApiKeyPolicyTemplateService`。
- 鉴权缓存使用 Bearer Key 的 SHA256 哈希，Redis 与本地 L1 缓存结合。
- 最新鉴权缓存运行时边界：`ApiKeyAuthCache` 的本地 L1 缓存会按 `api_key_auth_l1_cache_ttl_seconds` 过期，并通过 `api_key_auth_l1_max_entries` 控制最大条目数，当前配置默认 10000，`Settings.normalize_runtime_defaults()` 会将其钳制在 100 到 100000 之间；用户级缓存失效 `async_invalidate_user()` 通过 Redis set 扫描当前用户 API Key，并受 `api_key_auth_user_invalidate_scan_limit` 控制，默认 5000，同样被钳制在 100 到 100000。该实现降低热路径重复鉴权查询和用户变更后的批量失效成本，但目标架构需要把 L1 容量、过期、淘汰、用户 set 扫描上限和超限告警纳入 `AuthCacheRuntimePolicy`，并与脚本侧 `AuthCacheInvalidationPolicy` 区分：前者管运行时 L1/用户级失效，后者管维护脚本和批量 Redis key 清理。
- 限额检查结合 `RateLimitService`、`UserQuotaService`、`BillingService`、`ConcurrencyService`。
- `ApiClientKey`、`ApiKeyBase`、`ApiKeyUpdate` 和用户端表单已移除 `trusted_providers_only`、`allow_low_trust_providers`、`route_mode`、`default_provider_id`、`manual_allow_fallback`、`route_exhausted_retry_infinite_enabled`、`max_candidate_count`、`tpm_limit`、Key 自有 `balance_amount`、Key 自有 `total_recharge_amount` 等旧输入/存储字段；可信 provider、候选数、候选耗尽等待和无限重试等策略收敛到全局系统设置或路由领域。查询 DTO 仍会展示 `balance_amount`、`total_recharge_amount`，但语义是归属用户共享余额快照，不是 API Key 独立余额。
- `owner_user_id` 已成为 API Key 的必填归属字段；`ApiKeyAdminService.create_api_key` 未显式传入 owner 时使用当前管理员作为默认归属用户，`BillingService.create_api_key_balance_adjustment` 已改为报错提示需在用户账户余额中调账。
- API Key 局部内容防护策略已从当前 Schema、查询接口、鉴权缓存、路由上下文、用户门户、策略模板应用链路、ORM 模型、启动期兼容 DDL、治理迁移、后台模板和 `app.js` 中移除，当前代码层不再把 `content_guard_required` 作为 API Key 有效策略输入。
- 最新查询护栏：`GET /api/api-keys` 新增 `limit` 参数，默认和最大均为 500；`GET /api/api-keys/export` 新增 `limit` 参数，默认和最大均为 5000，并把导出上限写入管理员审计 `detail`。`ApiKeyAdminService.get_summary()` 新增 `CacheService` 10 秒短缓存 `api-key-admin-summary`，降低管理端重复刷新造成的统计查询压力。
- 最新导出与分析护栏：`ApiKeyAdminService.serialize_api_key()` 新增 `include_raw_api_key` 参数，`/api/api-keys/export` 传入 `False`，CSV 不再为了未导出的 `raw_api_key` 解密明文密钥；`get_analytics()` 的近期错误查询使用 `load_only()` 只加载卡片需要的日志字段；`API_KEY_ANALYTICS_MODEL_LIMIT=50`、`API_KEY_ANALYTICS_RECENT_ERROR_LIMIT=50`、`API_KEY_RECENT_USAGE_MAX_WINDOW_HOURS=720`、`API_KEY_LIST_MAX_LIMIT=5000` 为服务层内部调用提供硬上限，避免绕过路由参数时放大分组查询、近期错误 ORM 构造、近期用量扫描和全量列表加载。
- 最新授权维护边界：`ApiKeyAdminService.AUTO_PROVIDER_BINDING_BATCH_SIZE=200`，自动同步 provider 绑定、为新增 provider 自动绑定所有同步 Key、全量授权所有 Key 到所有 provider、历史回填所有 Key 到所有 provider 都改为按 API Key ID 分批读取、提交并失效鉴权缓存。这能降低长事务和 ORM 内存峰值，但也说明 API Key 管理模块需要独立 `ApiKeyProviderBindingBatchPolicy` 与 `ApiKeyAuthorizationMaintenanceService`，避免 provider 写操作、维护脚本和管理端批量操作各自实现一套批处理。
- 最新授权维护运行保护：`ApiKeyAdminService.AUTO_PROVIDER_BINDING_MAX_BATCHES=10000`，自动 provider 绑定最多连续处理 10000 批。常规规模不会触发该上限，但异常规模或错误循环时可以避免单次维护任务无限运行。
- 最新输入边界：`app/schemas/api_key.py` 为白名单/偏好类列表增加 `max_length`，`allowed_provider_ids`、`allowed_model_names`、`allowed_source_ips` 最多 500 项，`allowed_endpoint_paths`、`preferred_provider_ids`、`preferred_region_tags` 最多 100 项；批量更新 provider 白名单也有独立批量列表上限。`app/schemas/api_key_policy_template.py` 中 `MAX_TEMPLATE_ALLOWED_PROVIDER_IDS=500`、`MAX_TEMPLATE_ALLOWED_MODEL_NAMES=500`，策略模板不再允许提交无界 provider/model 列表。
- 最新自动同步校验优化：`ApiKeyAdminService` 在 `auto_sync_provider_bindings` 分支中复用刚查询到的全量 provider ID，不再把同一批 ID 再交给 `_validate_provider_ids()` 执行大 `IN` 查询；只有显式传入局部 provider 白名单时才执行存在性校验。

### 优点

- API Key 管理功能非常完整，既支持管理员批量治理，也支持用户自助管理。
- Key 明文可加密保存，缓存不保存原始明文 Key。
- 权限维度细，包括模型、端点、provider、来源 IP、QPS/RPM 和共享用户余额。
- 提供策略模板，能减少 provider、模型白名单、过期时间等重复配置。
- API Key CSV 导出跳过无用明文解密，减少批量导出时的 CPU 与加密服务开销，也降低明文 Key 在内存中短暂出现的机会。
- API Key 分析、近期错误和近期用量已经同时具备字段裁剪、limit 上限和窗口上限，内部调用绕过路由参数时也不会无限扩大查询。
- API Key 和策略模板列表字段已经有硬上限，异常请求无法通过超长数组放大 Pydantic 校验、数据库 `IN` 查询和 JSON 持久化成本。
- 自动同步 provider 绑定避免重复校验全量 provider ID，批量导入或自动授权场景少一次无意义大查询。
- 鉴权 L1 缓存有最大容量和过期淘汰，用户级失效也有扫描上限，避免大用户或异常 Redis set 导致一次变更扫穿缓存层。

### 缺点

- `ApiKeyAdminService` 超过 1100 行，包含查询、序列化、批量操作、计费摘要、绑定同步、校验等多类职责。
- `ApiKeyService` 同时负责密钥生成、加密、鉴权、限额、用量回写、缓存交互，职责偏大。
- API Key 服务、计费服务、用户额度服务、路由服务和缓存服务之间存在循环依赖。
- 共享余额已经改善“同一用户多个 Key 分散余额”的问题；API Key 局部内容防护开关已经从前后端有效契约中清理，后续重点是为可能已经执行过历史迁移的存量数据库补一条字段废弃或删除策略，避免旧库残留字段再次被误用。
- 来源 IP 白名单仍由 `ApiKeyService.extract_source_ip()` 读取请求来源后判断，但该方法优先使用 `X-Forwarded-For` 最左侧地址；在新增 IP 管理模块完全接管前，直连访问场景仍存在伪造转发头影响日志和白名单判断的风险。
- API Key summary 短缓存当前只在 `get_summary()` 内部设置，尚未形成统一失效策略；如果创建、更新、删除、批量启停、余额变更后未主动失效，10 秒内可能展示旧统计。当前可接受为短 TTL 缓存，但目标架构应由命令用例发布缓存失效事件。
- 自动 provider 授权维护已有批大小 200 和最大批次 10000，但仍在 `ApiKeyAdminService` 内部循环执行；目标应把“游标、批次、达到上限、失败重试、缓存失效”作为维护用例的输出，而不是只在日志里看到循环停止。
- API Key 导出、分析、近期用量和内部列表上限仍以 `ApiKeyAdminService` 常量表达，尚未进入独立查询策略；如果后续拆分查询服务时只迁移 API 路由参数，内部调用仍可能重新出现无上限导出、全窗口扫描或完整 RequestLog 加载。
- API Key 列表字段上限、策略模板字段上限和自动同步校验跳过目前仍位于 schema/service 具体实现中，目标应形成 `ApiKeyListFieldLimitPolicy`、`ApiKeyTemplateListFieldLimitPolicy` 和 `AutoProviderBindingValidationPolicy`，避免用户端、模板套用、批量授权和后台维护路径出现不同输入边界。
- 鉴权缓存运行时策略与维护脚本失效策略仍是两套实现：`ApiKeyAuthCache` 使用 L1 容量与用户 set 扫描上限，`apply_capacity_defaults.py` 使用 key 前缀扫描和批量删除；目标需要统一说明何时用用户 set 精确失效、何时用前缀扫描维护失效、达到上限后如何告警和继续处理。

### 改进建议

- 拆分为 `ApiKeyCredentialService`、`ApiKeyPolicyService`、`ApiKeyUsageService`、`ApiKeyAdminQueryService`。
- 将鉴权结果定义为只读 `AuthContext`，其构建过程依赖仓储和策略，不让其它服务反向调用 API Key 管理。
- 批量操作统一走命令对象和领域事件，缓存失效由事件消费者处理。
- 建立 `ApiKeyAdminQueryPolicy` 和 `ApiKeyAdminSummaryCachePolicy`，统一管理列表上限、导出上限、summary TTL、缓存 key、写操作失效和审计 detail，避免 API、服务和前端各自设定不同上限。
- 建立 `ApiKeyExportSerializationPolicy`、`ApiKeyAnalyticsQueryPolicy`、`ApiKeyRecentUsageWindowPolicy` 和 `ApiKeyServiceListLimitPolicy`：统一导出是否允许解密明文 Key、近期错误字段白名单、模型分布和错误列表最多 50、近期用量窗口 1-720 小时、内部列表最大 5000，并要求路由、服务、审计和测试共用同一策略。
- 建立 `ApiKeyAuthorizationMaintenanceService`：统一自动 provider 绑定批大小 200、最大 10000 批、游标推进、部分失败、鉴权缓存失效和后台任务摘要，provider 导入后只发布授权同步事件。
- 建立 `ApiKeyListFieldLimitPolicy`、`ApiKeyTemplateListFieldLimitPolicy` 与 `AutoProviderBindingValidationPolicy`：统一 provider/model/IP/endpoint/region 列表上限、模板套用边界、批量授权边界、显式局部白名单校验和自动同步全量 provider ID 复用规则。
- 建立 `AuthCacheRuntimePolicy`：统一 L1 TTL、L1 最大 10000 条默认容量、100-100000 钳制范围、本地过期清理、按 API Key ID 清理哈希映射、按用户失效最多扫描 5000 个 Key 的默认边界、超限后的告警摘要和后续补偿策略。

## 7. 用户账户与用户门户

### 功能是什么

系统支持管理员和普通用户两类角色。管理员可管理用户账号、角色、启停、密码、额度、余额、账单和用户详情；普通用户可登录用户门户，查看概览、管理自己的 API Key、查看可用模型、文档、日志、账单、会话、操作记录，并进行自助接口测试。

### 怎么实现

- 数据模型：`UserAccount`、`UserAccountBillingRecord`。
- 登录注册：`app/routers/auth.py`、`UserAuthService`。
- 管理端用户管理：`app/routers/user_accounts.py`、`users.html`、`user_detail.html`。
- 普通用户门户：`app/routers/user_portal.py`、`UserPortalService`、`user_*.html`。
- 页面访问控制使用 Session，前端 `app.js` 也有路由角色判断和 shell 导航。
- 用户门户已复用共享账户余额展示，`user_billing.html`、`user_api_keys.html`、`user_api_key_detail.html` 等页面通过 `display_money`、`display_tokens`、`display_price_per_1m` 过滤器统一展示美元、token 和每百万 token 单价。
- 最新管理端用户账户查询边界：`user_accounts.py` 已新增 `MAX_USER_QUOTA_BATCH_SIZE=200`，批量额度更新和额度预览都通过 `_parse_form_user_ids(..., max_count=200)` 限制单次用户数量；批量更新不再逐个 `db.get()`，而是一次 `select(UserAccount).where(UserAccount.id.in_(...))` 拉取目标用户。删除用户时管理员数量改为 `select(func.count())`，避免为了判断最后一个管理员而加载全量用户。
- 最新用户导出边界：`/users/export` 新增 `limit` 默认/最大 5000，并把实际 limit 写入管理员审计 detail；`/users/billing-export` 的 limit 上限收敛到 5000，且只为本次导出的账单记录中出现的 user_id 和 api_client_key_id 查询用户名与 Key 名称，不再预加载全部用户与全部 Key；`/api/users/options` 新增 `limit` 默认/最大 500，只返回启用用户并按 ID 倒序。这些变化说明管理端用户模块也开始从“全量列表供页面二次加工”转向“有界查询、按需投影、审计可追踪”。
- 最新用户门户查询边界：`UserPortalService.USER_CONVERSATION_COUNT_CACHE_TTL_SECONDS=30`，概览会话数使用 30 秒短缓存；`USER_SELF_TEST_MODEL_OPTION_LIMIT=500`，自检页面只为当前选中的 API Key 计算可用模型并最多返回 500 个模型。收益是普通用户刷新首页和自检页时不再重复做重型会话聚合和全量模型候选计算；风险是用户门户仍直接拼日志聚合、模型选项和自检 DTO，目标应拆出 `UserPortalQueryCachePolicy` 与 `UserSelfTestModelOptionPolicy`，并让用户门户只消费日志/模型/路由用例返回的受限投影。
- 用户端日志详情新增 `/api/user/logs/{log_id}/timeline`，通过 `UserPortalService.get_owned_request_log` 先确认日志归属，再复用管理端 `build_request_log_timeline_payload` 构建链路时间线。
- 会话回放新增资源边界：`ConversationService.REPLAY_LOG_LIMIT=200`，单次回放最多读取 200 条请求日志；单轮消息内容通过 `TURN_CONTENT_MAX_CHARS=4000` 截断，`ConversationReplay` 返回 `truncated` 与 `log_limit`，便于前端提示长会话只展示截断结果。
- 最新用户端列表投影：`/api/user/operations` 只选择操作记录列表需要的时间、动作、对象、结果、来源 IP 和摘要等字段，不再读取和返回 `detail_json` 大字段；用户详情页近期日志复用 `LogService._lightweight_log_load_options()` 并以 `include_payload_fields=False` 序列化摘要。
- 最新用户自检流式边界：用户接入自检的 SSE 本地消费新增 `SELF_TEST_STREAM_MAX_BYTES=1MB`、`SELF_TEST_STREAM_MAX_EVENTS=512`、`SELF_TEST_STREAM_OUTPUT_MAX_CHARS=4000`，异常上游或长输出不会无限占用内存，触达上限时会在预览中记录限制原因。
- 最新用户日志与指标优化：用户日志过滤选项只查询 `ApiClientKey.id/name/key_prefix`，不再加载 owner 与 provider bindings；`/api/user/metrics/summary` 与 `/api/user/metrics/timeseries` 只按 `user_account_id` 统计，不再重复查询全部 API Key ID 并构造大 `IN`；`/api/user/logs` 调用 `list_logs(include_api_key_options=False)` 时不再计算被丢弃的 API Key 选项；用户日志导出和过滤选项也只保留 `user_account_id` 范围过滤，避免已有用户范围下重复传入 key ID 列表。

### 优点

- 管理端和用户端边界较清晰，页面入口丰富。
- 用户端功能完整，不只是查看 Key，还包括日志、账单、会话、模型、自检和集成示例。
- 支持 `next` 跳转和角色默认首页，用户体验较完整。
- 用户端日志、操作记录、自检和指标接口开始采用轻量字段投影、流式消费上限和用户级作用域统计，普通用户 API Key 较多或日志 payload 较大时页面更稳。
- 管理端用户账户批量额度、用户导出、账单导出和用户选项接口已经补上 200/500/5000 等明确上限，并减少全量 ORM 加载，用户规模增长后更不容易因为一次页面操作拖慢数据库。

### 缺点

- `user_portal.py` 超过 1600 行，既处理页面渲染、表单、API、文件上传、自检请求、流式消费，也调用多个服务。
- `user_accounts.py` 约 750 行，HTML 表单处理和业务更新耦合较多。
- 普通用户门户与管理端部分查询逻辑重复，例如日志、账单、API Key 序列化。
- 会话回放已经有日志条数和单轮内容截断，但该策略仍写在 `ConversationService` 常量中，前端尚未看到统一的回放截断提示策略；后续应把它提升为 `ConversationReplayPolicy`，并区分“日志条数截断”和“单条内容截断”。
- 用户日志列表、导出、过滤选项、指标、操作记录和自检已经出现多种局部投影/边界常量，但仍分布在 `user_portal.py` 与 `UserPortalService` 中；目标应把它们合并为用户门户查询策略，而不是让每个接口各自决定是否带 API Key 选项、是否用 key ID 范围、是否加载 payload。
- 管理端用户账户的批量额度、CSV 导出、账单导出和用户选项虽然已有上限，但策略仍写在路由函数常量和 Query 参数中；目标需要把 `UserQuotaBatchPolicy`、`UserExportProjectionPolicy`、`UserBillingExportProjectionPolicy`、`UserOptionProjectionPolicy` 抽到用户账户应用层，避免后续页面或 API 绕过这些边界。

### 改进建议

- 将用户门户按页面拆路由，例如 profile、keys、logs、billing、conversations、self_test。
- 用户端查询统一使用 `UserPortalQueryService`，写操作使用 `UserPortalCommandService`。
- 用户自检功能单独拆成 `SelfTestService`，避免路由直接组装代理 payload 和消费流。
- 将会话列表、会话详情和会话回放抽成 `ConversationReplayService` 与 `ConversationReplayPolicy`：统一日志读取上限、内容截断长度、截断标记、前端提示和后续“查看更多历史”的分页扩展点。
- 建立 `UserOperationListProjectionPolicy`、`UserSelfTestStreamPolicy`、`UserLogFilterKeyOptionPolicy`、`UserMetricScopePolicy`、`UserLogApiOptionPolicy`、`UserLogExportScopePolicy` 和 `UserLogFilterScopePolicy`：统一操作记录列表字段、SSE 自检 1MB/512 事件/4000 字符上限、轻量 API Key 选项、用户指标只按 `user_account_id` 范围过滤、用户日志列表不计算被丢弃选项、导出和筛选不重复构造 key ID 大列表。
- 建立 `UserQuotaBatchPolicy`、`UserExportProjectionPolicy`、`UserBillingExportProjectionPolicy` 和 `UserOptionProjectionPolicy`：统一批量额度最多 200 人、用户 CSV 导出最多 5000、账单导出最多 5000 且只查询导出记录涉及的用户/Key、用户选项最多 500 且仅返回启用用户；路由、服务、审计和测试必须共用同一策略。

## 8. 日志、链路事件、审计与会话回放

### 功能是什么

系统记录对外请求日志、请求链路事件、异常事件、健康检查事件、计费事件、后台任务事件、用户操作事件、素材事件和管理员审计日志。日志页面支持筛选、导出、指标统计、详情查看和会话回放。当前工作区已进一步补充 usage 明细字段，包括 reasoning token、音频 token、prediction token、token 来源、上游 usage 缺失标记和原始 usage 明细 JSON，用于提高日志、计费和后续排障的一致性。

### 怎么实现

- 主日志表：`RequestLog`。
- 子事件表：`logging_events.py` 中的 `RequestAuthEvent`、`RequestValidationEvent`、`RequestRouteDecisionEvent`、`RequestProviderAttemptEvent`、`RequestUpstreamResponseEvent`、`RequestStreamEvent`、`RequestErrorResponseEvent`、`RequestContentGuardEvent`、`RequestBillingEvent` 等。
- 审计表：`AdminAuditLog`、`UserOperationAuditLog`。
- 服务：`LogService`、`AdminAuditService`、`ConversationService`。
- 统一日志系统：`app/logging/dispatcher.py`、`queue.py`、`sinks.py`、`registry.py`、`adapters/*`。
- API：`logs.py`、`logging_api.py`、`conversations.py`。
- 最新同步点：`RequestLog`、`LogService.create_log`、`LogService.extract_usage_payload`、`LogService.extract_usage_detail_tokens` 和 `migrations/2026-06-07_extend_request_log_usage_details.sql` 已覆盖 usage 明细字段；`LogService.is_model_list_request_path` 统一把 `/v1/models` 与 `/v1/models/{model_id}` 视为模型发现接口族，避免计费、补算和统计口径漂移。
- 最新请求日志内容防护证据字段：`RequestLog`、`RequestLogOut`、`LogService.create_log()` 和 `LogService.export_logs_csv()` 已新增 `content_guard_confidence` 与 `content_guard_score_delta`。`ProxyService` 在内容防护 summary 中把 `confidence`、`score_delta`、`final_strategy` 写入请求摘要，CSV 导出也会输出这两个字段。这说明请求日志已经从“只记录是否命中内容防护”升级为“保留可解释的内容防护置信度与分数变化证据”，但这些字段只能作为请求摘要证据，不能替代完整 typed event 证据链。
- 最新日志中心改动：`logging_api.py` 新增类型化日志导出 `/api/logging/export`，并为异常、健康检查、计费、后台任务、素材事件、内容防护事件等类型化日志补充时间范围、trace、请求日志 ID、锁状态、内容防护阶段和动作等筛选；`TYPED_LOG_TIME_FILTERS` 为不同类型指定时间字段和中文标签，`TYPED_LOG_FILTER_ALIASES` 支持“严重、成功、失败、跳过、运行、通过、复核、拦截”等中文关键词映射到底层枚举，类型化导出 `limit` 上限收敛为 5000 条，避免一次导出过重；`build_request_log_timeline_payload` 被管理端和用户端复用，用户端新增 `/api/user/logs/{log_id}/timeline` 查看自己请求的链路时间线。前端 `LOG_TYPE_LABELS` 已补充 `unsupported_endpoint` 和 `v1_preflight` 中文标签，`logs.html` 已增加“内容防护日志”和“调度任务日志”类型化 Tab，日志详情弹窗也强化了计费 token/价格分组、调度任务、素材事件、内容防护事件和原始 JSON 截断展示，避免超大日志直接撑爆弹窗。
- 最新类型化导出改动：`logging_api.py` 已新增 `TYPED_LOG_EXPORT_FIELDS`，为 exceptions、health-runs、billing-events、content-guard-events、background-jobs、asset-events 定义固定 CSV 字段顺序；`_items_to_csv` 已支持传入固定 fieldnames，空结果或稀疏字段也能输出稳定表头。计费事件列表从“分别查两类事件再内存合并切片”改为 SQL `union_all` 合并 token finalize 与 billing process，并按 `created_at/event_family/id` 排序分页。素材事件进一步通过 `migrations/2026-06-09_extend_typed_logging_details.sql` 增加 `asset_events.sha256_hex`，`AssetLogAdapter` 同时记录完整 SHA256 与 16 位前缀，typed 导出和前端详情可以展示完整哈希，摘要里的唯一哈希数优先按完整 SHA256 统计。
- 最新 typed logging 迁移状态：`migrations/2026-06-09_extend_typed_logging_details.sql` 已正式创建或补齐 `request_auth_events`、`request_validation_events`、`request_model_permission_events`、`request_route_decision_events`、`request_provider_attempt_events`、`request_upstream_response_events`、`request_stream_events`、`request_error_response_events`、`request_content_guard_events`、`request_billing_events`、`exception_events`、`health_check_runs`、`health_probe_events`、`token_finalize_events`、`billing_process_events`、`background_job_events`、`user_operation_audit_logs`、`asset_events` 以及对应索引。这说明 typed logging 已从“运行期模型和路由逻辑存在”进入“空库迁移必须可直接建表”的阶段，后续架构必须把表定义、ORM、adapter、projection、CSV schema、保留策略和 backfill 作为同一注册契约验收。
- 最新类型化查询改动：内容防护事件新增 `matched_rule` 查询条件，可同时搜索 `matched_rules_json`、`matched_categories_json`、reason 和 excerpt；调度任务日志支持在 keyword 中搜索 `result_summary_json`，并新增 `stale_running` 状态，超过 2 小时仍处于 running 的任务会被标记为运行超时并补充错误摘要。`_enrich_typed_log_response()` 还会为类型化日志返回 `time_filter`、`queue_status`、`retention` 和当前页 summary，前端 `typed-logs-summary-grid` 与 `typed-logs-meta-strip` 据此显示异常数、失败数、阻断数、素材字节数、唯一哈希数、统一日志队列 pending/processing 状态和当前类型日志保留天数。当前 `queue_status` 使用缓存 key `typed-logging:queue-status`，TTL 为 2 秒；`retention` 使用 `typed-logging:retention:{log_type}`，TTL 为 60 秒，并把 exceptions、health-runs、billing-events、content-guard-events、background-jobs、asset-events 分别映射到异常、健康、计费、请求子事件、后台任务和素材日志保留设置。
- 最新日志安全改动：`app/logging/sanitizers.py` 的 `sanitize_value` 和 `dumps_sanitized` 已支持 `max_list_items` 与 `max_bytes`，列表超限会追加 `_truncated_items` 摘要，序列化结果超字节会截断；`BackgroundJobLogRecorder` 将 `result_summary_json` 限制为 8192 字节、单字符串 500 字符和列表 50 项，降低后台任务结果把密钥、超大数组或长 payload 写入日志的风险。
- 最新队列可靠性改动：`LoggingQueue` 新增 `DEAD_LETTER_KEY=logging_events:dead_letter`、`FAILURE_COUNT_KEY=logging_events:failure_count`、`RECOVERY_BATCH_SIZE=500` 和 `MAX_BATCH_SIZE=1000`；worker 异常时会统计 processing 总量，并把前 `DEAD_LETTER_ITEM_LIMIT=100` 条样本封装进一个死信 envelope，死信队列保留最近 1000 个 envelope，并递增失败计数。`queue_lengths()` 现在返回 queued、processing、dead_letter 和 failure_count。`logging_event_queue_require_local_worker` 可要求本地 worker 存在时才入队，适配 Web/worker 分离部署；目标部署验收必须区分“Web 进程内 worker 强约束”和“独立 worker 消费 Redis 队列”两种形态，避免误开后导致 Web 进程拒绝入队。
- 最新队列恢复与死信样本边界：`LoggingQueue.RECOVERY_MAX_BATCHES=100`，启动恢复 processing 队列时最多处理 100 批；`RequestLogQueueService.RECOVERY_MAX_BATCHES=100`，请求日志队列恢复也最多处理 100 批；`LoggingQueue.DEAD_LETTER_ITEM_LIMIT=100`，死信迁移时只采样前 100 条 processing item 并记录总数、样本上限和截断标记。这些上限让“恢复失败队列”本身也有可控成本。
- 最新 typed sink 兜底：`DatabaseLogSink.write()` 遇到未注册 typed log event 不再静默丢弃，而是写入 `ExceptionEvent`，event_name 为 `typed_log_unregistered_event`，error_code 为 `typed_log_event_unregistered`，并记录 event_type、event_name 和 payload keys。这个兜底能暴露 registry 漏登记问题，但目标架构仍应让事件注册在测试阶段失败，而不是长期依赖运行时异常事件。
- 最新管理员审计查询护栏：`AdminAuditService.get_filter_options()` 支持 `limit`，默认 200、最大 500，并通过 `CacheService` 缓存 30 秒，缓存 key 形如 `admin-audit:filter-options:limit=200`，避免审计筛选项无限 distinct 扫描。
- 最新请求日志筛选项护栏：`GET /api/logs/filter-options` 和 `/api/user/logs/filter-options` 的 `limit` 默认 200、最大 500；`LogService.get_filter_options()` 会把 limit 规范到 1-500，缓存 key 前缀为 `logs:filter-options:`，并把 `exclude_health_checks`、用户作用域、API Key ID 作用域和规范化 limit 写入 key，TTL 为 10 秒。该接口返回 providers、model_names、requested_models、api_keys、users、tenants、projects、apps、environments 等 distinct 筛选项，并按上限截断，避免日志增长后筛选下拉每次刷新都做大范围 distinct 查询。
- 最新请求日志筛选项 key 收敛：用户作用域包含大量 API Key 时，`LogService.get_filter_options()` 不再把完整 API Key ID 列表拼进缓存 key，而是对排序后的 ID 列表计算 SHA256 并取 16 位摘要。这样能避免用户拥有大量 Key 时缓存 key 过长，但也意味着目标 `RequestLogFilterOptionsPolicy` 必须明确“作用域摘要如何生成、是否会碰撞、如何在调试日志中解释”和“写操作失效是否依赖摘要可逆性”。
- 最新指标查询改动：`LogService.api_client_metric_summary()` 与 `api_client_metric_timeseries()` 已接入 `CacheService` 5 秒短缓存，缓存 key 由指标名、窗口、桶大小、用户作用域和排序后的 API Key ID 列表组成，用来降低仪表盘短周期重复刷新对 `request_logs` 聚合查询的压力。
- 最新日志查询与导出边界：`LogService.METRIC_GROUP_LIMIT=500`，指标分组查询最多返回 500 个分组；`EXPORT_LIMIT=5000`，请求日志 CSV 导出最多 5000 条；`TOKEN_JOB_MAX_PAYLOAD_BYTES=65536`，Token/计费补全 job payload 超过 65536 字节时会跳过或降级摘要；`HEAVY_LOG_FIELD_NAMES` 已把 `request_body_json`、`response_body_json`、`response_text`、`api_client_policy_snapshot_json`、`trace_json`、`usage_details_json` 定义为重字段，轻量列表和时间线查询默认不加载这些字段。这说明日志模块正在形成 `LogMetricGroupPolicy`、`RequestLogExportPolicy`、`TokenFinalizePayloadPolicy` 和 `RequestLogHeavyFieldPolicy`。
- 最新日志/会话轻量投影：`logging_api._latest_background_job_statuses()` 只选择 `job_name`、`status`、`started_at` 并在内存中计算 `stale_running`，不再加载完整 `BackgroundJobEvent` 和大结果字段；`ConversationService.list_conversations()` 使用 SQL `func.substr(..., 1, 180)` 生成短预览；`ConversationService.get_replay()` 使用 `load_only()` 读取回放所需字段并继续保持最多 200 条日志；`logging_api.TYPED_LOG_FILTER_VALUE_LIMIT=50` 限制多值过滤项数量。
- 最新请求时间线轻量化：`build_request_log_timeline_payload()` 中的 `request_log` 改为 `LogService.serialize_log(..., include_payload_fields=False, derive_image_observability=False)`；管理端和用户端时间线路由也都使用 `LogService._lightweight_log_load_options()` 读取请求日志，避免时间线只展示事件摘要却先加载完整请求体、响应体、trace 和大文本。
- 当前最新缺口：内容防护 typed event 已从“只有模型和时间线”推进到“有 `/api/logging/content-guard-events` 列表、前端 Tab、`matched_rule` 筛选和固定表头导出”；请求摘要也已经记录 `content_guard_confidence` 与 `content_guard_score_delta`。但内容防护事件详情、请求日志摘要、内容防护页面最近事件和 CSV 字段仍没有统一 `ContentGuardEventProjection`，字段版本、证据字段解释、请求摘要与事件明细的边界、前端展示策略还需要继续从 `app.js` 和 `logging_api.py` 硬编码中抽离。

### 优点

- 日志维度非常丰富，可用于排障、计费、路由诊断、内容防护追溯和用户自助查看。
- 新增了统一事件 envelope、dispatcher、sink 和 adapter，比只写 request_logs 更可扩展。
- 请求体日志有结构摘要和敏感字段控制，避免默认保存完整大 payload。
- usage 明细从上游官方 `usage` 字段提取并落库，避免从摘要文本或总 token 反推缓存、推理、音频等细分字段。
- 类型化日志查询和导出能力更完整，管理员可以按异常、健康、计费、后台任务、素材、内容防护等维度分别排查；用户端也能在权限范围内查看自己的请求时间线；素材事件也能保留完整 SHA256，方便后续做去重、审计和文件完整性核查。
- typed CSV 已开始采用固定字段注册表，计费事件分页也改为数据库 union 分页，日志中心的长期审计和大数据量分页稳定性比上一版更好。
- 日志脱敏与摘要截断开始集中到 `app/logging/sanitizers.py`，后台任务摘要不再直接保存完整结果对象，减少长期运维日志中的敏感信息和体积失控。
- 统一日志事件队列开始具备死信和失败计数，队列观测不再只有 pending/processing，后续能定位“事件已经入队但无法落库”的问题。
- 队列恢复已经从“按批恢复”进一步加上最大恢复批次数，避免应用启动时被历史 processing 积压拖住；死信采样限制也让故障摘要更可控。
- 未注册 typed event 会落成异常事件，能防止新增事件忘记 registry 时被静默吞掉。
- 管理员审计筛选项开始有查询上限和短缓存，避免审计日志增长后筛选下拉成为热查询。
- 请求日志筛选项开始按用户/API Key 作用域、健康检查排除开关和 limit 组成缓存 key，管理员端和用户端都能复用同一服务层筛选项查询口径。
- typed log 响应已经能返回队列状态和当前类型日志保留策略，管理员在日志页可以同时看到“当前数据怎么筛选”和“这些日志会保留多久、队列是否积压”。
- 内容防护请求摘要新增置信度和分数变化字段，能帮助管理员从请求日志快速判断一次内容防护命中的强弱，而不必每次都展开完整事件。
- API Key 指标汇总和时间序列已有短 TTL 缓存，能缓解管理端或用户端反复刷新同一窗口指标时的数据库聚合压力。
- 指标分组、请求日志导出、Token job payload 和日志重字段已经有统一上限或白名单，列表、时间线和导出更不容易因为大 payload 或高基数字段拖慢数据库。
- 后台任务状态、会话列表预览、会话回放和请求时间线开始使用字段定向加载、SQL 侧截断和轻量序列化，大 payload 日志不会因为列表或时间线刷新被反复读出。
- typed log 多值过滤有 50 项上限，异常查询不会生成过长 `IN (...)` 条件。

### 缺点

- 当前存在两套日志路径：旧的 `LogService.create_log/request_logs` 与新的 `app/logging/*` 子事件系统并存。
- `LogService` 超过 2000 行，包含创建、序列化、筛选、派生字段、指标、CSV、会话、计费展示等大量职责。
- `request_adapter` 又反向依赖 `LogService`，形成日志系统内部循环。
- usage 明细提取已集中到 `LogService`，但它仍与代理、Token 补全、计费、CSV 导出和前端展示强耦合，后续应继续拆为独立 usage 提取规则和日志写入用例。
- `logging_api.py` 开始承担通用查询、时间线构建和 CSV 导出，后续如果继续扩展，容易成为新的日志查询控制器巨石。
- 类型化日志导出已有固定字段注册表，但字段版本、字段说明、兼容追加规则仍未形成正式 `TypedLogCsvSchemaRegistry`；当前注册表、time filter 元数据、中文筛选别名、summary 计算、统一日志队列状态、导出上限和素材 SHA256 展示仍位于路由文件 `logging_api.py`，还不是独立导出/投影用例。
- typed log 的 `queue_status` 与 `retention` 元数据也已经在 `logging_api.py` 中计算并缓存，短期提升页面可用性，长期会让路由层继续承担队列观测、数据保留策略和展示投影三类职责。
- `RequestLog` 新增内容防护置信度和分数变化后，请求摘要表继续变宽；如果后续把每个内容防护证据字段都塞进 `request_logs`，它会逐步变成混合事件表，削弱 summary/event 分层。
- 请求日志筛选项缓存当前在 `LogService.get_filter_options()` 内部实现，key、TTL、作用域和写后失效还没有形成 `RequestLogFilterOptionsPolicy`，未来管理端、用户端或导出页新增筛选项时容易各自复制 distinct 查询。
- 指标短缓存当前仍直接写在 `LogService` 中，TTL、缓存 key 生成、用户/API Key 作用域和写入失效策略尚未抽成统一 `MetricQueryCachePolicy`，后续指标查询继续增加时容易散落多套 key 规则。
- `METRIC_GROUP_LIMIT`、`EXPORT_LIMIT`、`TOKEN_JOB_MAX_PAYLOAD_BYTES` 和 `HEAVY_LOG_FIELD_NAMES` 仍是 `LogService` 内部常量，目标应抽成查询/导出/payload 策略；否则后续日志查询拆分时容易漏掉大字段排除、导出上限或 Token job payload 上限。
- `LoggingQueue` 已有死信和 failure_count，但仍是 typed logging 自己维护 Redis key；request log queue、token finalize queue 和未来 billing queue 还没有统一 `QueueFailurePolicy`、死信查看/重放/丢弃入口和跨队列观测 DTO。
- 队列恢复批次数和死信样本数已经成为生产边界，但目前分散在 `LoggingQueue` 与 `RequestLogQueueService`，日志页和监控页还不能统一说明“本轮恢复是否达到 100 批上限、剩余多少 processing 未恢复”。
- 未注册 typed event 的运行时兜底虽然可观测，但也说明 `TypedLogRegistryContractTest` 仍缺失：新增 adapter/event/model 时应该在测试期发现未注册，而不是到生产后写异常事件。
- 审计筛选项缓存目前只在 `AdminAuditService` 内部实现，目标应抽成 `AdminAuditQueryPolicy`，统一筛选项上限、TTL、权限作用域和写入审计日志后的失效策略。
- 计费日志已用 SQL union 合并两类事件并区分 `event_family`，但两张表字段结构仍不同，共用筛选项和列展示时仍容易出现某些状态对另一类事件恒为空；目标上仍应由事件族 projection 明确字段语义。
- 后台任务日志主要覆盖 `distributed_job_lock` 装饰器链路，不等于完整后台队列观测；独立 worker、请求日志队列、统一日志队列、Token finalize 队列的消费深度、重试和死信并没有全部进入同一个任务事件模型。
- 后台任务状态投影、会话预览 SQL 截断、回放 `load_only()`、typed filter 上限和时间线轻量序列化仍散落在 `logging_api.py`、`ConversationService`、`LogService` 和用户端路由中；这些属于查询策略，不应长期依附具体路由函数。

### 改进建议

- 明确 `request_logs` 作为请求摘要表，`logging_events` 作为事件明细表，由 `LoggingDispatcher` 统一写入。
- 将 `LogService` 拆为 `RequestLogWriter`、`RequestLogQueryService`、`MetricQueryService`、`ConversationReplayService`、`LogExportService`。
- 消除 `logging.adapters.request_adapter -> LogService -> request_adapter` 循环。
- 将 usage 解析、日志字段回填、模型发现接口族判断抽成共享领域规则，供日志、计费、Token 补全、统计和监控积压共同调用。
- 将类型化日志分页、筛选、导出、时间线构建拆成查询用例和导出用例，避免 `logging_api.py` 继续堆积 SQL 过滤和 CSV 细节。
- 将 `api_client_metric_summary/timeseries` 的 5 秒短缓存抽为 `MetricQueryCachePolicy`：统一 key 组成、TTL、用户/API Key 作用域、筛选变更后的失效策略和测试夹具，避免指标口径或缓存污染。
- 将现有 `RequestContentGuardEvent` 独立列表、筛选、导出和前端 Tab 继续收敛为正式查询用例，并让请求详情、内容防护页面最近事件、日志中心类型化 Tab 复用同一 DTO 与字段投影。
- 建立 `ContentGuardEvidenceProjection` 与 `RequestLogSummaryPolicy`：`request_logs` 只保留稳定摘要字段，例如 `content_guard_confidence`、`content_guard_score_delta`、最终策略和摘要结果；命中规则、片段、候选切换、缓冲等待、重试 provider 数等完整证据进入 typed event projection，避免摘要表无限扩字段。
- 将当前 `TYPED_LOG_EXPORT_FIELDS` 从路由文件迁入 `TypedLogCsvSchemaRegistry`，为每一种 typed log 定义稳定导出 schema、表头版本、字段说明、空结果导出规则和兼容追加策略；同时把类型化日志摘要、time filter 元数据、queue status、素材 `sha256_hex` 字段解释迁入 `TypedLogProjectionService`，禁止新增类型时重新退回动态推导字段或在路由层堆展示逻辑。
- 建立 `TypedLogRetentionPolicy`：把 exceptions、health-runs、billing-events、content-guard-events、background-jobs、asset-events 到系统保留天数字段的映射从路由迁出，并定义 `typed-logging:retention:{log_type}` 的 60 秒缓存、写设置后的失效和前端展示文案。
- 建立 `RequestLogFilterOptionsPolicy`：统一日志筛选项默认 200、最大 500、缓存 key `logs:filter-options:*`、TTL 10 秒、健康检查排除、用户/API Key 作用域、筛选项字段集合和写入请求日志后的可接受收敛窗口。
- 建立 `LogMetricGroupPolicy`、`RequestLogExportPolicy`、`TokenFinalizePayloadPolicy` 和 `RequestLogHeavyFieldPolicy`：统一指标分组最多 500、请求日志导出最多 5000、Token job payload 最大 65536 字节，以及轻量查询默认排除 `request_body_json/response_body_json/response_text/api_client_policy_snapshot_json/trace_json/usage_details_json`。
- 将后台任务日志、后台队列指标和 worker 消费状态分开建模：任务锁事件记录调度任务，队列观测记录 backlog、重试、死信、消费延迟和活跃 worker。
- 建立 `TypedLoggingQueuePolicy` 与 `QueueFailurePolicy`：统一 typed logging 的 batch 上限 1000、processing 恢复批量 500、死信保留 1000、failure_count、require_local_worker 和后续重放入口，并逐步推广到 request log 与 token finalize 队列。
- 将 `RECOVERY_MAX_BATCHES=100`、`DEAD_LETTER_ITEM_LIMIT=100` 纳入 `QueueRecoveryLimitPolicy` 与 `DeadLetterSamplePolicy`：启动恢复达到上限时必须写告警摘要，死信迁移必须同时记录 processing 总数、样本数和截断标记。
- 建立 `AdminAuditQueryPolicy`：统一审计列表、筛选项 distinct 上限、筛选项短缓存、写操作失效和导出边界。
- 建立 `TypedLogRegistryContractTest`：所有可发出的 typed event 都必须在 registry、模型、CSV schema 和 projection 中登记，禁止依赖运行时 `typed_log_unregistered_event` 兜底作为常态。
- 建立 `BackgroundJobStatusProjectionPolicy`、`ConversationPreviewProjectionPolicy`、`ConversationReplayLoadPolicy`、`TypedLogFilterValuePolicy`、`RequestLogTimelineProjectionPolicy` 和 `RequestLogTimelineLoadPolicy`：统一后台任务状态字段、会话预览 180 字符 SQL 截断、回放字段加载、typed filter 50 项上限、时间线轻量序列化和路由读取轻量字段的验收。

## 9. Token 统计、费用计算与账单

### 功能是什么

系统根据上游 usage、请求/响应 payload 和模型价格计算 prompt/completion/cache/reasoning/audio/prediction token、费用和用户账户余额变动，并写入 API Key 成本累计与用户账单。支持后台补全、失败重试、用户余额调整、账单导出和用量趋势。

### 怎么实现

- 服务：`TokenUsageService`、`BillingService`。
- 账单模型：`ApiClientBillingRecord`、`UserAccountBillingRecord`。
- 日志字段：`RequestLog` 中记录 token、价格、费用、计费状态、billing_finalized_at 等。
- 后台任务：`TokenUsageService.start_background_workers()`、`scheduled_token_usage_backfill()`。
- Token 估算使用 `tiktoken`，同时提供快速估算与精确统计。
- 缓存读写 token 只从上游 usage 官方语义字段提取。
- `TokenUsageService._extract_usage_from_response` 与 `ProxyService._extract_usage_info` 已按 Chat/Responses usage 结构提取缓存、推理、音频和 prediction 明细；`BillingService.compute_log_cost` 通过 `LogService.is_model_list_request_path` 排除模型发现接口族。
- 最新账本同步：`ProviderModel` 新增 `cache_write_price_per_1k`；`ApiClientBillingRecord` 和 `UserAccountBillingRecord` 新增 cache read/write token 及对应读写单价字段；`migrations/2026-06-08_fix_billing_owner_and_cache_write.sql` 回填历史账单缓存明细，并为缺少归属用户的 API Key 选择默认启用用户做 owner 回填。
- `BillingService.compute_log_cost` 已把 cache write token 按独立 `cache_write_price_per_1k` 计费，未设置时回退 input price；`price_unresolved`、`price_unset` 不再伪装为 0 费用，而是保持待解决状态。
- `TokenUsageService._update_quota_cache` 新增 `request_delta`，在 usage finalize 时同步 Redis 中 API Key 和账户维度的请求次数、token 和费用计数，避免请求次数只存在数据库日志里。
- 最新 Token finalize 队列边界：`TokenUsageService` 使用 `token_finalize_worker_count` 启动后台 worker，内存队列大小来自 `token_finalize_queue_size`；worker 单次从队列聚合批处理，配置 `token_finalize_batch_size` 默认 50，并受 `MAX_FINALIZE_BATCH_SIZE=500` 硬上限保护；`token_finalize_immediate_delay_ms` 用于延迟立即补算入队，运行时钳制在 0 到 5000 ms；`token_usage_backfill_interval_seconds` 控制定时补算任务频率，调度时按至少 15 秒执行。这说明计费补算已经具备“实时队列 + 后台兜底 backfill + 批处理硬上限”的三层结构，目标应形成 `TokenFinalizeQueuePolicy`、`TokenFinalizeBatchPolicy` 和 `TokenUsageBackfillSchedulePolicy`。

### 优点

- 计费链路较完整，支持 API Key 归属用户共享余额、API Key 成本累计和用户账户账单流水。
- 主请求链路可把 Token 和计费后置到后台，降低请求延迟。
- 对图片生成、缓存 token、不同价格层有扩展处理。
- usage 明细字段可直接支撑后续推理 token 成本、音频 token 成本、prediction token 成本或更细粒度运营报表扩展。
- cache read 与 cache write 的 token、单价和账单流水都已可追溯，后续排查 prompt cache 成本更直接。
- Token finalize worker 支持按批处理，默认 50、最大 500，能降低逐条开线程/开事务成本；延迟入队与 backfill 周期也可配置，便于在低配部署和高并发部署之间调整补算压力。

### 缺点

- `TokenUsageService` 接近 1400 行，既处理队列、估算、usage 提取、回写、告警、Redis 计数、账单触发。
- `BillingService` 与 API Key 缓存、模型价格、日志字段强耦合。
- 计费最终一致性的边界需要更清晰的状态机，当前靠多个字段组合表达。
- 当前细分 token 已落到日志，但费用计算仍主要围绕 prompt/completion/cache 价格口径；后续若要对 reasoning/audio/prediction 单独定价，需要先建立价格策略扩展点。
- 账单逻辑仍同时写 `request_logs`、API Key 成本、用户余额和两类账单记录，幂等状态机还不够显式。
- Token finalize 队列的批大小、最大批、延迟入队、backfill 周期仍由 `TokenUsageService` 和 `tasks.py` 直接读取配置；目标策略未形成前，新增独立 worker、压测 profile 或部署脚本可能设置出互相不匹配的补算吞吐。

### 改进建议

- 将 Token 估算、Usage 提取、Finalize Job、Billing Command 分开。
- 建立明确计费状态机：`pending_usage`、`usage_finalized`、`billing_pending`、`billing_done`、`billing_failed_retryable`、`billing_failed_final`。
- 对费用计算引入纯函数单元测试，降低价格策略变更风险。

## 10. 健康检查、能力探测与熔断

### 功能是什么

系统能对提供商、模型和能力进行健康检查，包括连通性、文本流式、工具调用、图像理解、图片生成、内容完整性探针等；结果用于页面展示、路由过滤、健康状态更新、熔断和恢复。

### 怎么实现

- 路由：`providers.py`、`provider_models.py`。
- 服务：`HealthService`、`ProviderHealthStateService`。
- 调度：`scheduled_provider_l0_health_check`、`scheduled_model_l1_text_health_check`、`scheduled_model_l2_capability_health_check`、`scheduled_model_l3_content_integrity_health_check`。
- 事件记录：`HealthLogRecorder`、`HealthCheckRun`、`HealthProbeEvent`。
- 回归脚本：`stage14`、`stage27_provider_partial_health`、`stage33_content_guard`。
- 最新口径：Chat Completions / Responses 端点协议支持的权威来源是管理员在提供商模型挂载矩阵中的挂载级协议配置；健康检查、端点测试和探针结果只记录可用性或能力结果，禁止自动反推、改写或收紧协议支持。
- 单模型即时测试开始复用 `app/utils/test_features.py` 的 `normalize_test_features` 和 `phase_keys_from_test_features`，并使用交互式短预算、并行阶段、单端点策略执行。
- 最新调度资源边界：`HealthService.SCHEDULED_PROVIDER_SCAN_LIMIT=200`，自动调度的 provider L0、模型 L1 文本、L2 能力和 L3 内容完整性检查每轮最多扫描 200 个 provider；当前手动流式和非流式全部检查也通过 `MANUAL_PROVIDER_SCAN_LIMIT=200` 保留单次上限。这说明健康检查已经从“自动有限、手动无界”进一步收敛为“单次任务都有预算，真正全量用多批完成”，目标架构应沉淀为 `HealthScanBudgetPolicy`，避免后续新增探针时把任一入口重新改成无上限全表扫描。
- 最新手动健康检查边界已经收紧：`HealthService.MANUAL_PROVIDER_SCAN_LIMIT=200`，手动流式和非流式全部健康检查都按 200 个 provider 裁剪；`check_all()` 对需要模型挂载的全部检查改为一次性预加载 provider models，避免 N+1；`providers.py` 的流式检查生成器会检测客户端断开并取消后台任务，进度事件通过非阻塞投递避免慢客户端反压探测任务。

### 优点

- 健康检查分层，支持 L0 provider 连通、L1 文本、L2 能力、L3 内容完整性。
- 探测结果可落库并进入路由决策。
- 手动测试和批量测试提供进度反馈。
- 端点协议配置与健康探针解耦后，路由行为更可控，避免因为一次探针失败就自动收紧管理员配置的协议能力。
- 定时扫描上限能保护低配部署，避免健康巡检与正式代理请求争抢数据库连接、上游连接和 Web worker。
- 手动全部健康检查也有 provider 扫描上限，管理员误触发时不会无限扩大上游连接和数据库会话占用。
- 健康检查流式响应支持客户端断开取消和非阻塞进度投递，后台探测任务不会因为浏览器关闭或网络慢消费继续长期占用槽位。

### 缺点

- `HealthService` 超过 3600 行，是第二大复杂点，包含探针构造、并发控制、落库、状态更新、内容防护、日志记录、调度检查等。
- 健康服务依赖 `ProxyService`，而 `ProxyService` 又依赖 provider/route/health 状态，形成核心循环。
- 探针阶段和能力映射规则较多，新增能力时需要同时改多处。
- 内容完整性探针阶段已抽到 `ContentGuardProbeService.build_health_phase_specs`，但健康服务仍负责组合大量阶段，后续仍需要进一步用 `HealthProbePlan` 收敛。
- `SCHEDULED_PROVIDER_SCAN_LIMIT` 与 `MANUAL_PROVIDER_SCAN_LIMIT` 仍是健康服务内部常量，路由层、后台任务日志和页面说明尚未通过同一策略对象解释“为什么单次扫描最多 200、剩余 provider 如何继续检查”。
- `MANUAL_PROVIDER_SCAN_LIMIT`、客户端断开取消和非阻塞队列投递目前仍分散在 `HealthService` 与 `providers.py`，还没有被健康检查应用用例统一解释；后续若增加新的流式健康入口，容易漏掉取消和非阻塞投递。

### 改进建议

- 拆成 `HealthProbeRunner`、`HealthResultWriter`、`CapabilityProbeService`、`ProviderCircuitService`、`HealthSchedulerFacade`。
- 探针只依赖上游客户端和 provider 仓储，不依赖完整代理主链路。
- 能力探针定义数据化，按 capability registry 执行。
- 明确健康检查只能产生可用性或能力观测，不能写回端点协议支持；端点协议变更只能来自管理员挂载级配置。
- 建立 `ScheduledHealthScanPolicy`：统一自动任务 provider 扫描上限 200、分页游标、跳过原因、后台任务 processed/success/failed 计数和验收测试。
- 将当前口径修订为 `HealthScanBudgetPolicy`：同时覆盖自动扫描上限 200 和手动全部检查上限 200，若后续确实需要真正全量手动检查，必须改成分页/游标式多批执行，而不是单次无上限扫描。
- 建立 `HealthCheckModelPreloadPolicy`：声明全部健康检查何时必须预加载 provider_models、何时禁止加载模型挂载，避免 N+1 查询和过度 eager load 在不同阶段之间来回摇摆。
- 建立 `HealthStreamDisconnectPolicy` 与 `HealthStreamNonBlockingQueuePolicy`：统一客户端断开检测、后台任务取消、手动检查槽位释放、`put_nowait()` 非阻塞投递和 completed/error/结束哨兵保留规则。

## 11. 内容完整性防护

### 功能是什么

系统对 provider 返回内容进行风险检测，识别广告、短链、结构异常、工具调用污染、JSON 模式异常、文件引用风险等，并可对低信任 provider 使用流式预缓冲检测。高风险时可阻断、切换 provider、记录违规、降低内容完整性评分并触发告警。当前还新增了面向 provider_model 的可信检测能力，可信基线由固定答案完整性、外链广告识别、流式污染检测三类探针组成。

### 怎么实现

- 服务：`ContentGuardService`、`ContentGuardModuleService`、`ContentGuardRuleService`、`ContentRuntimeGuardService`、`ContentTrustProbeService`、`ContentGuardProbeService`。
- 页面与接口：`content_guard.py`、`content_guard.html`。
- 数据字段：`Provider`、`ProviderModel`、`RequestLog`、`AppSetting` 中的 content_guard 与 content_integrity 字段。
- 路由过滤：`RouterService` 会排除内容完整性低分或 blocked provider。
- 监控动作：`SystemMetricsService` 可自动隔离高风险 provider。
- 回归：`stage33_content_guard_regression_check.py`。
- 新增审查依据：根目录 `内容防护模块问题全审查.md` 已把内容防护模块问题归档到 700 条，覆盖配置、规则引擎、运行时代理、可信探针、路由联动、迁移、前端页面、日志中心和测试覆盖。
- `ContentGuardRuleService` 是新拆出的规则与算法入口，已经从继承原 `ContentGuardService` 改为组合式静态门面，统一转发默认规则、规则 JSON 解析、文本/JSON/SSE 检测、URL 检测、风险评分和阻断判断等能力，减少外部模块直接依赖原巨型服务。
- `ContentRuntimeGuardService` 是新拆出的请求过程中防护服务，负责正式代理响应的非流式检测、流式首段预缓冲检测、后续 chunk 滑动检测、运行时动作决策、违规记录、高风险策略解析、SSE data payload 消费、有限字节缓冲和内容防护错误构造。
- `ContentTrustProbeService` 是新拆出的预先防护服务，负责可信探针编排、内部/外部检测目标解析、端点解析、单探针执行、跳过/未知探针结果、探针结果聚合、provider_model 可信状态更新以及 `RouterService` 请求前可信路由判断；`ContentGuardModuleService` 已把原本内置的探针目标解析和汇总逻辑下沉到该服务。
- 最新新增：`/api/content-guard/trust-probe` 固定执行可信检测必需探针，探针组合为固定答案、外链广告识别、流式污染检测；`pollution_rules` 会验证短链、外链、广告意图是否被规则识别。提供商列表、挂载矩阵和模型绑定预览均增加“可信检测”入口；内部目标只有在本次选择的 `probe_keys` 覆盖完整必需探针时，才允许持久化 provider_model 可信状态，避免半套探针误写可信状态。
- 最新探针预算护栏：`ContentGuardRunRequest.probe_keys` 最多 5 个；`ContentGuardProbeService` 为 SSE 污染探针增加 `SSE_PROBE_IDLE_TIMEOUT_SECONDS=4`，保留 `SSE_PROBE_MAX_DURATION_SECONDS=12` 与最大读取字节预算，并从内容防护流式缓冲设置读取最大读取字节但钳制到 65536；污染规则探针最多执行 `POLLUTION_PROBE_MAX_SCENARIOS=3` 个场景，总超时 24 秒、单场景超时 8 秒，避免一次可信检测拖垮后台请求。
- 最新可信状态写入语义：探针结果写入 `content_probe_results_json` 时会记录 `detection_source` 和 `manual_detection`；普通手动探针、可信手动探针、自动探针、健康探针已经开始通过不同来源字符串区分。通过探针后，provider_model 会恢复 `passed/closed`，provider 也可能从 blocked/degraded/unknown 恢复到 passed 并刷新熔断；未覆盖完整必需探针或命中失败窗口时仍可能进入 blocked。

### 优点

- 内容防护不是简单关键词判断，还结合结构化响应、URL、上下文、provider 信任等级和流式策略。
- 支持全局设置、规则管理、文本检测、外部探针和内部 provider 探针。

- 深层 JSON 扫描有节点和深度上限，复杂 Responses、summary/reasoning、多模态 content 和 image_url 元数据扫描覆盖更完整，同时降低超深结构导致性能问题的风险。
- `request_content_guard_events` 与 `health_probe_events` 已进入正式内容防护迁移脚本，生产禁用自动 DDL 时不再只能依赖模型定义和 `create_all` 建表。
- `stage33` 已经成为内容防护架构契约的主基线，能在重构时快速发现规则服务边界、运行时策略、typed logging 和前端接线是否退化。
- 内容防护运行时事件默认 7 天窗口和导出列投影能降低运维页面、CSV 导出和无筛选查询对事件表的压力。

### 缺点

- `ContentGuardService` 与 `ProviderService` 直接互相牵连，检测结果写 provider 状态的边界不够清晰。
- 内容规则、路由策略、监控自动处置分布在多个服务中，整体行为需要跨文件理解。
- 流式内容防护与代理流式发送的反向 import 已明显改善：`ContentRuntimeGuardService` 不再导入 `ProxyService`，但 `ProxyService` 仍保留一批兼容包装方法，运行时检测、请求日志 summary、provider 状态写入和流式发送编排还没有完全通过端口和状态机分离。
- 手动可信状态会写入模拟探针明细用于追溯，这改善了展示，但也说明人工标记和真实探针需要在领域模型中明确区分来源。
- 配置、规则、探针和运行时状态的缓存失效边界仍不完整：内容防护设置和规则变更主要失效 settings runtime cache，未形成统一的 provider runtime、route candidate、v1 models 等缓存失效协议。
- API Key 级 `content_guard_required` 已从当前代码层移除；运行时检测是否执行由全局内容防护开关和 provider 的 `content_guard_enabled` 决定，流式首段缓冲再叠加低信任 provider 或高风险路由上下文判断。若存量数据库中仍残留历史字段，只能通过迁移废弃或删除，禁止重新解释为 Key 级绕过或强制检测开关。
- 可信探针选择与持久化边界已有改善：内部目标只有在选择完整必需探针时才写可信状态；但前端可选 probe_keys、必需探针、附加探针和“本次是否会持久化状态”的展示仍需要明确，探针失败次数、blocked 后恢复、provider 级与 model 级状态恢复也缺少完整闭环。
- 单次 `block` 结果现在会直接触发 provider_model `blocked` 与熔断打开，连续失败 3 次也会触发同类处置；这符合快速隔离高风险内容的方向，但当前仍由探针服务直接写状态，尚未经过统一 `ContentGuardActionStateMachine` 判断 `record_only`、关闭高风险拦截、手动探针来源和自动探针来源等上下文。
- 探针预算、来源标记和状态恢复仍写在 `ContentGuardProbeService` 中，目标应形成 `ContentProbeBudgetPolicy` 与 `ContentProbeStateTransitionPolicy`；否则后续新增探针时容易绕过 5 个 probe key、3 个污染场景、SSE 4 秒 idle/12 秒总时长/65536 字节等护栏。
- 手动探针通过后可恢复 provider/provider_model 状态，这对运维有用，但也要求状态机明确“手动检测通过是否足以恢复路由候选”“自动检测失败是否能覆盖手动恢复”“恢复后是否清理 `circuit_opened_at`”等边界。
- 外部检测安全边界已有明显改善，`https`、localhost/内网/IP 地址校验、域名 DNS 解析到内网地址拒绝和长度限制已落地；最新代码还为外部目标生成基于 host、endpoint 和 model 的稳定 `target_id`、负数 provider/provider_model 标识，并且返回 target 时不再暴露完整 `base_url`。剩余治理点主要是检测完成后前端密钥输入清理、响应大小/总超时、DNS 解析结果与真实请求之间的绑定。
- 内容防护 typed event 与请求日志摘要仍未完全闭合：列表/Tab/导出/迁移已补齐，非流式切换 provider 前也已避免额外生成孤立请求日志；但内容防护事件详情、请求日志摘要、CSV 字段、内容防护页面最近事件和健康探针事件之间还缺少统一 `ContentGuardEventProjection`，稳定表头与证据字段版本也未完成。
- 内容防护前端仍集中在 `initContentGuardPage` 大函数中，规则编辑、探针选择、本地检测、外部检测、结果渲染、Tab 切换、治理列表操作和状态刷新耦合；当前已补齐内容防护 Tab 点击切换、提供商“恢复/隔离”按钮请求接线、探针完成后自动跳转结果 Tab、本地检测动作/分类/片段/原因明细、复核态按钮反馈、探针勾选自定义样式、键盘焦点样式、规则表分页/筛选、规则配置错误提示和移动端规则表自适应，但危险操作确认、占位值保存、密钥清理和完整浏览器 smoke 仍需要继续治理。
- `record_only`/review 污染 provider 治理状态的问题已在 `record_violation()` 侧有明显收敛，但完整状态机仍未形成：高风险 block、safe_error、switch_provider、async_review、手动探针、自动探针和监控隔离仍需要统一定义“是否阻断、是否扣分、是否熔断、是否写 alert_events”。
- 手动模型健康测试会附带内容探针，但健康日志事件主要展开 `endpoint_results`，未完整展开 `content_probe_results`，导致日志中心无法复盘手动健康测试中的内容探针过程。
- SSE 探针、普通 JSON/文本探针和本地检测的规则口径仍可能不一致，例如 SSE 检测未显式传入自定义规则 JSON 时，会出现规则在一种链路生效、另一种链路不生效。
- 内容防护规则治理已有推进：`reason`、非法 regex、动作语义、URL 白名单、规则表分页/筛选、规则配置错误提示和 `image_url` 响应提取已进入后端或前端处理；剩余缺口主要是前端规则编辑器仍集中在大函数中，危险操作确认、占位值保存、工具参数/复杂 Responses 输出字段扫描一致性，以及规则变更后的缓存失效和浏览器 smoke 仍需补齐。
- 内容防护概览和规则列表已有展示/采样上限，但这些上限仍是 `ContentGuardModuleService` 内部常量，目标架构需要形成 `ContentGuardOverviewQueryPolicy`、`ContentGuardRuleListPolicy` 和 `ContentGuardProbeSourcePolicy`，否则拆分后容易重新出现全量 provider、全量日志或无法追踪探针来源的问题。
- 运行时事件默认 7 天窗口和导出列投影仍在 router helper 中，目标架构应形成 `ContentGuardRuntimeEventWindowPolicy` 与 `ContentGuardEventExportProjection`；否则日志中心、内容防护页面和未来 API 很容易各自定义默认时间窗、字段顺序和导出成本。
- `ContentGuardSettingsUpdate` 当前直接承担 URL 白名单 JSON 解析、域名规范化、去重和格式校验，短期提升了接口安全性，但从目标架构看应下沉到独立 `ContentGuardAllowlistPolicy` 或配置用例，避免 Schema 层继续承载复杂业务规则。
- 内容污染触发切换 provider 时，非流式路径已减少孤立失败 summary 日志，但流式污染、探针污染、健康失败和运行时高风险告警之间的边界仍需要统一事件投影和状态机约束。
- `stage33` 当前同时承担内容防护、typed logging、日志前端、迁移空库、规则 UI、设置校验和部署资源版本等多个领域契约，覆盖面强但也越来越像“巨型验收脚本”。后续若不拆成 pytest marker 或模块化用例，失败定位会变慢，内容防护模块和日志模块的测试边界也会继续耦合。

### 改进建议

- 将内容检测引擎、处置策略、provider 状态更新、告警上报拆成独立接口。
- 内容防护只产出 `GuardDecision`，由代理层或监控层按上下文执行动作。
- 对规则注册表、URL 检测、结构检测分别建立单元测试。
- 将可信检测结果建模为独立 `TrustProbeDecision`，明确固定答案、外链广告识别、流式污染检测三类必需探针、人工确认、真实探针、失败次数和最近通过/失败时间，供 provider_model 可信展示和路由可信策略复用。
- 继续把 `ProxyService` 中保留的内容防护兼容包装方法收敛为用例层调用，最终让代理只编排运行时防护结果，SSE 工具、运行时违规记录端口和错误响应构造器由内容防护或协议基础设施模块直接提供。
- 建立 `ContentGuardConfigService` 或等价配置用例，统一保存设置、规则、URL 白名单和自动预检间隔，并在写入后失效 settings、provider runtime、route candidates、v1 models 等受影响缓存。
- 将概览摘要、provider 展示限制、延迟采样、最近事件限制、规则分页筛选和规则配置错误投影下沉到内容防护查询用例，避免路由和前端直接关心 JSON 规则解析细节或全量数据边界。
- 建立 `ContentGuardRuntimeEventWindowPolicy` 和 `ContentGuardEventExportProjection`：无筛选查询默认最近 7 天，导出只按固定列投影，内容防护页面、日志中心 Tab、请求时间线和 CSV 导出复用同一 DTO、字段顺序和截断说明。
- 建立 `ContentProbeBudgetPolicy`：统一 probe_keys 最大 5、污染规则场景最多 3、SSE 探针 idle 4 秒、总时长 12 秒、最大读取 65536 字节、污染探针总超时 24 秒和单场景 8 秒。
- 建立 `ContentProbeStateTransitionPolicy`：统一 detection_source、manual_detection、通过恢复、失败降级、单次 block、连续失败 3 次、熔断打开时间清理/写入和 provider/provider_model 联动刷新。
- 在当前外部检测校验基础上继续建立 `ExternalContentProbePolicy`：保留 DNS 解析到私网地址拒绝，继续补充解析结果与实际请求的绑定、响应大小和总超时控制、检测完成后清理前端 API Key 输入、日志中对 base_url 做脱敏或哈希化目标标识，并为外部目标生成稳定追踪 ID。
- 扩展 `stage33_content_guard_regression_check.py` 或迁移后的 pytest：覆盖 probe_keys 交互语义、API Key 局部内容防护旧字段清理、外部目标稳定 `target_id` 和 base_url 脱敏、typed event 投影与稳定 CSV schema、SSRF/内网地址安全边界、blocked 恢复路径和内容防护页面浏览器 smoke。
- 将 `record_only`、`block`、`switch_provider`、`safe_error`、`async_review` 和“是否更新 provider 状态”拆成显式策略矩阵，确保仅记录策略不会误触发扣分、熔断或自动隔离。
- 将健康检查内容探针事件投影到 `HealthProbeEvent` 或 `RequestContentGuardEvent` 的统一结构中，手动测试弹窗、健康日志详情和导出必须看到同一组探针结果。
- 代理层执行 `switch_provider` 时，候选失败、命中规则、最终策略和重试 provider 数必须写入 typed event/trace 或统一内容防护事件表，禁止为同一次外部请求额外生成多条彼此孤立的失败 summary 日志。
- 把已落地的规则校验从 schema 层上升为独立 `ContentGuardRuleValidationService`，继续覆盖规则 JSON 损坏提示、规则导入/重置预览、重复 ID、ReDoS 复杂度和跨链路扫描一致性。
- 将 `stage33` 中新增的内容防护契约拆为多个 pytest case 或 marker：规则服务边界、运行时动作状态机、typed event 投影、前端 smoke、迁移空库、设置校验分别独立断言；根目录 `stage33_content_guard_regression_check.py` 继续作为兼容入口调用这些用例，避免脚本继续无限膨胀。

## 12. 路由策略、容量租约、限流与重试

### 功能是什么

系统根据 API Key 权限、模型映射结果、provider 可用性、挂载级端点协议与能力、健康度、容量、QPS/RPM、失败率、信任策略、内容完整性、会话粘性、当前负载、路由得分和成本等因素选择上游。达到容量或临时失败时可等待和重试。

### 怎么实现

- `RouterService` 加载可用候选并排序。
- `ProviderCapacityService` 管理 provider 活跃请求、流式请求、QPS/RPM 快照与租约。
- `ConcurrencyService` 管理全局、API Key、账户、provider 级并发租约。
- `RateLimitService` 管理 API Key 和 provider 短窗口限流。
- `ProviderHealthStateService` 记录 Redis 中的健康分、失败率、熔断桶。
- `ProxyService` 在主链路中获取和释放租约，并处理候选耗尽后的等待重试。
- 最新候选与缓存护栏：`RouterService.RAW_CANDIDATE_LIMIT=5000`，原始候选构造达到 5000 后停止继续构造并缓存当前候选窗口，避免极端 provider/model 挂载组合一次性生成过多候选；`RouterService._cache_list_digest()` 会把 allowed/preferred provider id、地域标签等策略列表转成 SHA256 16 位摘要，用于候选缓存 key，避免长列表直接拼入 key 造成 Redis key 过长或泄露策略明细；`ProxyService.MODEL_CATALOG_LIMIT_LOCK_LIMIT=2048` 与 `RouterService.CANDIDATE_CACHE_LOCK_LIMIT=2048` 分别限制模型目录 limit 锁和候选缓存锁表规模。
- 最新容量快照优化：路由读取 provider 容量前，会先按启用状态、熔断/维护状态、API Key 授权、端点协议和能力支持等条件预过滤 provider，再读取容量快照，避免为明显不可用候选做额外 Redis/容量计算。
- 最新重试 trace 护栏：`ProxyService.ROUTE_RETRY_TRACE_LIMIT=100`，候选耗尽等待和重试轨迹只保留最近 100 条，避免长时间等待窗口内 trace 无限增长。

### 优点

- 生产治理能力较强，考虑了多 worker 下需要 Redis 共享状态。
- 会话粘性、健康优先、容量硬过滤、失败率过滤和候选耗尽等待重试都已实现；当前用户可见路由口径已不再依赖权重字段。
- 路由评分已经移除内容完整性分、信任等级加减分和违规次数惩罚；内容完整性与可信策略更接近候选硬过滤/诊断原因，而不是混入软排序分数。
- 候选耗尽重试区分可恢复和不可恢复错误。
- 原始候选构造、候选缓存 key、候选缓存锁和重试 trace 都开始有明确上限，说明路由热路径正在补足大规模场景下的内存与 Redis key 边界。
- 容量读取前预过滤 provider 可以减少无效容量快照读取，让容量服务更专注于“有机会被路由选中的候选”。

### 缺点

- 路由决策散布在 `ProxyService`、`RouterService`、`ModelMappingService`、`ProviderCapacityService`、`ApiKeyService` 中。
- `RouterService` 直接依赖 `LogService`、`ProviderService`、`ModelCatalogService`、`SettingService` 等，领域边界不纯。
- 容量租约释放路径很多，虽然已有 finally 防护，但由于主链路过大，维护风险仍高。
- API Key 侧旧路由字段已退出，但全局 `SettingUpdate`、`SettingService` 和设置页仍保留 `route_mode`、`default_provider_id`、`manual_allow_fallback` 等兼容字段或展示逻辑；后续架构升级应把这些作为历史兼容输入收敛到健康优先策略模型，避免用户界面继续把手动/权重/故障切换当成主策略。
- `RAW_CANDIDATE_LIMIT`、`_cache_list_digest()`、容量预过滤、锁表上限和重试 trace 上限仍散落在 `RouterService` 与 `ProxyService`，目标 `RoutingEngine` 如果只迁移排序算法而漏掉这些资源预算，极端规模下仍可能出现候选构造过多、缓存 key 过长或 trace 膨胀。

### 改进建议

- 建立单独 `RoutingEngine`，输入为不可变 `RouteRequestContext`，输出为 `RouteDecision`。
- 容量租约封装为 async context manager，减少手工 release 分支。
- 对重试策略建立独立 `RetryPolicy`，便于测试不同错误类别。
- 建立 `RouteSettingsPolicy`，把历史全局 `route_mode/default_provider_id/manual_allow_fallback` 解释为兼容配置或迁移输入；目标前端只展示健康优先、候选数、容量、重试等待、可信策略等仍有效的路由治理项。
- 建立 `RouteRawCandidatePolicy`、`RouteCandidateCacheKeyPolicy` 和 `RouteRetryTracePolicy`：分别固化 5000 原始候选上限、SHA256 16 位策略列表摘要、2048 锁表容量上限和 100 条重试 trace 上限。
- 建立 `RouteCapacitySnapshotPolicy`：候选容量快照读取前必须先按启用、维护/熔断、授权、端点协议和能力支持做预过滤，并在诊断中保留过滤原因。

## 13. Responses 与 Chat 协议适配

### 功能是什么

系统优先要求上游原生支持 Chat Completions 或 Responses 请求端点。当前自动 Chat/Responses 端点互转 fallback 已禁用；只有在管理员显式开启 Responses→Chat 兼容适配时，才允许把 `/v1/responses` 单向接入 Chat-only 上游。适配器支持状态会话、previous_response_id、工具回合、上下文压缩、web_search 代理配置、快照大小限制和多种存储后端。

### 怎么实现

- `ResponsesChatAdapterService` 负责协议转换、状态读取保存、流式事件包装、上下文压缩和会话清理。
- `ProxyService` 负责判断正式请求端点是否具备原生支持；自动 fallback 不再作为默认兜底。
- 会话存储可用 memory、Redis 或 database；当前默认存储类型已从 memory 调整为 database，数据库表为 `responses_chat_adapter_sessions`，并由 `scheduled_responses_chat_adapter_session_cleanup` 定期清理过期状态。
- 回归：`stage31_responses_chat_adapter_regression_check.py`。
- 最新回归契约：`stage31_responses_chat_adapter_regression_check.py` 同时断言运行时配置与 `Settings` schema 的默认 adapter storage 均为 `database`，防止后续重构把默认会话存储退回单进程 memory。
- 最新资源护栏：`ResponsesChatAdapterService.MEMORY_SESSION_MAX_ENTRIES=10000`，环境变量上游规格解析上限为 `ENV_UPSTREAM_SPEC_LIMIT=500`；数据库会话清理使用 `DATABASE_CLEANUP_BATCH_SIZE=5000` 与 `DATABASE_CLEANUP_MAX_BATCHES=100`，避免一次清理无限扫描或长事务。

### 优点

- 禁用自动端点互转后，正式路由协议边界更清晰，不会在复杂请求中悄悄发生有损转换。
- 状态快照限制和上下文压缩防止无限膨胀。
- 支持环境变量上游映射，方便临时接入。
- database 默认存储比单 worker memory 更适合多进程和长期 previous_response_id 状态。
- memory 存储、环境变量规格和数据库清理都有明确上限，降低兼容适配器因为状态会话或配置膨胀拖垮主进程的风险。

### 缺点

- 适配逻辑分布在 `ResponsesChatAdapterService` 和 `ProxyService`，职责切分不彻底。
- `ResponsesChatAdapterService` 反向依赖 `ProxyService`，形成明显循环。
- 协议转换的对象模型仍以 dict 为主，复杂场景可读性一般。
- 显式适配虽然更安全，但要求管理员理解“原生端点支持”和“兼容适配”的区别，否则 Chat-only 上游不能自动承接 Responses 请求。
- 适配器资源上限仍散落为服务常量，目标架构缺少 `ResponsesChatAdapterResourcePolicy` 来统一内存会话上限、环境变量规格上限、数据库清理批大小和最大批次数。

### 改进建议

- 将协议转换定义为独立 `ProtocolAdapter` 接口，代理层只调用接口，不被适配器反向依赖。
- 对 Chat/Responses 请求和事件定义内部 DTO，减少 dict 深层访问。
- 适配器作为可选插件注册到代理编排层。
- 建立 `ResponsesChatAdapterResourcePolicy`：统一 memory session 10000、env upstream specs 500、数据库清理 5000 条一批且最多 100 批，并让 stage31 或 pytest 覆盖默认存储、清理边界和显式适配开关。

## 15. 监控指标与告警中心

### 功能是什么

系统提供 `/live`、`/ready`、`/health`、`/metrics` 以及后台 `/api/metrics/*`，展示数据库、Redis、连接池、活跃请求、队列积压、流量、provider、后台任务、内容防护等状态。告警中心记录异常事件，支持订阅设置和确认处理。

### 怎么实现

- 路由：`health.py`、`metrics.py`、`pages.py` 中 alerts 相关接口。
- 服务：`SystemMetricsService`、`AlertService`、`RuntimeStateService`。
- 数据模型：`AlertEvent`、`AlertSubscription`。
- 页面：`alerts.html`、`operations.html`、`dashboard.html`。
- 最新监控采集边界：`SystemMetricsService.PROVIDER_METRIC_LIMIT=200`，provider 指标快照对相关 provider 分组按事件量排序后最多采集 200 个，避免监控页在 provider 或日志规模变大后扫过多分组。
- 最新进程与后台快照边界：`SystemMetricsService.PROCESS_SCAN_LIMIT=500`，项目进程扫描最多遍历 500 个进程；`PROJECT_PROCESS_CACHE_SECONDS=30`，项目进程信息带 30 秒缓存并在响应中返回 `cache_seconds`；`BACKGROUND_SNAPSHOT_CACHE_SECONDS=5`，后台任务/队列快照使用 5 秒短缓存。这些边界说明监控页不应把进程扫描、Redis job state 扫描和后台队列快照当成无成本实时查询。
- 最新告警恢复边界：`AlertService.ALERT_RESOLVE_MAX_BATCHES=100`，告警服务单次最多恢复 100 批失活告警；`SystemMetricsService.MONITORING_ALERT_RESOLVE_MAX_BATCHES=100`，监控告警恢复也最多处理 100 批，防止一次刷新把大量历史告警恢复做成大事务。
- 最新告警看板查询边界：`AlertService.DASHBOARD_CACHE_TTL_SECONDS=15`，看板 payload 15 秒短缓存；异常用户候选最多 500，且只查询余额异常的启用用户；provider 异常事件最多 100；告警事件列表最多 500；异常 API Key 查询已在同一 SQL 中联表 owner username 与 owner balance，避免逐条回表。收益是告警中心刷新不会全量扫描用户、Key 和事件；风险是这些上限仍散在告警服务内部，还没有成为统一 `AlertDashboardQueryPolicy`。

### 优点

- 指标覆盖系统运行核心路径，包含 Redis、DB、队列、provider、后台任务。
- 监控异常能写入统一告警事件表。
- 内容完整性风险可触发自动隔离。
- provider 指标和告警恢复已有采集/维护上限，降低运维页面和告警刷新在历史数据增长后的热查询和长事务风险。
- 进程扫描、后台快照和告警看板都开始有短缓存、扫描上限和候选上限，运维页面在低配服务器上更可控。

### 缺点

- `SystemMetricsService` 超过 1300 行，采集、判断、告警生成、自动处置都在一起。
- 告警服务又依赖 API Key、计费、日志、provider、监控等多个服务，查询和事件生成耦合较强。
- 监控指标缺少清晰的采集器接口，新增指标容易继续堆进一个大文件。
- provider 指标采集上限和告警恢复最大批次数仍写在 `SystemMetricsService`、`AlertService` 内部，目标架构缺少统一 `ProviderMetricSamplePolicy` 与 `AlertResolveBatchPolicy`，页面也难以解释监控结果是否被截断。
- 进程扫描 500、项目进程缓存 30 秒、后台快照缓存 5 秒、告警事件列表 500、异常用户候选 500、provider 事件 100 等边界还没有统一成 `SystemMetricCollectionBudgetPolicy`、`ProcessScanPolicy`、`BackgroundSnapshotCachePolicy`、`AlertEventListPolicy` 和 `AlertDashboardQueryPolicy`；如果后续拆分监控采集器时遗漏其中一个常量，页面性能会出现回退。

### 改进建议

- 拆分指标采集器：DatabaseCollector、RedisCollector、QueueCollector、TrafficCollector、ProviderCollector、BackgroundJobCollector。
- 告警规则独立成 `AlertRule` 列表，输入指标快照，输出告警事件。
- 自动处置和告警记录分离，避免采集过程直接修改业务状态。
- 建立 `ProviderMetricSamplePolicy` 与 `AlertResolveBatchPolicy`：统一 provider 指标采集 200 上限、截断标记、告警恢复每轮 100 批、剩余告警处理方式和任务摘要字段。
- 建立 `SystemMetricCollectionBudgetPolicy`、`ProcessScanPolicy`、`BackgroundSnapshotCachePolicy`、`AlertEventListPolicy` 和 `AlertDashboardQueryPolicy`：统一 provider metric 200、进程扫描 500、项目进程缓存 30 秒、后台快照缓存 5 秒、告警事件列表 500、异常用户候选 500、provider 事件 100、看板 15 秒 TTL，以及截断提示、缓存新鲜度和写后收敛窗口。

## 16. 压测与真实上游验证

### 功能是什么

项目提供真实并发压测、内容防护开销压测、代理压测、真实上游功能测试和 mock OpenAI 上游服务，用于评估吞吐、延迟、SSE、日志落库和上游兼容性。最新实现开始为压测入口增加生产护栏，避免压测本身拖垮本机服务或堆积大量报告文件。

### 怎么实现

- 后台压测接口：`app/routers/benchmark.py`。
- 压测脚本：`scripts/real_concurrency_benchmark.py`、`benchmark_proxy.py`、`benchmark_proxy_node.js`、`benchmark_content_guard_overhead.py`。
- Mock 上游：`mock_openai_upstream.py`、`mock_openai_upstream_threaded.py`、`mock_openai_upstream_node.js`。
- 真实上游功能测试：`scripts/real_upstream_functional_test.py`、`run_real_upstream_functional_test.py`、`run_real_upstream_functional_test.ps1`。
- 管理端压测页面：`app/templates/benchmark.html` 与 `initBenchmark()` 支持模型选择器、端点过滤、任务启动/停止、轮询进度、实时日志、稳定并发结果展示、HTML/JSON 报告链接和 token 单位规范化展示。
- 后台接口已限制压测参数：基准并发最大 1000、探测最大并发 2000、样本请求最大 10000、每并发请求数最大 20、预热请求最大 1000、客户端和单请求超时最大 600 秒；页面表单的 `max` 值已与这些后端上限同步。
- 压测 job 和报告文件开始做资源保留控制：`app/routers/benchmark.py` 最多保留 20 个已完成 job、80 个 JSON/HTML 报告文件；启动新任务前和任务结束后会清理旧 job 或旧报告。`scripts/benchmark_proxy.py` 也限制请求数、并发、超时、预热、响应体读取上限、httpx 连接池上限，并在准备专用 benchmark API Key 时按 1000 条一批清理该 Key 的请求日志和账单流水。
- 最新脚本侧护栏：`scripts/benchmark_proxy.py` 将请求数限制为 10000、并发 500、超时 600 秒、预热 1000、单响应读取 1 MiB、HTTP 最大连接 1000、keepalive 500，并把专用 fixture provider/API Key 容量设置为与压测并发匹配但不超过 500。`scripts/real_concurrency_benchmark.py` 将基准并发限制为 1000、探测并发 2000、样本请求 10000、每并发请求数 20、单 stage 请求 10000、预热 1000、超时 600 秒、HTTP 最大连接 2000、keepalive 1000。`scripts/benchmark_content_guard_overhead.py` 将迭代次数限制为 20000、并发 256、扫描字节 262144。`scripts/real_upstream_functional_test.py` 查询上游模型最多取 1000 个，并按 1000 条一批清理功能测试 Key 关联日志和账单。
- 最新真实上游与压测脚本细节：`scripts/real_concurrency_benchmark.py` 报告文件只写一次；`scripts/real_upstream_functional_test.py` 的 `wait_for_logs()` 使用 `load_only()` 读取摘要字段，流式消费新增 `MAX_FUNCTIONAL_STREAM_EVENTS=1024` 与 `MAX_FUNCTIONAL_STREAM_BYTES=1MB`，并用 `time.monotonic()` 计算等待截止时间；`scripts/benchmark_proxy.py` 的 `wait_for_benchmark_background_idle()` 会先等待请求日志队列空闲，再轮询当前 benchmark API Key 未完成 token finalize 日志；`scripts/benchmark_content_guard_overhead.py` 的 `run_async_operation()` 复用线程本地 event loop，不再每次操作都 `asyncio.run()`。
- 容量默认回填脚本也补充了缓存失效护栏：`scripts/apply_capacity_defaults.py` 删除认证缓存时每批 500 个 key，单前缀最多扫描 10000 个，避免一次性 `scan_iter` 收集所有认证缓存 key 后大批量删除导致 Redis 或本地内存压力。

### 优点

- 覆盖了本地 mock、真实上游、并发压测和报告输出。
- 后台页面可启动和查看压测任务，方便运营验证。
- Node 与 Python 两套 mock/benchmark 增强了跨运行时验证能力。
- 页面侧已经能按模型和端点过滤可探测对象，并把长任务过程反馈、阶段结果和报告下载放在同一工作流中，适合日常容量验收。
- 压测入口开始有明确资源上限、报告保留和响应体上限，不再允许页面或脚本直接发起 5000 到 20000 并发、20 万请求这类过重参数，降低误操作风险。
- 压测脚本和真实上游功能测试开始使用分批清理，降低清理专用测试 Key 历史日志/账单时的大事务风险。
- 内容防护性能基准和内容防护扫描字节上限使用同一 262144 字节硬边界，能把运行时策略和性能评估绑到同一个资源预算。
- 压测报告、真实上游流式读取、日志等待和后台空闲判断都有明确边界，报告更接近“后台日志与计费已收敛后的系统状态”。
- 内容防护性能脚本复用 event loop，降低微基准中事件循环创建本身对开销测量的干扰。

### 缺点

- 压测 job 以进程方式管理，状态存在内存字典中，服务重启后历史运行态不可恢复。
- 压测逻辑与后台接口耦合，缺少统一 job 存储和取消协议。
- 已完成 job 和报告文件虽有数量保留，但仍不是持久化 `BenchmarkJobStore`，多进程部署或 Web worker 重启后仍无法跨进程查询历史状态。
- 脚本侧上限和后台接口上限仍不是同一个 `BenchmarkLimitPolicy` 输出：代理压测脚本并发上限 500，后台基准并发上限 1000，真实并发脚本探测并发上限 2000，内容防护性能脚本并发上限 256。它们可能都有合理场景，但需要在目标策略中明确不同 profile，避免后续维护者误以为只有一套上限。
- 认证缓存失效扫描上限目前只写在容量默认回填脚本里，API Key、用户、授权绑定等其它写操作如果继续各自失效缓存，仍可能出现不同批大小和不同扫描边界。
- 报告写入、流式读取、后台空闲等待、subprocess 输出回放和 event loop 复用目前分散在多个脚本中；这些是工程治理策略，不应依赖脚本作者逐个记住。

### 改进建议

- 建立 `BenchmarkJobStore`，把 job 状态、参数、报告路径持久化。
- 将压测执行器抽象为后端 worker，可迁移到独立任务进程。
- 将当前散落在 API、页面和脚本里的压测上限收敛为 `BenchmarkLimitPolicy`，统一定义并发、样本数、超时、报告保留、响应体上限和专用测试数据清理策略。
- 建立 `BenchmarkProfilePolicy`：区分页面基准压测、代理脚本压测、真实并发探测、内容防护性能基准和真实上游功能验证，分别定义请求数、并发、响应体、连接池、模型候选和清理批大小；文档、脚本和页面必须引用同一策略说明。
- 建立 `BenchmarkReportWritePolicy`、`FunctionalTestLogSummaryLoadPolicy`、`FunctionalStreamReadPolicy`、`BenchmarkBackgroundIdlePolicy` 和 `BenchmarkAsyncLoopReusePolicy`：统一报告单次写入、功能测试日志 `load_only()`、真实上游流式 1024 事件/1MB 上限、压测报告前队列与 token finalize 空闲确认、内容防护性能基准 event loop 复用。
- 将认证缓存失效扫描护栏抽成 `AuthCacheInvalidationPolicy`：保留单前缀扫描上限 10000、删除批大小 500，并由容量默认回填、API Key 变更、用户变更和授权绑定变更等写操作复用。

## 17. 后台任务与独立 worker

### 功能是什么

系统支持后台请求日志队列、统一日志事件队列、Token/计费 finalize 队列、定时健康检查、定时数据清理、Responses adapter 会话清理。生产可以关闭 Web 进程内 worker，使用 `scripts/run_background_workers.py` 独立消费。

### 怎么实现

- 应用生命周期：`app/main.py` 中 `lifespan` 启动 Redis、上游客户端、后台 worker 和 scheduler。
- 队列服务：`RequestLogQueueService`、`LoggingQueue`、`TokenUsageService`。
- 调度器：`AsyncIOScheduler`，任务定义在 `app/tasks.py`。
- 分布式锁：`distributed_job_lock` 使用 Redis `SET NX EX` 和 Lua 脚本释放。
- 独立 worker：`scripts/run_background_workers.py`。
- Web 生命周期清理：`app/main.py` 的 lifespan 已为 Redis、上游客户端、日志队列、请求日志队列、Token finalize worker 和 scheduler 增加启动阶段标记，并用统一 `try/finally` 只关闭已成功启动的组件，避免中途启动失败后遗留连接或后台任务。
- 独立 worker 启停清理：`scripts/run_background_workers.py` 同样为 Redis、统一日志队列、请求日志队列和 Token finalize worker 增加启动标记，启动失败时只关闭已启动组件。
- 请求日志可靠入队：`RequestLogQueueService.enqueue` 在 Redis 事件循环线程内遇到 ingress queue 满载时，已从直接抛 `QueueFull` 改为降级写入 Redis 主队列，避免瞬时拥塞破坏可靠入队语义。
- 队列恢复：`RequestLogQueueService` 与 `LoggingQueue` 的 processing 队列恢复已改为每批 500 条拉取、回推主队列并 `ltrim`，避免 worker 重启时一次性读取全部 processing 列表造成 Redis 或内存压力。
- 最新任务行为：Redis 分布式锁不可用时任务会跳过并写入 `BackgroundJobEvent`，状态区分 `skipped_lock_unavailable` 与 `skipped_locked`；任务成功时会记录 processed/success/failed 数量。
- 最新调度并发边界：`configure_scheduler()` 为 provider L0、model L1、model L2、content L3、token backfill、data retention、responses cleanup 和 IP management cleanup 都设置 `max_instances=1` 与 `coalesce=True`；misfire grace time 分别为 provider L0 30 秒、model L1 60 秒、model L2 120 秒、content L3 120 秒、token backfill 15 秒、data retention 300 秒、responses cleanup 120 秒、IP management cleanup 300 秒。这说明调度层已经开始明确“不并发补跑、不无限堆积错过任务”的生产口径。
- 最新任务触发来源：`distributed_job_lock` 已读取并写入 `trigger_type`，Redis job state 与 `BackgroundJobEvent` 都能记录 scheduler、manual、startup、system 等来源；任务结果摘要通过 `BACKGROUND_JOB_RESULT_SUMMARY_MAX_BYTES=8192`、字符串 500 字符、列表 50 项限制写入体积。
- 内容完整性 L3 定时探针不再跟随普通健康检查间隔，而是使用 `content_guard_probe_interval_sec`；仅当 `content_guard_enabled` 与 `content_guard_precheck_auto_enabled` 同时开启时执行。
- IP 管理事件清理已进入 APScheduler：`scheduled_ip_management_event_cleanup` 每 6 小时按 `event_retention_days` 清理旧事件，并复用 Redis 分布式锁和后台任务事件口径。
- IP 管理事件清理也已按批执行：`IpManagementEventService.CLEANUP_BATCH_SIZE=5000`，每批按 ID 删除并提交，避免事件表长期运行后清理任务形成大事务。
- IP 管理事件清理已有最大批次数：`IpManagementEventService.CLEANUP_MAX_BATCHES=100`，单次最多删除 100 批，剩余历史事件留给下一轮清理任务。
- 数据保留清理已改为分批删除：`DataRetentionService.CLEANUP_BATCH_SIZE=5000`，通过 `_delete_batched` 按 ID 批量查询和删除 request_logs、审计日志、子事件、健康事件、计费事件等旧数据，每批提交一次，降低大表清理时长事务和锁表风险。
- 最新数据保留边界：`DataRetentionService.CLEANUP_MAX_BATCHES_PER_MODEL=100`，每类模型或事件表的清理最多连续处理 100 批。该上限与 5000 条批大小结合后，能防止一次定时清理无限占用数据库，目标架构应形成 `DataRetentionBatchPolicy` 并写入任务结果摘要。
- 最新日志清理边界：`LogService.CLEAR_LOGS_MAX_BATCHES=100`，管理员清空日志时单次最多删除 100 批；若仍有剩余，需要再次触发或交给后台清理，避免一次手动操作长时间锁住日志表。
- Token finalize worker 停止时会关闭 Redis client，延迟入队任务也增加 done callback、取消释放和异常释放逻辑，降低停机或延迟任务失败后 finalize job 长期占用幂等标记的风险。
- Token finalize worker 批处理配置已进入运行时：单批默认 50、服务层硬上限 500，队列大小来自 `token_finalize_queue_size`；定时 backfill 由 `token_usage_backfill_interval_seconds` 控制且最小 15 秒。后台任务模块需要把它和 request log queue、typed logging queue 一起纳入统一队列吞吐配置，而不是只在计费服务内部解释。

### 优点

- 后台化设计能降低请求主链路阻塞。
- Redis 分布式锁避免多 worker 重复执行同一个调度任务。
- 请求日志入口队列满载时可降级到 Redis 主队列，减少高并发瞬时拥塞导致日志入队失败的风险。
- 独立 worker 形态符合生产部署需求。
- Web worker 和独立后台 worker 启动失败时能按阶段清理资源，重启稳定性更好。
- 任务事件从“只记录完成结果”增强到能记录运行中、跳过、锁不可用、处理数量和失败数量，便于日志中心按后台任务筛选排障。
- 数据保留从一次性 delete 改为按 ID 分批删除，更适合生产大表，但也暴露出数据保留模块需要独立仓储和任务用例，不应长期把所有表的清理条件堆在一个服务函数中。
- 清理最大批次数让后台任务具备“本轮做多少就停止”的资源边界，避免长期积压时单轮任务拖垮数据库。
- 调度任务统一 `max_instances=1`、`coalesce=True` 和明确 misfire grace time，能避免低配服务器或短暂阻塞后多个相同任务并发补跑。
- `trigger_type` 与 8192 字节结果摘要上限让任务来源和结果体积更可观测，日志中心筛选调度/手动/启动任务时不会混成同一类。
- IP 管理事件清理、数据保留清理、管理员清空日志、告警恢复都开始有最大批次数，这说明后台维护任务已经从“尽量一次做完”转向“单轮有预算、剩余留到下一轮”的生产口径。
- Token finalize 批处理和 backfill 周期可配置，能让高峰期实时补算和低峰期兜底补算分摊压力，减少主请求链路阻塞。

### 缺点

- 队列实现存在 `RequestLogQueueService` 与 `LoggingQueue` 两套体系，语义相近但用途不同。
- 后台任务和业务服务仍在同一代码层互相调用，缺少统一任务契约。
- 部分任务失败状态依赖日志记录，缺少集中重试面板。
- `RequestLogQueueService.enqueue` 不再因为当前进程未检测到 active worker 就拒绝入队，这提升 Web/worker 分离形态的可靠入队能力，但也更依赖部署侧保证至少一个独立 worker 持续消费。
- `BackgroundJobEvent` 当前更像“调度任务锁事件”，不能覆盖所有后台队列；如果只看后台任务 Tab，可能误以为队列消费、Token finalize、日志落库和独立 worker 都已完整可观测。
- 后台任务先写 `running` 再更新同一行，若进程崩溃，记录可能长期停留在运行中；当前日志查询层已能把 2 小时以上 running 标为 `stale_running`，但仍缺少真实心跳、超时转失败和运维侧修复入口。
- `trigger_type` 已开始从任务装饰器、健康检查和后台任务事件传递，手动触发、启动触发、系统触发、调度触发的口径比之前清晰；但还没有统一 `JobTriggerPolicy`，各任务仍可能自行拼来源。
- APScheduler 的 `max_instances/coalesce/misfire_grace_time` 现在写在 `configure_scheduler()` 里，目标架构还没有 `SchedulerJobConcurrencyPolicy` 与 `SchedulerMisfirePolicy`；新增任务如果忘记这些参数，仍可能回到并发补跑或 misfire 语义不一致。
- `CLEANUP_MAX_BATCHES_PER_MODEL=100` 仍是数据保留服务内部常量，任务页面还不能稳定说明“是否因为批次数上限而本轮未清完、剩余多少、下轮何时继续”。
- `CLEANUP_MAX_BATCHES=100`、`CLEAR_LOGS_MAX_BATCHES=100`、`ALERT_RESOLVE_MAX_BATCHES=100` 这类最大批次散落在不同服务里，尚未形成统一维护任务预算模型；如果后续新增清理/恢复任务，很容易漏掉单轮上限或摘要字段。
- Web lifespan 与独立 worker 已有相似的分阶段启动清理逻辑，但还没有抽象为共享生命周期组件；后续新增队列或客户端时，如果只改其中一处，仍可能出现 Web 与 worker 启停行为不一致。
- Token finalize 的实时队列、延迟入队和 backfill 调度仍散在 `TokenUsageService`、`tasks.py` 与配置项中，目标队列模块需要输出“实时处理吞吐、兜底积压、批大小、重试次数、幂等占用释放”的统一观测，否则日志队列空闲并不等于计费已经收敛。

### 改进建议

- 统一后台任务抽象：队列名称、payload schema、幂等键、重试策略、死信处理。
- 将请求日志、事件日志、Token finalize 都迁移到统一任务基础设施。
- 为后台任务增加心跳、超时、stale running 检测、死信队列和重放入口；锁不可用、抢锁失败、任务失败、消费失败必须有不同事件类型和告警等级。
- 将 `BackgroundJobEvent` 与队列消费指标分离，后台任务页面同时展示调度任务状态和队列状态，但不要把二者混成一个“后台任务成功率”。
- 建立 `DataRetentionBatchPolicy`：统一 5000 条批大小、每模型/每表最多 100 批、剩余数据估算、任务摘要字段、后台任务告警阈值和测试验收，避免重构后恢复为无上限清理或单事务删除。
- 建立 `MaintenanceBatchBudgetPolicy`：覆盖 IP 管理事件清理、管理员清空日志、告警恢复、模型映射规范化、数据保留清理等单轮维护任务，统一 100 批上限、达到上限的告警/摘要、剩余数据处理和再次触发策略。
- 建立 `WebLifespanStartupCleanupPolicy` 与 `BackgroundWorkerStartupCleanupPolicy`：统一阶段标记、启动失败清理、关闭顺序、部分启动组件关闭、异常摘要和编译/启动验收，Web 进程与独立 worker 复用同一生命周期语义。
- 建立 `TokenFinalizeQueuePolicy`：统一 token finalize worker 数、队列大小、批大小默认 50、批大小硬上限 500、延迟入队 0-5000 ms、backfill 最小 15 秒调度周期、队列满转 backfill 和停止时幂等释放策略。
- 建立 `SchedulerJobConcurrencyPolicy`、`SchedulerMisfirePolicy`、`JobTriggerPolicy`、`IpManagementEventRetentionJobPolicy` 和 `JobResultSummaryPolicy`：统一所有定时任务 `max_instances=1`、`coalesce=True`、各任务 misfire grace time、触发来源枚举、IP 管理事件每 6 小时保留期清理，以及后台任务摘要 8192 字节/字符串 500/列表 50 的脱敏截断边界。

### 怎么实现

- 配置：`app/config.py`。
- 数据库：`app/database.py` 使用 SQLAlchemy engine 和 SessionLocal。
- 内置初始化：`app/main.py` 的 `init_database` 和多个 `_migrate_*` 函数。
- SQL 迁移：`migrations/*.sql`。
- 部署脚本：`start_aliyun.sh`、`start_tencent.sh`、`update_aliyun.sh`、`update_tencent.sh`、`run.ps1`。
- 独立 DB 初始化：`scripts/run_startup_db_init.py`。
- 真实上游包装脚本：`scripts/run_real_upstream_functional_test.py` 的健康等待与日志等待使用 `time.monotonic()`，日志摘要通过 API Key ID-only 查询和 `load_only()` 读取摘要字段；子进程 stdout/stderr 写到固定日志文件，结束后按 `MAX_FUNCTIONAL_SUBPROCESS_OUTPUT_BYTES=1MB` 回放，并设置 `PYTHONIOENCODING=utf-8`。
- 数据库连接池：`app/config.py` 已新增 `db_connections_per_worker`，当 `DB_POOL_SIZE=0` 时按 `WEB_CONCURRENCY × DB_CONNECTIONS_PER_WORKER` 动态补齐连接池；当 `DB_MAX_OVERFLOW=0` 时按连接池规模自动补齐 overflow。
- 上游连接池：`app/config.py` 将 `upstream_max_connections` 默认收敛为 200，并钳制在 10 到 5000；`upstream_max_keepalive_connections` 默认 50，并钳制在 1 到 `upstream_max_connections`。`UpstreamClientService` 的 httpx limits 使用这两个配置，aiohttp `TCPConnector.limit` 使用最大连接数，`limit_per_host` 使用 `min(keepalive, max_connections)`；httpx/aiohttp 客户端因配置指纹变化而重建时，会异步关闭旧连接池，避免热变更后旧连接长期悬挂。
- 部署默认值：`.env.example` 和 `start_aliyun.sh` 已把 `WEB_CONCURRENCY` 默认收敛到 2，`DB_POOL_SIZE`/`DB_MAX_OVERFLOW` 改为 0 以触发动态计算；阿里云部署入口默认关闭 Web 进程内后台 worker，鼓励使用独立后台 worker 服务。
- 启动期数据库初始化边界：`_should_run_startup_database_init()` 在生产环境会忽略 `ENABLE_STARTUP_DB_INIT` 并警告，禁止 Web worker 启动阶段执行 create_all 或自动 DDL；`enable_startup_heavy_sync` 默认 `False`，只有显式开启时才在启动初始化里执行 API Key 自动 provider 绑定、历史 provider model 同步和模型目录同步；启动补账回填使用 `startup_billing_backfill_batch_size`，默认 5000，运行时钳制在 1 到 50000。这说明启动期已经从“顺手做所有兼容迁移和重同步”转向“生产跳过 DDL，重同步显式开关，重补账有批大小”的部署口径。

### 优点

- 本地开发启动门槛低。
- 部署脚本覆盖 venv、依赖、Redis、PostgreSQL、Gunicorn、systemd、nginx、SSE 配置和健康检查。
- 数据库连接池默认值开始与 Web worker 数联动，低配服务器和多 worker 形态更容易保持资源口径一致。
- 上游连接池默认从高并发固定大池收敛为更保守的 200/50，并有 10-5000、1-max 的钳制范围；aiohttp 按 keepalive 约束单 host 并发，低配部署更不容易因为默认池过大耗尽文件描述符或上游连接。
- 上游客户端重建时释放旧连接池，降低连接泄漏和热配置切换后的资源占用风险。
- 真实上游包装脚本避免系统时间回拨影响等待窗口，并避免异常输出通过 `communicate()` 无界进入内存。
- 生产 Web worker 启动不再执行 DDL；重型启动同步默认关闭，避免多 worker 启动时重复执行模型目录同步、API Key 授权同步和历史账单回填。

### 缺点

- `app/main.py` 中内置大量 DDL 补字段逻辑，与独立 `migrations/*.sql` 并存，迁移来源不唯一。
- 当前不是 Alembic 这类版本化迁移体系，难以精确追踪每个环境已应用的迁移版本。
- 根目录部署文档和历史临时说明较多，知识分散。
- 阿里云脚本虽已把 Web worker 默认降到 2 并默认关闭内置后台 worker，但独立后台 worker 是否启用仍依赖 `ENABLE_SEPARATE_BACKGROUND_SERVICE`，部署验收时必须确认队列确实有人消费。
- 数据库池、上游池、Web worker 和后台 worker 默认值已经开始联动，但还没有统一的 `RuntimeResourceProfile` 输出总连接数、文件描述符预算、DB 最大连接占用和上游并发预算；部署时仍需要人工推导这些参数是否适合 2C2G、单机多 worker 或 Web/worker 分离形态。
- 迁移/联调脚本已经出现 keyset 分页、单调时钟、输出落盘限量回放等资源边界，但它们仍是脚本局部实现；目标工程治理层需要把这些写成脚本通用策略，避免下一个迁移或包装脚本重新使用 offset 或无界 pipe。
- 内置兼容 DDL 仍保留在 `app/main.py` 供开发或独立初始化使用，虽然生产启动已跳过，但目标仍要迁出到正式 migration runner；否则开发启动、独立初始化和 SQL migration 三套字段口径仍可能漂移。
- `enable_startup_heavy_sync` 与 `startup_billing_backfill_batch_size` 仍属于启动入口配置，目标需要把“启动同步、历史补账、模型目录同步、授权同步”迁到显式维护任务或 CLI，避免 Web 启动路径长期承担数据修复职责。

### 改进建议

- 引入版本化迁移目录和迁移状态表，逐步把 `app/main.py` 里的 DDL 移出。
- 保留开发环境自动初始化，但只调用迁移执行器，不在应用入口散落 DDL。
- 统一部署文档，把历史临时命令整理为正式运维手册。
- 建立 `StartupDatabaseInitPolicy` 与 `StartupHeavySyncPolicy`：生产环境 Web worker 禁止 DDL；重型同步默认关闭，只能由独立初始化/维护命令显式触发；启动补账批大小默认 5000、最大 50000，并且必须记录处理条数、是否达到批量上限和剩余处理方式。
- 建立 `RuntimeResourceProfile`、`DatabasePoolSizingPolicy` 和 `UpstreamClientPoolPolicy`：统一 `WEB_CONCURRENCY=2` 保守默认、`DB_POOL_SIZE=0` 动态计算、`DB_CONNECTIONS_PER_WORKER=10`、overflow 自动补齐、上游连接池默认 200/50、钳制范围和 aiohttp per-host 语义；部署脚本、`.env.example`、配置校验和监控页面应能展示这些推导结果。

- 金额、token、`$/1M` 等展示格式已抽出后端 `app/utils/display_format.py`，前端也同步使用 `<数字> $`、`token/k/m`、`$/1M` 口径，减少模板、JS 和接口展示不一致。

### 缺点

- `app/static/js/app.js` 单文件已超过 17280 行，`app/static/css/app.css` 单文件超过 12860 行，页面逻辑高度集中。
- 多页面初始化函数共享大量全局变量和工具函数，缺少模块边界。
- 任何页面交互修改都可能影响全站脚本，测试粒度较粗。
- 日志详情、provider 操作菜单、内容防护探针、压测页面和模型能力矩阵继续堆在同一个 `app.js` 中，虽然功能更完整，但也进一步放大了前端控制器巨石化风险。
- 新增 API 超时、页面级 abort、壳层导航 abort、页面隐藏跳过轮询等基础能力后，前端生命周期管理已经具备雏形，但仍散落在巨型 `app.js` 中，缺少独立 `ApiClient`、`PageLifecycle` 和轮询控制器，后续页面很容易重复实现或遗漏取消逻辑。

### 改进建议

- 在不改变界面和功能前提下，把 JS 拆分为 `core/`、`components/`、`pages/`、`api/` 模块，再由打包或多脚本方式加载。
- 把当前 `fetchWithTimeout()`、45 秒默认超时、页面切换 abort、壳层导航 abort 和隐藏页暂停轮询抽成 `core/api_client.js` 与 `core/page_lifecycle.js`，让所有页面复用同一取消、超时和错误归一化策略。
- CSS 拆成 tokens、base、layout、components、pages。
- 为关键前端工具函数补充轻量 Playwright 或 DOM 测试。

## 20. IP 管理、可信代理解析与来源 IP 治理

### 功能是什么

项目已开始新增独立的 IP 管理模块，用于管理请求来源 IP 的可信解析、规则匹配、IP 维度限流、阻断、观察记录、事件审计和测试验证。该模块的目标不是替代对外 API Key 鉴权，也不是新建第二套请求日志主表，而是在保持现有功能默认不变的前提下，为 `/v1/*`、`/api/*` 和用户端页面提供可独立启停的来源 IP 安全治理能力。

### 怎么实现

- 数据模型：`app/models/ip_management.py` 已定义 `IpManagementSetting`、`IpAccessRule`、`IpManagementEvent`，对应 `ip_management_settings`、`ip_access_rules`、`ip_management_events`。
- Schema：`app/schemas/ip_management.py` 已定义设置更新、规则创建/更新、解析测试、规则测试等入参结构。
- 服务：`ClientIpResolver` 负责可信代理解析，`IpManagementRuleService` 负责 exact IP、CIDR、range 规则规范化和匹配，`IpManagementRateLimitService` 使用 Redis key 执行 QPS/RPM 限流，`IpManagementEventService` 负责事件写入、分页和清理，`IpManagementService` 负责编排设置、作用域、解析、规则、限流、事件和总览。
- 中间件：`IpManagementMiddleware` 已在 `app/main.py` 注册，模块启用且作用域命中时调用 `IpManagementService.evaluate_request`；外部 `/v1/*` 阻断或限流返回 OpenAI 兼容错误对象，内部 `/api/*` 返回内部 JSON 错误。
- API：`app/routers/ip_management.py` 已提供 `/api/ip-management/overview`、`settings`、`rules`、`events`、`events/{event_id}`、`test-resolution`、`test-rule` 和事件清理接口，并对写操作记录管理员审计；事件列表已支持状态码、开始时间、结束时间等筛选条件，当前若传入 `api_key` 查询参数会返回 422，明确表示暂不支持 API Key 前缀筛选。
- 迁移：`migrations/2026-06-08_add_ip_management_module.sql` 已创建配置、规则和事件表及索引，`app/main.py` 也有开发期兼容建表逻辑。
- 当前页面状态：`pages.py` 已有 `/ip-management` 页面入口，`app/templates/ip_management.html` 已提供总览指标、可信代理命中指标、设置、可信头优先级、规则、事件、解析测试、规则测试和规则编辑弹窗，`base.html` 左侧导航也已展示“IP 管理”；`app/static/js/app.js` 已注册 `page === "ip-management"` 初始化分支并新增 `initIpManagementPage()`，当前页面控制器已调用 `/api/ip-management/overview`、`settings`、`rules`、`events`、`events/{event_id}`、`events/cleanup`、`test-resolution`、`test-rule`，可完成管理端配置、查看、清理和测试闭环；解析测试会读取 `ip-test-trusted-header-order`，未选择时回退到已保存设置。
- 最新性能边界：`IpManagementService._RULE_CACHE_TTL_SECONDS=5`，启用规则会按快照缓存并在规则创建、更新、启停、删除后主动失效；`/api/ip-management/events` 在没有任何筛选和时间范围时默认查询最近 7 天事件；总览接口已使用条件聚合统计关键指标，避免为页面指标加载全量事件。
- 最新中间件快路径：`IpManagementMiddleware` 会在路径不属于 IP 管理作用域，或关闭状态设置缓存仍新鲜时提前短路，不再为无关请求创建数据库会话。这保证模块默认关闭或只启用局部作用域时，对 `/static`、不相关页面和普通请求的额外成本接近 no-op。

### 优点

- 模块默认关闭，且作用域开关、规则引擎、阻断、限流、事件记录均可独立控制，符合“不启用不改变现有行为”的安全上线原则。
- 可信代理解析只在直连来源命中可信代理 CIDR 时才使用 `Forwarded`、`X-Forwarded-For`、`CF-Connecting-IP`，避免直接信任客户端可伪造请求头。
- `ClientIpResolver.parse_forwarded_header()` 已通过 `strip_forwarded_for_value()` 收紧 `Forwarded for=` 解析：会去掉引号，拒绝空值、`unknown`、以下划线开头的 obfuscated identifier，支持 `[IPv6]` 方括号，剥离 IPv4 端口，并拒绝未加方括号且包含多个冒号的 IPv6 候选；`all_forwarded_entries_trusted` 也改为每个转发 IP 命中任一可信网段即可，而不是错误要求所有地址落在同一个网段。
- IP 限流使用 Redis 共享状态，不依赖单 worker 内存计数。
- 事件写入已开始执行 `event_sample_rate` 采样、`trace_id` 幂等去重、IP 掩码和原始转发链保存开关，事件列表也具备更细筛选和详情入口。
- `IpManagementService` 的设置读取已加入 5 秒进程内缓存并使用 `SimpleNamespace` 快照，设置保存后通过 `invalidate_cache()` 失效；这降低了请求中间件频繁读库，但目标架构仍应把设置缓存口径迁入独立配置应用服务。
- 启用规则快照缓存和写后失效让请求中间件不必每个请求全量查规则；事件默认 7 天窗口和总览条件聚合降低了管理页无筛选加载成本。
- 中间件快路径能保持模块关闭或路径不命中时不打扰主链路，符合“默认关闭不改变现有行为”的设计目标。
- 事件表与 `request_logs` 主表分离，通过 trace、路径、作用域、规则和决策记录模块自身证据，避免重复造第二套请求日志主表。
- `/v1/*` 和 `/api/*` 错误响应按不同协议返回，边界比直接在 API Key 鉴权里塞 IP 处置更清楚。

### 缺点

- `IpManagementService` 当前同时负责设置缓存、规则 CRUD、请求决策、事件写入、总览统计和序列化，已经有继续长成第二个“大服务”的趋势。
- 中间件直接创建 `SessionLocal`，事务、异常和失败放行策略还没有通过统一应用用例层管理。
- `IpManagementEventService.create_event` 同步提交数据库，若高流量下启用事件记录，可能给请求主链路增加写库压力。
- `event_sample_rate`、`store_raw_headers_enabled` 已开始影响事件写入，但事件落库仍在请求链路同步执行，尚未接入统一后台事件队列。
- `IpManagementEventService.cleanup_old_events` 已经按 5000 条一批删除旧事件，这解决了清理大事务风险，但清理调度仍直接由 `app/tasks.py` 调用模块服务，尚未进入统一数据保留 JobHandler。
- `fail_open_enabled` 已开始影响 Redis 限流后端失败场景；但中间件自身异常仍是记录 warning 后放行，尚未把所有模块异常都纳入统一 fail open / fail closed 策略。
- 新模块尚未与现有 `ApiKeyService.extract_source_ip()`、`ProxySafeHelpers.extract_source_ip()` 和用户操作审计来源 IP 形成统一口径；默认仍不改变 API Key 来源 IP 白名单判断。
- 管理端事件筛选当前尚未支持 API Key 前缀，接口会显式拒绝 `api_key` 查询参数；后续如要支持，应先在事件投影和索引上明确 API Key 前缀脱敏、权限边界和查询成本。
- 页面模板、导航入口、CSS 和前端控制器已补齐，管理员已经可以从当前前端完成 IP 管理的总览查看、配置保存、规则维护、事件筛选详情、事件清理和测试验证；剩余风险已从“不可操作”转为“前端页面控制器仍被塞在巨型 `app.js` 中，缺少独立模块和浏览器 smoke 验收”。
- 规则缓存、事件默认窗口和总览聚合仍在服务/路由内部硬编码，尚未成为 `IpRuleCachePolicy`、`IpManagementEventWindowPolicy` 和 `IpManagementOverviewProjection`；后续拆分时若只搬代码，容易遗漏缓存失效或默认查询窗口。
- 中间件快路径目前仍嵌在 `IpManagementMiddleware`，目标需要 `IpMiddlewareFastPathPolicy` 明确哪些路径、哪些关闭缓存状态可以不建库会话，避免后续改造把 no-op 成本重新变高。

### 改进建议

- 将 `IpManagementService` 拆成 `IpManagementSettingsService`、`ClientIpResolver`、`IpAccessRuleService`、`IpDecisionService`、`IpEventQueryService` 和 `IpManagementApplicationService`。
- 中间件只负责读取决策结果并转换 HTTP 响应，具体 DB、缓存、错误目录和事件写入由应用层用例处理。
- 事件记录迁入统一日志/后台队列，至少支持采样、幂等、异步落库、保留清理和 trace 回填 request_log_id。
- 将当前 `/ip-management` 的 `initIpManagementPage()` 拆为独立页面模块，保留总览、设置保存、规则 CRUD、事件筛选/详情/清理、解析测试和规则测试现有行为；后续重点是模块化、浏览器 smoke 和 API DTO 稳定化，而不是再补基础接线。
- 在保持默认不变前提下，为 API Key 白名单增加显式开关：只有管理员确认后才允许使用 IP 管理解析结果替代旧 `extract_source_ip()` 结果。
- 为解析服务、规则服务、限流服务和中间件 no-op 行为补充单元/集成测试，重点覆盖伪造 XFF、可信代理链、Forwarded 引号、`unknown`、obfuscated identifier、IPv4 端口、IPv6 方括号、未括号 IPv6 拒绝、Cloudflare 头、block/rate_limit 和默认关闭不影响请求。
- 建立 `IpRuleCachePolicy`、`IpManagementEventWindowPolicy` 和 `IpManagementOverviewProjection`：统一规则快照 TTL 5 秒、规则写操作主动失效、无筛选事件默认 7 天、总览条件聚合字段和 stage36 验收断言。
- 建立 `IpMiddlewareFastPathPolicy`：统一路径作用域判断、关闭状态缓存、无需 DB session 的短路条件、异常 fail-open/fail-closed 边界和 no-op 性能验收。

## 21. 回归验证体系

### 功能是什么

根目录存在 `stage7` 到 `stage36` 多个回归脚本，覆盖工具调用、Responses 管理、错误响应、真实上游请求次数、健康路由、故障切换延迟、可观测性、Embeddings、Chat 管理、Completions、Moderations、Files、模型兼容、provider payload adapter、缓存命中、路由策略、协议字段、Responses Chat Adapter、错误目录、内容防护、统一日志系统、usage 明细准确性和 IP 管理。

### 怎么实现

- 每个 `stage*_regression_check.py` 使用项目 `.venv`、FastAPI TestClient 或直接服务调用。
- 部分脚本 monkeypatch `ProxyService` 的上游发送函数，模拟 upstream 响应。
- 部分脚本创建临时数据并检查数据库日志或服务返回。
- 最新回归同步：`stage14` 明确端点协议支持依赖管理员配置而非探针缓存；`stage25` 增加候选耗尽等待、全局无限重试开关和不可恢复错误不重试等路由实时性检查，且 API Key 局部无限重试字段已从目标结构移除；`stage31` 断言 runtime 与 settings schema 的 Responses Chat Adapter 默认存储都是 `database`；`stage33` 增加可信检测三件套、内容防护规则筛选分页、页面错误态、危险操作确认/撤销、手动可信追溯、内容检测流量 `is_detection_traffic` 标记、模型级 content blocked 硬排除、标准信任 provider 也执行首段缓冲、浏览器拒绝接收外部 API Key、`safe_error` 独立错误码、URL 白名单 JSON 域名校验、外部检测地址长度限制、深层 JSON 扫描节点/深度保护、Chat 多模态 content 与 Responses summary/reasoning 扫描、review/record 不污染 provider 状态、高风险运行时隔离写入 `alert_events`、typed log 固定导出表头、内容防护 `matched_rule` 筛选、调度任务 `stale_running`、探针窗口 blocked 恢复细节、SSE/外链广告探针场景、内容防护前端保留勾选和提供商选择、`/trust-probe` 与 `/api/content-guard/precheck/trust-probe` 前后端接线、监控自动处置、Redis 锁不可用跳过，并开始引入 `ContentTrustProbeService` 与探针健康会话夹具来覆盖可信探针和 blocked 状态行为；`stage8` 更新日志中心页面标题、类型化日志按钮、用户日志详情、用户日志 API 隔离和协议字段夹具；`stage36` 新增 IP 管理模块回归基线。
- 最新测试入口变化：`tests/test_content_guard_regression.py` 已作为 pytest 包装入口直接调用 `stage33.main()`，说明高价值 stage 脚本开始进入标准 `tests/` 发现链路；但目前仍是单个大用例包装，尚未按规则引擎、运行时状态机、typed logging、前端 smoke、迁移空库等模块拆分。

### 优点

- 回归覆盖了大量真实历史问题，能防止关键链路退化。
- 不依赖完整外部上游即可验证大部分行为。
- 脚本命名按阶段记录项目演进脉络。
- `stage33` 已经有 pytest 包装入口，后续可以在不删除历史脚本的前提下逐步接入标准测试发现、CI 和 marker 分层。

### 缺点

- 回归脚本散落在根目录，未纳入 pytest 标准测试套件。
- 部分脚本对实现细节 monkeypatch 较多，架构重构时维护成本高。
- 缺少统一测试分层：单元、集成、端到端、性能压测之间边界不清。
- 当前 `tests/test_content_guard_regression.py` 只是调用 `stage33.main()` 的大用例，失败时仍可能需要在近两千行脚本中定位具体领域，尚未真正获得 pytest fixture、marker、分组运行和精确失败定位的收益。

### 改进建议

- 建立 `tests/` 目录，把阶段脚本逐步迁移为 pytest 用例。
- 保留 stage 脚本作为兼容入口，但内部调用 pytest marker。
- 按功能模块建立 fixture 和 mock upstream 工具。

## 22. 功能完整性结论

该项目已经实现一个功能非常密集的 OpenAI 兼容代理与提供商治理平台。功能层面覆盖面强，尤其在代理协议、provider 治理、日志计费、健康检查、内容防护、用户门户和部署运维方面已经远超最小可用产品。

当前主要风险不在“功能缺失”，而在“功能过度集中于少数超大模块”。如果继续在现有文件中累加功能，后续维护风险会快速上升，尤其是代理主链路、健康检查、日志计费、provider 管理和前端单文件控制器。
