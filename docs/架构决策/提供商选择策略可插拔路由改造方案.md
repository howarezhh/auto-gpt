# 提供商选择策略可插拔路由改造方案

摘要：本文给出在保持现有路由行为不变的前提下，将提供商选择逻辑重构为可插拔策略流水线的完整方案。关键词：提供商选择、RouterService、ProxyService、RoutePolicyContext、RouteRequest、RouteDecision、RoutePipeline、RouteFilter、RouteScorer、RouteOrderer、RouteDiagnoser、策略注册表、阶段化调试。

最后维护时间：2026-06-17

## 背景与目标

当前提供商选择已经集中在 `app/services/router_service.py`，并由 `app/services/proxy_service.py` 在正式请求中调用。现有实现具备统一入口、候选缓存、硬过滤、容量过滤、打分排序、不可用诊断和请求 trace，但策略仍主要通过 `RouterService` 大函数和 `ProxyService` 中的辅助逻辑串联。

本次改造目标不是改变业务行为，而是把现有能力重组为清晰、可测试、可插拔的路由模块：

- 现有对外 `/v1/*` 行为、错误格式、候选排序结果和日志字段保持兼容。
- 提供商选择统一收敛到路由模块接口，调用方不再直接拼装候选、过滤、排序、诊断和候选耗尽策略。
- 路由执行拆成 `context -> filters -> scorer -> orderer -> diagnoser` 流水线。
- 策略开关从散落参数收敛成明确的枚举、配置对象和策略注册表。
- 调试输出按阶段记录，每一阶段都能看到候选保留、剔除、加分、扣分和排序原因。
- `ProxyService` 只负责执行候选、写成功/失败结果和处理协议转发，不再负责路由策略判断。
- 每个流水线阶段都有独立测试，避免新增策略时影响其它阶段。

## 当前问题

### 统一封装已有但边界偏厚

`RouterService` 已经承担候选加载、硬过滤、容量过滤、打分、排序和诊断职责，但这些职责集中在一个服务类里。新增策略通常需要同时修改：

- 候选缓存 key。
- `_candidate_passes_runtime_filters`。
- `_route_score_breakdown`。
- `_balanced_order`。
- `diagnose_candidate_unavailability`。
- `ProxyService` 中 route trace、候选失败和候选耗尽等待逻辑。

这会导致新增策略的改动面偏大，也使测试只能围绕大函数做回归。

### 调用方仍直接依赖内部细节

以下模块仍直接使用路由模块内部能力或旧式聚合入口：

- `ProxyService` 调用 `RouterService.async_order_candidates`、`async_diagnose_candidate_unavailability`，并自行维护候选失败集合、route outage、候选耗尽等待和 trace 拼装。
- `ModelMappingService` 直接调用 `RouterService.diagnose_candidate_unavailability` 判断目标模型是否可路由。
- `UserPortalService` 直接调用 `RouterService.get_available_candidates` / `order_candidates` 生成候选预览。
- 测试直接断言 `_route_score_breakdown`、`_balanced_order`、`_append_recent_session_direct_candidate` 等内部方法。

这些依赖说明路由模块尚未形成稳定的公开接口层。

### 诊断结果不够阶段化

当前日志已有 `request_route_decision`、`top_candidates_json`、`score_breakdown` 和 `diagnostics_json`，能看到最终候选、分数和无候选原因。但它还不是严格的阶段化调试：

- 不能稳定区分每个候选在哪一个过滤器被排除。
- 分数项已可见，但没有统一的评分项来源、策略 ID 和版本。
- 排序原因只保留摘要，无法完整解释排序链路。
- 候选耗尽和 route outage 逻辑在 `ProxyService` 中生成，和候选诊断不属于同一个调试模型。

## 目标架构

### 模块边界

建议把路由模块从单文件服务演进为独立包：

```text
app/services/routing/
  __init__.py
  service.py              # 对外统一门面：RoutingService
  context.py              # RouteRequest、RoutePolicyContext、RouteRuntimeContext
  candidate.py            # RouteCandidate、RouteCandidateRef、RouteCandidateState
  decision.py             # RouteDecision、RouteDiagnostics、RouteStageTrace
  registry.py             # 策略注册表
  enums.py                # 策略枚举、阶段枚举、原因码枚举
  pipeline.py             # RoutePipeline 编排
  filters.py              # 内置过滤器
  scorers.py              # 内置评分器
  orderers.py             # 内置排序器
  diagnosers.py           # 诊断聚合器
  outage.py               # 候选耗尽、等待重试、route outage cache
  adapters.py             # 兼容旧 RouterService 的适配层
```

保留 `app/services/router_service.py` 作为兼容外壳，短期只转发到 `RoutingService`，长期逐步删除内部静态方法。

### 对外统一接口

其它模块只允许依赖以下稳定接口：

```python
class RoutingService:
    async def select_candidates(request: RouteRequest) -> RouteDecision: ...
    async def diagnose(request: RouteRequest) -> RouteDiagnostics: ...
    async def preview_candidates(request: RouteRequest) -> RouteDecision: ...
    def build_policy_context(auth_context: Any, setting: Any) -> RoutePolicyContext: ...
    def mark_candidate_failed(decision: RouteDecision, candidate_key: RouteCandidateKey, reason: str) -> RouteDecision: ...
    async def next_retry_plan(decision: RouteDecision, upstream_error: dict | None = None) -> RouteRetryPlan: ...
```

接口分工：

| 接口 | 使用方 | 职责 |
| --- | --- | --- |
| `select_candidates` | `ProxyService`、协议适配链路 | 返回已过滤、已评分、已排序、可执行的候选序列和完整阶段 trace |
| `diagnose` | 错误响应、模型映射、后台调试 | 返回结构化不可用诊断，不要求真实执行候选 |
| `preview_candidates` | 用户端自测、管理端候选预览 | 返回候选预览和阶段化说明，不触发执行租约 |
| `build_policy_context` | 鉴权层、缓存鉴权层 | 统一构造路由上下文 |
| `mark_candidate_failed` | `ProxyService` | 把执行失败回写到本轮决策状态，生成下一轮排除策略 |
| `next_retry_plan` | `ProxyService` | 统一判断候选耗尽是否可恢复、等待多久、是否写入 route outage cache |

### 流水线阶段

路由决策固定经过以下阶段：

```text
RouteRequest
  -> ContextBuilder
  -> CandidateProvider
  -> FilterPipeline
  -> ScoringPipeline
  -> OrderingPipeline
  -> DiagnosticsBuilder
  -> RouteDecision
```

| 阶段 | 输入 | 输出 | 可插拔点 |
| --- | --- | --- | --- |
| `context` | 鉴权结果、请求能力、全局设置、映射结果 | `RouteRuntimeContext` | `RouteContextEnricher` |
| `filters` | 原始候选、上下文 | 候选保留/剔除结果 | `RouteFilter` |
| `scorer` | 已保留候选、指标、容量、健康状态 | 分数项和总分 | `RouteScorer` |
| `orderer` | 已评分候选、会话粘性、失败候选 | 排序后的候选窗口 | `RouteOrderer` |
| `diagnoser` | 全阶段 trace、候选状态 | 诊断摘要、原因计数、错误详情 | `RouteDiagnoser` |

## 核心数据结构

### RouteRequest

`RouteRequest` 是所有路由调用的唯一输入对象，替代散落参数。

```python
@dataclass(slots=True)
class RouteRequest:
    requested_model: str | None
    selected_model: str | None
    endpoint_path: str
    public_endpoint_path: str
    request_kind: RouteRequestKind
    capabilities: RouteCapabilitySet
    policy_context: RoutePolicyContext
    sticky_key: str | None = None
    forced_provider_id: int | None = None
    excluded_candidate_keys: set[RouteCandidateKey] = field(default_factory=set)
    mapping_trace: dict[str, Any] | None = None
    debug_enabled: bool = True
```

现有 `require_vision`、`require_stream`、`require_tools`、`require_image_generation`、`require_chat_completions`、`require_responses`、`required_upstream_protocol_type` 应收敛进 `RouteCapabilitySet`。

### RouteDecision

`RouteDecision` 是路由模块的唯一输出对象。

```python
@dataclass(slots=True)
class RouteDecision:
    request: RouteRequest
    candidates: list[RouteCandidate]
    selected: RouteCandidate | None
    diagnostics: RouteDiagnostics
    stage_traces: list[RouteStageTrace]
    retry_plan: RouteRetryPlan | None = None
    cache_key: str | None = None
    policy_version: str = "route-pipeline-v1"
```

`ProxyService` 只读取 `decision.candidates` 并执行候选；日志、错误详情、候选耗尽判断都从 `decision` 或路由模块提供的序列化方法生成。

### RouteStageTrace

所有阶段调试输出使用统一结构：

```python
@dataclass(slots=True)
class RouteStageTrace:
    stage: RouteStage
    strategy_id: str
    result: RouteStageResult
    input_count: int
    output_count: int
    events: list[RouteCandidateTraceEvent]
    summary: dict[str, Any] = field(default_factory=dict)
```

候选级事件统一记录：

```python
@dataclass(slots=True)
class RouteCandidateTraceEvent:
    provider_id: int | None
    provider_model_id: int | None
    action: Literal["kept", "rejected", "scored", "ordered", "selected"]
    reason_code: str
    reason_label: str
    details: dict[str, Any] = field(default_factory=dict)
```

这样任意过滤器、评分器、排序器都能解释自己做了什么。

## 过滤器设计

### RouteFilter 接口

```python
class RouteFilter(Protocol):
    id: RouteFilterId

    def apply(self, candidates: list[RouteCandidate], context: RouteRuntimeContext) -> RouteFilterResult:
        ...
```

`RouteFilterResult` 必须包含：

- `kept_candidates`。
- `rejected_events`。
- `reason_counts`。
- `stage_summary`。

### 过滤器迁移映射

| 当前逻辑 | 新过滤器 |
| --- | --- |
| provider 启停、维护、熔断 | `ProviderAvailabilityFilter` |
| API Key 授权 | `ProviderAuthorizationFilter` |
| provider 端点协议 | `ProviderEndpointProtocolFilter` |
| provider 内容可信 | `ProviderTrustFilter` |
| provider_model 启停、全局模型、模型ID | `ProviderModelBasicFilter` |
| provider_model 端点协议 | `ProviderModelEndpointProtocolFilter` |
| 可用性门槛 | `HealthGateFilter` |
| stream、vision、tools、生图能力 | `CapabilityFilter` |
| 能力探针失败 | `CapabilityProbeFilter` |
| model 熔断与 half-open 探针 | `ModelCircuitFilter` |
| Redis 容量快照与容量上限 | `CapacityFilter` |

每个过滤器只做一类判断，并输出稳定原因码。诊断器不再重复实现过滤逻辑，而是消费过滤器产生的事件。

## 评分器设计

### RouteScorer 接口

```python
class RouteScorer(Protocol):
    id: str

    def score(self, candidate: RouteCandidate, context: RouteRuntimeContext) -> RouteScoreItem:
        ...
```

每个评分器只返回一个分项：

```python
@dataclass(slots=True)
class RouteScoreItem:
    scorer_id: str
    label: str
    value: float
    direction: Literal["bonus", "penalty"]
    reason_code: str
    details: dict[str, Any]
```

`RouteScoreAggregator` 汇总分项得到 `route_score`。现有 `score_breakdown` 变成兼容序列化字段，由 `RouteScoreItem` 自动生成。

### 现有评分保持不变

默认评分项必须逐项迁移，初始值与现有公式一致：

- 健康状态分。
- 模型优先级分。
- 提供商优先级分。
- 偏好提供商加分。
- 成功率分。
- 地区加分。
- 延迟惩罚。
- 流式 TTFB 惩罚。
- 饱和度惩罚。
- 近期错误惩罚。

迁移完成前后，同一测试数据的 `route_score` 和候选顺序必须一致。

## 排序器设计

### RouteOrderer 接口

```python
class RouteOrderer(Protocol):
    id: str

    def order(self, candidates: list[RouteCandidate], context: RouteRuntimeContext) -> RouteOrderResult:
        ...
```

默认排序器拆成四个可组合插件：

| 排序器 | 职责 |
| --- | --- |
| `RecentSessionOrderer` | 同一会话最近成功 provider/model 置前 |
| `FailedCandidateExclusionOrderer` | 排除本轮已失败 provider/model |
| `BalancedScoreOrderer` | 按分数桶、负载、偏好、优先级和稳定 ID 排序 |
| `CandidateWindowOrderer` | 按 `max_candidate_count + route_candidate_expand_count` 裁剪候选 |

排序器必须输出候选排名变化事件，记录 `previous_rank`、`new_rank`、`reason_code` 和排序键。

## 诊断器设计

### RouteDiagnoser 接口

```python
class RouteDiagnoser(Protocol):
    id: str

    def diagnose(self, context: RouteRuntimeContext, stage_traces: list[RouteStageTrace]) -> RouteDiagnostics:
        ...
```

诊断器不再重复扫描 provider/model，而是聚合流水线事件：

- 原始 provider/model 数量。
- 各过滤器输入/输出数量。
- 每个 reason_code 的计数。
- 代表性样本。
- 协议 mismatch 的 required/actual。
- 容量耗尽、熔断、可用性不可达等可恢复性判断。
- 对外错误详情所需字段。

这样 `diagnose` 和 `select_candidates` 使用同一套过滤器结果，避免正式路由和诊断口径漂移。

## ProxyService 调整

### 保留职责

`ProxyService` 继续负责：

- 解析外部请求体和协议入口。
- 调用模型映射。
- 调用 `RoutingService.select_candidates`。
- 按候选执行上游请求。
- 执行内容防护、伪成功响应识别、计费、日志落库和响应转换。
- 在候选执行失败时把失败原因回传给 `RoutingService`，请求下一轮决策或重试计划。

### 移出职责

以下逻辑应迁入路由模块：

- 候选失败集合的结构和排除规则。
- 候选耗尽是否可恢复。
- 候选耗尽等待重试计划。
- route outage cache key 与等待策略。
- route decision trace 拼装。
- top candidates 序列化。
- diagnostics_json 结构。
- `route_candidate_count`、`candidate_window_count` 等路由指标计算。

迁移后 `ProxyService` 的候选执行伪代码：

```python
decision = await RoutingService.select_candidates(route_request)
ProxyService.append_route_trace(trace, decision.to_trace_event())

while decision.should_wait_before_retry:
    await asyncio.sleep(decision.retry_plan.sleep_seconds)
    decision = await RoutingService.select_candidates(route_request.next_retry(decision))

for candidate in decision.candidates:
    result = await ProxyService.execute_candidate(candidate)
    if result.success:
        return result.response
    decision = RoutingService.mark_candidate_failed(decision, candidate.key, result.reason)

retry_plan = await RoutingService.next_retry_plan(decision, result.upstream_error)
if retry_plan.should_retry:
    ...
raise RoutingService.build_route_unavailable_error(decision)
```

## 调试输出标准

### 请求日志 trace

`request_route_decision` 事件保持兼容现有字段，同时新增阶段化字段：

```json
{
  "event_name": "request_route_decision",
  "route_policy": "availability_first",
  "policy_version": "route-pipeline-v1",
  "candidate_count": 3,
  "selected_provider_id": 1,
  "selected_provider_model_id": 11,
  "stage_traces_json": "[...]",
  "top_candidates_json": "[...]",
  "diagnostics_json": "{...}"
}
```

`stage_traces_json` 中至少包含：

- `context`：请求模型、选中模型、端点、能力集合、策略上下文摘要。
- `filters`：每个过滤器的输入数、输出数、剔除原因计数和样本。
- `scorer`：每个候选的评分项、加分/扣分来源、最终分。
- `orderer`：排序器序列、排名变化、最终候选窗口。
- `diagnoser`：最终摘要、可恢复性、错误分类建议。

### 前端与接口展示

管理端、用户端和日志详情页不需要理解每个策略实现，只展示路由模块序列化后的调试结果：

- 候选列表：排名、提供商、挂载模型、总分、选择原因。
- 过滤详情：按过滤器分组展示剔除数量与样本。
- 评分详情：按候选展示评分项。
- 候选耗尽：展示可恢复性、下一次重试等待和主要阻断原因。

## 缓存与兼容性

### 候选缓存

候选缓存 key 改由 `RouteRequest.cache_fingerprint()` 生成，包含：

- 请求模型和映射后模型。
- 端点路径和原生协议要求。
- 能力集合。
- 策略 ID 与策略版本。
- `RoutePolicyContext` 摘要。
- 候选数量窗口。
- 内容防护、可信策略、可用性门槛。

缓存值仍只保存 provider/model ID，命中后必须重新 hydrate 并经过运行时过滤器，保持现有安全语义。

### 兼容外壳

短期保留旧接口：

- `RouterService.get_available_candidates`。
- `RouterService.order_candidates` / `async_order_candidates`。
- `RouterService.diagnose_candidate_unavailability` / `async_diagnose_candidate_unavailability`。
- `RouterService._route_score_breakdown` 和 `_balanced_order` 仅供旧测试过渡使用。

这些方法内部调用 `RoutingService`，并标注为兼容层。新代码禁止继续调用这些内部方法。

## 迁移步骤

### 阶段一：建立数据结构与门面

目标：不改变现有行为，只新增路由包和兼容门面。

工作项：

- 新增 `app/services/routing/` 包。
- 定义 `RouteRequest`、`RouteDecision`、`RouteDiagnostics`、`RouteStageTrace`、策略枚举和注册表。
- `RoutingService.select_candidates` 通过路由策略注册表和阶段插件编排候选选择，并在兼容路径下复用 `RouterService` 的历史加载与辅助函数。
- `RoutingService.diagnose` 通过兼容诊断入口复用 `RouteFilterChain` 过滤事件口径，并由 `StageTraceDiagnoser` 聚合阶段摘要。
- 给 `RouteDecision` 增加兼容序列化方法，输出当前 `top_candidates_json` 和 `diagnostics_json` 等字段。

验收：

- 所有现有路由测试通过。
- `ProxyService` 尚未大改，但可以通过新门面拿到等价候选。

### 阶段二：迁移过滤器

目标：把 `_candidate_passes_runtime_filters` 拆成过滤器链。

工作项：

- 实现 provider 基础过滤器、授权过滤器、协议过滤器、内容可信过滤器、模型基础过滤器、能力过滤器、能力探针过滤器、熔断过滤器。
- 过滤器输出 `RouteCandidateTraceEvent`。
- `diagnose` 改为复用过滤器事件，不再重复手写一套过滤逻辑。
- 保持 reason_code 与现有诊断原因兼容。

验收：

- 同一 fixture 下，旧 `_candidate_passes_runtime_filters` 和新过滤器链结果一致。
- 无候选诊断 `reason_counts` 与现有输出一致或仅新增兼容字段。

### 阶段三：迁移评分器与排序器

目标：把 `_route_score_breakdown` 和 `_balanced_order` 拆成评分器、排序器。

工作项：

- 实现所有现有评分项。
- 实现 `RecentSessionOrderer`、`BalancedScoreOrderer`、`FailedCandidateExclusionOrderer`、`CandidateWindowOrderer`。
- `score_breakdown` 由评分器输出自动生成。
- 排序阶段记录排名变化和排序键。

验收：

- 同一候选集合下，新旧 `route_score` 完全一致。
- 同一候选集合下，新旧排序完全一致。
- 最近会话粘性、偏好提供商、容量负载、失败候选排除用例全部通过。

### 阶段四：迁移候选耗尽与 route outage

目标：把 `ProxyService` 中的路由恢复性判断迁入路由模块。

工作项：

- 新增 `routing/outage.py`。
- 迁移 `_should_retry_route_diagnostics`。
- 迁移 `_route_exhausted_retry_wait_plan`。
- 迁移 `_remember_route_outage` 与 `_maybe_wait_for_route_outage`。
- `RoutingService.next_retry_plan` 对外提供统一重试计划。

验收：

- 候选容量满、容量快照不可用、熔断、模型未挂载、协议不支持等场景的可恢复性判断保持不变。
- route outage cache key 与等待行为保持兼容。

### 阶段五：收敛 ProxyService 依赖

目标：让 `ProxyService` 只执行候选。

工作项：

- `ProxyService` 不再直接调用 `RouterService.async_order_candidates`。
- `ProxyService` 不再直接调用 `RouterService.async_diagnose_candidate_unavailability`。
- `ProxyService` 不再拼装 route decision trace，而是消费 `RouteDecision.to_trace_event()`。
- 候选失败通过 `RoutingService.mark_candidate_failed` 更新决策状态。
- 模型映射失败重试仍由 `ProxyService` 编排，但目标模型可路由性检查调用 `RoutingService.diagnose`。

验收：

- `rg "RouterService\\." app/services/proxy_service.py` 只允许出现在兼容过渡注释或完全不存在。
- `ProxyService` 中不再存在 route outage、candidate trace serialization、candidate failed exclusion 等路由策略函数。

### 阶段六：替换其它调用方

目标：其它模块只调用路由公开接口。

工作项：

- `ModelMappingService` 改用 `RoutingService.diagnose`。
- `UserPortalService` 改用 `RoutingService.preview_candidates`。
- `ResponsesChatAdapterService` 只接收/传递 `RoutePolicyContext`，不依赖路由内部实现。
- 测试从内部方法断言迁移为阶段插件和公开接口断言。

验收：

- `rg "RouterService\\." app/services` 只保留 `routing/adapters.py` 或 `router_service.py` 兼容层。
- 新业务代码禁止直接调用旧 `RouterService` 内部方法。

### 阶段七：清理兼容层

目标：完成架构切换。

工作项：

- 删除或收缩旧 `RouterService` 内部静态方法。
- 更新 `docs/模块/提供商选择策略模块.md` 的代码地图和维护要求。
- 更新测试文件名和测试说明。
- 若正式移除旧接口，再同步清理旧调用方和旧测试。

验收：

- 路由模块公开接口稳定。
- 文档、测试、日志字段和代码边界一致。

## 验收标准

### 行为验收

- 现有正式代理请求返回行为不变。
- OpenAI 兼容、Gemini 原生、Claude 原生入口候选约束不变。
- 原有 `route_score` 和候选排序在默认策略下不变。
- 原有错误响应结构和 `trace_id` 不变。
- 原有请求日志核心字段不删除，只新增阶段化字段。

### 架构验收

- 路由模块提供唯一稳定门面 `RoutingService`。
- `ProxyService` 不再包含路由策略判断。
- `ModelMappingService`、`UserPortalService` 等模块不再直接使用路由内部方法。
- 新增策略只需要注册过滤器、评分器、排序器或诊断器，不需要修改主流程。
- 新增诊断原因只需要在对应插件声明，并由诊断器统一聚合。

### 调试验收

- 每个候选能看到被哪个阶段保留或剔除。
- 每个评分项能看到来源、数值、加分/扣分方向。
- 每次排序能看到排序策略和排名变化。
- 候选耗尽能看到是否可恢复、为什么可恢复或不可恢复、下一次重试计划。

## 风险与控制

| 风险 | 控制方式 |
| --- | --- |
| 默认候选顺序变化 | 双轨等价测试，迁移期保留旧实现对比 |
| 诊断原因漂移 | 过滤器事件作为唯一诊断来源，reason_code 兼容旧值 |
| `ProxyService` 改动面过大 | 先门面适配，再分阶段迁移，避免一次性重写 |
| 日志字段兼容问题 | 旧字段保留，新阶段 trace 作为新增字段 |
| 策略注册过度抽象 | 只注册现有真实策略，不预置无实现策略 |
| 容量和 Redis 行为变化 | 容量过滤与租约保持分离，正式租约仍在执行前获取 |

## 不纳入本次改造范围

- 不调整 provider/model 数据库字段。
- 不改变计费、余额预占、内容防护、伪成功响应检测的业务结果。
- 不新增新的路由策略默认值。
- 不改变管理端前端交互，除非后续要展示阶段化 trace。
- 不改变对外 API 协议和错误对象结构。
