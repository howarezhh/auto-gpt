# 提供商选择策略模块

摘要：本文记录对外代理请求进入系统后，如何通过 `RoutingService` 统一门面和 `context -> filters -> scorer -> orderer -> diagnoser` 纯路由内核插件流水线，从 API Key 授权范围、模型映射、挂载能力、可用性/熔断、内容可信、容量、路由得分和重试策略中选择最终提供商与挂载模型。关键词：`RoutingService`、`RoutePipeline`、`RouteRequest`、`RouteDecision`、`RoutePolicyContext`、`RouteCandidate`、`RouteFilterChain`、`StageTraceDiagnoser`、`route_strategy`、`availability_first`、`latency_first`、`capacity_avoidance`、`ProxyService`、`ModelMappingService`、`ProviderCapacityService`、`ProviderHealthStateService`、`FixedSuccessResponseService`、`ContentTrustProbeService`、`allowed_provider_ids`、`preferred_provider_ids`、`route_health_gate_mode`、`route_score`、`route_exhausted_retry`、`stage_traces_json`。

最后维护时间：2026-06-19

## 模块职责与边界

提供商选择策略模块的职责是为一次正式代理请求选出可尝试的 `Provider + ProviderModel` 候选序列，并在候选失败、候选耗尽或模型映射目标失败时给出可追踪、可重试或可拒绝的处理结果。

本模块不负责提供商配置持久化、模型挂载新增、可用性探针执行、内容防护探针执行、计费结算或请求协议适配的具体实现；但它会读取这些模块沉淀的状态作为路由约束。

任何改动以下代码、配置或跨模块契约时，必须同步检查并更新本文：

- `app/services/routing/`
- `app/services/proxy_service.py` 中候选调用、候选耗尽、同提供商重试、模型映射失败重试和 route outage 逻辑
- `app/services/model_mapping_service.py`
- `app/services/api_key_service.py` 与 `app/services/api_key_auth_cache.py` 中 `RoutePolicyContext` 构建逻辑
- `app/services/provider_capacity_service.py`
- `app/services/provider_health_state_service.py`
- `app/services/content_trust_probe_service.py`
- `app/schemas/setting.py` 与 `app/services/setting_service.py` 中路由设置字段
- 影响提供商选择的模型权限、端点协议、能力字段、可用性字段、熔断字段、内容完整性字段、容量字段和请求日志路由指标；当前数据库兼容字段仍命名为 `health_status`

## 决策输入

一次路由决策至少由以下输入共同决定：

- 请求模型ID：外部请求体中的 `model`，进入项目后视为平台模型ID，经模型映射后可能变成目标模型ID。
- 请求形态：非流式或流式、图片输入、工具调用、生图、Chat Completions、Responses、Gemini 原生或 Claude 原生。
- API Key 策略：授权提供商集合、模型白名单、偏好提供商、偏好地区、延迟偏好和成功率偏好。
- 全局路由设置：`route_strategy`、`trusted_providers_only`、`route_health_gate_mode`、`max_candidate_count`、`route_candidate_expand_count`、候选缓存 TTL、候选耗尽重试窗口。
- Provider 状态：启停、维护模式、熔断、协议类型、内容完整性、信任等级、优先级、容量限制、地区标签。
- ProviderModel 状态：启停、平台模型ID、上游模型ID、协议类型、能力、可用性、熔断、优先级、内容完整性。
- 运行时状态：Redis 中 provider/model 可用性、短窗口成功率/失败率、EWMA 延迟、EWMA 首 token、容量快照。
- 历史指标：`request_logs` 近 5 分钟路由指标，包括成功率、失败率和平均延迟。
- 会话粘性：同一会话最近成功使用的目标模型ID、提供商和挂载模型。

## 总流程

1. 对外入口完成 Bearer API Key 鉴权，`ApiKeyService` 校验密钥启用、过期、IP/端点限制、用户额度和授权提供商。
2. 鉴权层生成 `RoutePolicyContext`：`allowed_provider_ids` 来自 API Key 绑定，`route_strategy`、可信策略和可用性门槛来自全局设置，偏好提供商/地区及偏好权重来自 API Key。
3. `ProxyService` 解析请求能力和入口协议，补充内容防护路由策略，并校验请求模型ID是否在 API Key 模型权限内。
4. `ModelMappingService` 对源模型ID执行映射选择；若没有可用目标模型ID，保留源模型ID并在 trace 中记录 `model_mapping_no_available_target`。
5. `ProxyService` 检查模型 token 限制、长输出限制、route outage 缓存。
6. `RoutingService.select_candidates` 接收 `RouteRequest`，通过路由策略注册表执行硬过滤、容量过滤、打分、排序和阶段 trace 生成。
7. 若有候选，`ProxyService` 按排序依次尝试候选；每次尝试前做余额预检查，并通过 `ProviderCapacityService.async_lease` 获取容量租约。
8. 上游调用成功后执行内容防护、伪成功固定文本检测、日志、计费和运行时可用性更新；失败时记录候选失败并按同提供商重试、候选切换、模型映射 failover 或候选耗尽重试处理。
9. 每次内部提供商尝试、失败、同提供商等待、候选耗尽等待和候选切换都必须写入请求子事件时间线；主日志保持一次外部请求一条，并在等待或重试期间维持 `request_status='请求中'`。
10. 若无候选，`RoutingService.diagnose` 生成结构化诊断，`ProxyService` 按诊断和 `routing/outage.py` 的等待计划决定是否等待重试、尝试下一个映射目标或返回结构化错误。

## RoutePolicyContext

`RoutePolicyContext` 是跨鉴权、映射、路由和代理执行的策略载体：

| 字段 | 含义 |
| --- | --- |
| `allowed_provider_ids` | API Key 被授权使用的提供商集合；为空时鉴权直接拒绝 |
| `forced_provider_id` | 内部调试或受控链路强制指定的提供商；对外 `/v1/*` 禁止暴露此能力 |
| `preferred_provider_ids` | 偏好提供商，进入打分时加 `preferred_provider_bonus` |
| `preferred_region_tags` | 偏好地区，命中后加地区分 |
| `latency_bias` | 延迟惩罚倍率 |
| `success_rate_bias` | 成功率得分倍率 |
| `require_trusted_provider` | 是否只允许官方/可信提供商 |
| `content_guard_required` | 内容防护路由是否必需 |
| `health_gate_mode` | `permissive`、`healthy_only`、`trusted_healthy` 三档可用性门槛；字段名为兼容历史保留 |
| `route_strategy` | 管理员全局主路由策略，允许 `availability_first`、`latency_first`、`capacity_avoidance`；默认 `availability_first` |

缓存鉴权 `ApiKeyAuthCache` 必须重建同一语义的 `RoutePolicyContext`，避免缓存命中后绕过最新全局可信策略和可用性门槛。

## RouteRequest 与 RouteDecision

新代码必须优先通过 `RoutingService` 的公开接口调用路由模块，禁止在业务调用方继续直接拼装候选、过滤、排序或诊断细节。

| 对象 | 作用 |
| --- | --- |
| `RouteCapabilitySet` | 收敛 `vision`、`stream`、`tools`、`image_generation`、Chat/Responses 入口和原生上游协议要求 |
| `RouteRequest` | 候选选择、候选预览和诊断的唯一输入对象，包含请求模型ID、映射后模型ID、端点路径、策略上下文、失败候选集合和策略 ID |
| `RouteDecision` | 路由模块输出对象，包含可执行候选序列、选中候选、诊断、缓存指纹、策略版本和阶段 trace |
| `RouteStageTrace` | 统一记录 `context`、`filters`、`scorer`、`orderer`、`diagnoser` 各阶段输入数、输出数、事件和摘要 |
| `RouteCandidateTraceEvent` | 记录单个候选在某阶段被保留、剔除、评分、排序或选中的原因、标签和调试细节 |

`ProxyService` 只消费 `RouteDecision.candidates` 执行上游尝试，并使用 `RouteDecision.to_trace_payload()` / `stage_traces_payload()` 写入请求日志；候选失败集合、候选 key 序列化、route outage 等路由策略相关工具由 `RoutingService` 提供。

## 插件流水线

默认策略为 `availability_first`，管理员可在全局路由设置中切换为 `latency_first` 或 `capacity_avoidance`。三类策略均注册在 `RouteStrategyRegistry` 中，并复用同一硬过滤链，差异只体现在评分权重和排序输入。

| 阶段 | 主要实现 | 输出 |
| --- | --- | --- |
| `context` | `RouteRequest`、`RouteCapabilitySet`、`RouteRuntimeContext` | 请求模型ID、端点、能力集合、策略上下文摘要 |
| `filters` | `RouteFilterChain`、`CapacityFilter` | 候选保留/剔除结果、`reason_counts`、候选级 `rejected` 事件 |
| `scorer` | `AvailabilityFirstScorer`、`LatencyFirstScorer`、`CapacityAvoidanceScorer` | 评分项和最终分；低延迟优先放大延迟/首 token 惩罚，容量避让放大容量饱和惩罚 |
| `orderer` | `RecentSessionOrderer`、`BalancedScoreOrderer`、`FailedCandidateExclusionOrderer`、`CandidateWindowOrderer` | 排名变化、失败候选排除数、最终候选窗口 |
| `diagnoser` | `StageTraceDiagnoser` | 聚合阶段 trace、原因计数、诊断样本和兼容诊断 payload |

新增策略时应优先新增或组合过滤器、评分器、排序器、诊断器，并在注册表中登记；不得把新策略散落到 `ProxyService` 或调用方里。

## 模型映射阶段

`ModelMappingService.resolve_for_request` 在候选提供商排序之前执行。当前实现会：

- 跳过未启用映射或无目标的映射。
- 排除本轮 failover 已尝试过的目标模型ID。
- 校验 API Key 是否允许目标模型ID。
- 校验目标模型ID对应的模型目录是否存在且全局启用。
- 校验目标模型ID级能力和入口协议是否明显不匹配。
- 调用 `RoutingService.diagnose` 预判该目标是否存在最终候选；无最终候选时记录 `target_route_unavailable`。
- 若同一会话最近成功目标仍在可用目标中，优先复用；否则按映射目标配置顺序选择。

映射阶段只选择目标模型ID；真正的 provider/model 候选排序、容量租约、可用性门槛、内容可信硬排除和上游尝试仍由后续路由阶段执行。若目标模型ID上游失败且错误可恢复，`ProxyService` 可尝试下一个映射目标。

## 候选硬过滤

`RouteFilterChain` 是正式候选的硬过滤插件链，由纯路由内核直接调用。硬过滤不打分，任何一项不满足都会排除候选，并输出稳定的 `reason_code` 与候选级 trace 事件。

| 插件 | 排除条件 |
| --- | --- |
| `ProviderAvailabilityFilter` | `provider.enabled` 为假、provider 熔断或维护模式 |
| `ProviderContentTrustFilter` | 提供商被 `blocked`、内容完整性 `blocked`、评分过低，或要求可信但非官方/可信 |
| `ProviderAuthorizationFilter` | `allowed_provider_ids` 不包含该提供商 |
| `ProviderEndpointProtocolFilter` | 请求入口或原生协议要求与提供商协议能力不匹配 |
| `ProviderModelBasicFilter` | 挂载禁用、挂载内容策略阻断、模型全局禁用或请求模型ID不匹配 |
| `ProviderModelEndpointProtocolFilter` | Chat/Responses/原生协议要求与挂载协议能力不匹配 |
| `HealthGateFilter` | `healthy_only` 要求 provider 和 model 均为 `healthy`；`trusted_healthy` 还要求官方/可信 |
| `CapabilityFilter` | 流式、vision、tools、image generation、Chat/Responses 能力不满足 |
| `CapabilityProbeFilter` | vision/tools/image generation 最近探针明确失败 |
| `ModelCircuitFilter` | 挂载熔断未到恢复探测时间，或正式路由抢占 half-open 探针名额失败 |
| `CapacityFilter` | 容量快照缺失或 provider 活跃请求、活跃流、QPS、RPM 已达上限 |

## 端点协议规则

原生协议要求通过 `required_upstream_protocol_type` 下沉到路由层。`gemini` 只允许选择实际原生协议为 `gemini` 的挂载；`claude_messages` 只允许选择实际原生协议为 `claude_messages` 的挂载。

OpenAI 兼容入口请求 Chat/Responses 时，Gemini/Claude 原生挂载可以进入候选，前提是请求入口可由原生适配层转换；后续由协议适配层负责请求体和响应体转换。

OpenAI 兼容挂载若只声明 Chat，则不能承载 Responses；若只声明 Responses，则不能承载 Chat；`both` 可以承载两类入口。

## 内容可信与可用性门槛

内容可信硬排除由 `ContentTrustProbeService.get_trust_decision_for_route` 决定：

- `trust_level == "blocked"`：排除。
- `content_integrity_status == "blocked"`：排除。
- `content_integrity_score <= 20`：排除。
- `require_trusted_provider == true` 且提供商非 `official` / `trusted`：排除。
- 挂载内容完整性 `blocked` 或评分过低：排除。

可用性门槛由 `route_health_gate_mode` 决定：

- `permissive`：不因可用性状态直接排除，仍会在打分中体现可用性差异。
- `healthy_only`：只允许 provider 和 model 有效可用性状态均为 `healthy` / `available`。
- `trusted_healthy`：在 `healthy_only` 基础上要求 provider 为 `official` 或 `trusted`。

有效可用性状态优先读取 `ProviderHealthStateService` 的运行时状态，缺失时回落到数据库字段。API 兼容返回 `db_health`、`runtime_health`、`effective_health`，并新增 `db_availability`、`runtime_availability`、`effective_availability`、`availability_status`。

管理端对象目录、详情和模型挂载摘要读取运行时可用性时，若 Redis 最近连接失败，应在短冷却期内跳过运行时状态读取并回落到数据库状态，避免管理页面被 Redis socket 超时拖死。该降级只适用于展示与序列化读路径，不改变正式代理请求的可用性门槛判断原则。

## 伪成功固定文本检测

部分中转站在模型不可用时会以 HTTP 200 返回固定失败文本，例如“当前模型暂不可用，请稍后再试。”。这类响应不能记录为正常成功，也不能等下一次请求才生效。

- `FixedSuccessResponseService` 按 provider/model 缓存最近两条成功响应的归一化文本、请求指纹、响应指纹和摘要。
- 只有归一化文本长度在 `6` 到 `1200` 字符之间时才参与比较；归一化会做 Unicode NFKC、空白合并、去首尾空白和小写化。
- 当相邻两条不同请求的响应文本相似度达到 `0.95` 或以上时，记录 `fixed_success_response_detected`；相同请求指纹的重放不会触发。
- 固定文本命中后不会立刻标记异常，必须先触发 `ContentGuardProbeService.probe_fixed_answer` 固定答案完整性探针；该探针要求上游只输出 `AOTU_CONTENT_GUARD_OK`，用于确认 provider/model 仍能按新请求生成指定内容。
- 固定答案确认必须遵守统一探针限频。若首次确认因 `probe_rate_limited` 未发起真实上游探针，`ProxyService` 仅对该固定答案确认按 `2s`、`5s`、`10s` 依次重试；任一重试探针通过即视为本次固定文本命中未确认异常，清理该 provider/model 的固定文本样本，不标记异常，不切换候选。
- 若固定答案探针真实执行但失败、返回内容不匹配，或首次及 `2s/5s/10s` 重试全部仍为限频结果，则确认该 provider/model 存在伪成功风险，写入 `health_status='unhealthy'`、`circuit_state='open'`、`last_error='fixed_success_response_detected'`。
- 非流式响应在返回用户前命中且固定答案确认失败时，`ProxyService` 将当前候选视为可重试上游故障并立即切换下一个候选；固定答案确认通过时，当前响应按正常成功链路记录。
- 流式响应若在首段缓冲期命中且固定答案确认失败，在下发前切换候选；确认通过则继续使用当前流。若已经下发给下游，确认失败只标记该 provider/model 后续不可路由，并在请求日志 trace 中记录 `downstream_already_started=true`；确认通过则保留正常成功日志。
- 该能力不新增 `provider_models.route_status` 持久化字段；后台展示的 `route_availability_status` 是由启停、可用性、熔断、内容完整性和优先级派生出的展示字段。

## 容量过滤与租约

候选加载阶段会批量读取 provider 容量快照。容量过滤发生在硬过滤之后、排序之前，并由 `CapacityFilter` 统一输出 `capacity_snapshot_unavailable`、`provider_capacity_exceeded` 等原因码和候选级 trace 事件：

- 活跃请求数达到 `max_active_requests` 时排除。
- 流式请求活跃流数达到 `max_active_streams` 时排除。
- 当前秒 QPS 达到 `max_qps` 时排除。
- 当前分钟 RPM 达到 `max_rpm` 时排除。

正式上游调用前必须通过 `ProviderCapacityService.async_lease` 获取租约。即使候选排序时容量可用，执行时仍可能因并发变化被租约拒绝；此时应进入候选失败和后续重试/切换逻辑。

容量状态依赖 Redis。容量服务不可用且不允许本地兜底时，代理返回容量服务不可用错误，而不是把它误判为模型不可用。

管理端对象目录、详情和模型挂载摘要读取容量快照时，若 Redis 最近连接失败，应在短冷却期内快速降级为空容量快照或展示缺省值，禁止因逐个 provider 读取容量状态导致目录接口超时。正式代理请求执行前的容量租约仍必须依赖 Redis；Redis 不可用时应返回容量服务不可用或进入可恢复失败处理，不得静默绕过容量保护。

## 候选缓存

候选缓存 key 包含以下维度：

- 请求模型ID。
- vision、stream、tools、image generation 能力要求。
- Chat/Responses 端点要求。
- 原生上游协议要求。
- 内容防护总开关。
- 管理员全局主路由策略 `route_strategy`。
- `allowed_provider_ids`、`preferred_provider_ids`、`preferred_region_tags` 摘要。
- 最大候选数、候选扩展数。
- 延迟偏好、成功率偏好。
- 可信提供商要求、内容防护要求、可用性门槛模式。

候选缓存只保存 provider/model ID，命中后仍会重新 hydrate 并再次检查运行时过滤，避免直接复用过期对象。候选缓存 TTL 默认 10 秒，最大 60 秒。

## 打分公式

`AvailabilityFirstScorer` 对每个候选计算基础分项：

| 分项 | 规则 |
| --- | --- |
| 可用性分 | `healthy=100`、`degraded=60`、`unknown=55`、`unhealthy=0`；`half_open` 最高 35，`open` 为 0 |
| 模型优先级分 | `max(0, 30 - provider_model.priority)` |
| 提供商优先级分 | `max(0, 20 - provider.priority)` |
| 偏好提供商加分 | provider ID 在 `preferred_provider_ids` 中加 35 |
| 成功率分 | `success_rate * 40 * success_rate_bias` |
| 地区加分 | provider `region_tag` 命中偏好地区加 20 |
| 延迟惩罚 | `min(30, latency_ms / 100) * latency_bias` |
| 流式 TTFB 惩罚 | 流式请求时 `min(25, ewma_ttfb_ms / 100)`；该运行态 TTFB 取提供商实际尝试内的 `first_token_latency_ms`，不使用包含前置路由、失败候选和重试等待的端到端首包 |
| 饱和度惩罚 | 基于容量快照最大使用率，最高 40 |
| 近期错误惩罚 | `min(45, failure_rate * 100)` |

最终分数为各正向分相加后减去惩罚项。分数只决定排序，不绕过硬过滤。

`LatencyFirstScorer` 复用可用性优先基础分项，并将延迟惩罚与流式首 token 惩罚按策略权重放大，用于优先选择近期响应更快的候选。`CapacityAvoidanceScorer` 复用基础分项，并将容量饱和惩罚按策略权重放大，用于主动避开接近容量上限的提供商。两类新增策略都不改变硬过滤条件，也不允许绕过容量租约。

## 排序规则

`BalancedScoreOrderer` 的稳定排序键为：

1. 路由得分桶降序。
2. 负载因子升序。
3. 偏好提供商加分降序。
4. 原始路由得分降序。
5. 挂载优先级升序。
6. 提供商优先级升序。
7. 提供商 ID 升序。
8. 挂载 ID 升序。

同一会话最近成功使用的 provider/model 若仍满足硬过滤、容量过滤和排除列表，会由 `RecentSessionOrderer` 优先放到前面；失败后该候选会加入本轮失败集合，并由 `FailedCandidateExclusionOrderer` 排除，避免同轮无限重复尝试。

## 候选数量

最终候选数量由 `max_candidate_count + route_candidate_expand_count` 决定，并受实际候选数限制。默认 `max_candidate_count=10`，`route_candidate_expand_count=5`。扩展候选用于提供切换空间，避免前几个候选临时失败后立刻耗尽。

## 代理执行与失败切换

非流式与流式代理都按候选序列逐个尝试。每个候选执行时：

1. 做账户余额预检查。
2. 获取 provider 容量租约。
3. 按入口协议与挂载协议转发上游。
4. 成功后执行内容防护、usage 提取、日志写入、计费和运行时状态更新。
5. 失败后根据错误类型、状态码、内容防护结果和 retry policy 判断是否同 provider 重试、切换候选或结束；每次真实上游尝试的终态必须写入 provider attempt 子事件，包含提供商、挂载模型、状态码、错误码、错误说明、是否可重试、路由轮次和同 provider 重试序号。`connecting`、`same_provider_retry_wait`、`stream_opened`、`first_chunk_received`、`finished` 等连接进度或等待节点只能作为 trace 过程信息，禁止计入 provider attempt 次数。

同一 provider 的即时重试次数由 provider 自身最大重试配置决定，等待策略支持 `Retry-After` 和指数退避抖动。等待期间主日志保持 `请求中`，子事件记录 `retry_wait_seconds` 和 `retry_wait_plan_json`。候选失败会记录到 `failed_candidate_keys`，后续候选排序会排除本轮已失败 provider/model。

流式请求一旦已经向下游发送 SSE 数据，内容防护命中或上游错误不能切换到其它 provider 拼接内容，只能发送标准错误事件并以 `[DONE]` 收尾。未发送任何下游数据前，允许按候选切换逻辑更换 provider。

请求日志主表中的 `duration_ms` 表示端到端总耗时：从应用接收到外部客户端请求开始，到完整响应结束或终态错误写入为止，包含请求体读取、鉴权、路由、余额预检、候选失败、同 provider 重试等待、模型映射 failover、内容防护和响应转换等前后置时间。`upstream_duration_ms` 表示最终记录到主日志的提供商请求耗时；成功请求通常为最终成功上游尝试耗时，失败请求优先取最近一次 provider attempt 耗时。`latency_ms` 继续保留为提供商运行态和路由评分使用的上游延迟，禁止改作端到端耗时。

流式请求日志中 `ttfb_ms` 表示端到端首包耗时：从外部请求进入应用层开始，到项目实际读到第一段上游流数据为止，包含请求体读取、鉴权、路由、余额预检、候选失败、同 provider 重试等待和模型映射 failover 等前置时间。`first_token_latency_ms` 表示最终成功上游尝试内的首 token / 首 chunk 延迟，用于提供商运行态和路由评分，避免把其它候选失败或等待时间计入成功提供商性能。TPS 按 `completion_tokens * 1000 / (duration_ms - ttfb_ms)` 计算；当没有有效首包或分母不可用时，才回退使用 `duration_ms`。

内容防护运行时检测必须只扫描用户可见输出文本、工具调用参数和明确需要治理的输出字段，禁止把 `id`、`object`、`model`、`finish_reason`、`usage`、`system_fingerprint` 等协议元数据当作普通文本扫描。URL 检测默认关闭；只有管理员显式开启 `content_guard_url_check_enabled` 后，才允许因未授权外链、短链或外链广告意图命中异常外链规则。Markdown fenced code block 中的示例 URL、HTML/CSS/JS 资源引用和 CDN 地址不得按异常外链规则命中。

## 候选耗尽与等待重试

无候选或所有候选失败后，`RoutingService.next_retry_plan` / `RouteOutageService` 会区分可恢复与不可恢复，`ProxyService` 只负责按重试计划等待或返回错误：

- 没有任何匹配模型挂载：不可恢复，直接返回模型不可用。
- 硬过滤前存在候选但容量过滤后为 0：可恢复，可等待容量释放。
- 全部失败原因都是授权、模型停用、全局停用、协议不支持、能力不支持等：不可恢复。
- 存在容量满、容量快照不可用、provider/model 熔断、model unhealthy 等：可恢复。
- 上游错误若分类为 recoverable，也可进入 route exhausted retry。

等待重试采用 `(1, 2, 5, 10, 15, 30)` 秒退避并带抖动，若上游错误提供 `Retry-After` 则优先使用。普通模式最大等待窗口由 `route_exhausted_retry_max_wait_seconds` 控制，默认 600 秒，最大 600 秒；`route_exhausted_retry_infinite_enabled` 开启后不受最大窗口限制。每个候选耗尽等待窗口必须写入 `request_route_decision_events`，其中 `selection_guard` 为 `route_exhausted_wait_retry`，并记录 `retry_wait_ms`、`retry_wait_plan_json`、诊断摘要和失败候选统计。

route outage cache 会把同一端点、模型、能力、强制/授权 provider 和内容可信策略下的短期耗尽结果缓存起来，后续同路由请求会先等待缓存中的下一次重试时间，减少重复打穿。

流式请求在候选耗尽、等待重试窗口结束或其它最终错误发生时，若尚未建立下游 SSE 内容流，入口层也必须返回 `event: error` 错误事件并以 `data: [DONE]` 收尾，确保客户端收到明确终止信息；若服务器仍在等待重试窗口内，则保持连接等待，不提前发送终止事件。

## 诊断输出

无候选诊断由 `RoutingService.diagnose` 与 `StageTraceDiagnoser` 统一生成；诊断器消费过滤插件产生的事件和阶段摘要，避免正式路由与诊断扫描各写一套判断逻辑。诊断必须保留：

- 请求模型ID、请求能力、端点协议、原生协议要求、可用性门槛。
- provider 总数、扫描数、挂载总数、匹配模型挂载数。
- 容量前候选数和最终候选数。
- `reason_counts` 和样本。
- 协议不匹配时的 required/actual protocol。
- forced provider 不存在、provider 未授权、模型未挂载、能力不支持、容量不足、熔断、内容可信阻断等具体原因。
- `stage_traces_json` 中的过滤、评分、排序、诊断阶段事件，便于定位候选在哪个插件被排除或排序。

对外错误详情必须结构化返回端点、能力和诊断样本，禁止只返回泛化 `model_not_available` 让调用方猜测。

## 典型边缘场景

| 场景 | 处理规则 |
| --- | --- |
| API Key 没有授权 provider | 鉴权阶段返回 `no_authorized_provider` |
| API Key 不允许请求模型ID | 代理阶段返回 `model_not_allowed` 并写失败日志 |
| 强制 provider 不存在 | 诊断记录 `forced_provider_not_found` |
| 强制 provider 存在但不满足约束 | 只在该 provider 范围内诊断失败原因 |
| 模型目录未启用 | 挂载被 `model_globally_disabled` 排除 |
| 模型未挂载到任何 provider | `matching_model_mount_count=0`，不可恢复 |
| Provider 维护中 | 正式路由排除；自动探针也不得污染状态 |
| Provider 熔断 | provider 级直接排除，等待恢复或人工处理 |
| Model 熔断 | 到恢复探测时间后仅允许抢占一个 half-open 探针名额 |
| 可用性未知 | `permissive` 下可参与但可用性分较低；严格可用性门槛下排除 |
| 内容完整性 blocked | provider 或 model 被硬排除 |
| 只允许可信 provider | 非 official/trusted provider 被硬排除 |
| Chat 请求命中只支持 Responses 的 OpenAI 兼容挂载 | 排除并记录 `chat_not_supported` |
| Gemini/Claude 原生入口命中 OpenAI 兼容挂载 | 原生协议不匹配，排除 |
| OpenAI 兼容入口请求 Gemini/Claude 模型 | 原生挂载可作为候选，由适配层转换 |
| 能力探针明确失败 | 对应能力请求排除该挂载 |
| 所有 provider 容量满 | 可恢复，进入候选耗尽等待重试 |
| Redis 容量服务不可用 | 返回容量服务不可用，不能误判模型不可用 |
| 映射目标模型ID全部不可用 | 保留源模型ID并记录映射不可用 trace |
| 映射目标上游可恢复失败 | 可尝试下一个映射目标 |
| 非流式内容防护命中 | 未成功返回前可切换候选或返回安全错误 |
| 流式已下发后出错 | 不切换 provider，发送 SSE 错误并收尾 |

## 与其它模块的契约

- 提供商管理模块必须维护 provider/model 的启停、优先级、协议、能力、容量、可用性、熔断和内容完整性字段。
- 可用性状态模块必须统一维护 DB 可用性与运行时可用性；路由只读取有效状态，不在普通成功路径任意改写长期状态。
- 内容防护模块必须通过独立内容完整性字段表达可信风险，不得用可用性或熔断字段表达内容污染。
- 计费模块可在候选尝试前做余额预检查，余额不足只影响当前候选或请求，不应污染 provider 可用。
- 请求日志必须记录 route trace、候选、诊断、失败原因和 `trace_id`，供后续运营排查与短窗口指标计算。

## 维护要求

1. 修改候选硬过滤、打分、排序、诊断、模型映射、可用性门槛、容量、内容可信、伪成功响应检测或候选耗尽重试时，必须同步更新本文。
2. 新增影响路由选择的配置项时，必须同时更新 `app/schemas/setting.py`、`app/services/setting_service.py`、管理页面、本文和 `docs/文档索引.md`。
3. 新增诊断原因码时，必须优先由对应过滤器、评分器、排序器或诊断器声明并输出，再同步补充诊断含义、可恢复性判断和对外错误分类说明。
4. 改动正式代理入口协议、请求能力识别或原生协议适配时，必须同时检查本文与 `docs/模块/提供商原生协议与模型分组.md`。
5. 新增路由策略时，必须在 `RouteStrategyRegistry` 注册插件组合，并补充阶段测试；禁止在 `ProxyService` 或其它调用方散落新增策略判断。
6. 若实现与本文不一致，必须先判断是代码缺陷还是文档过期；修正时禁止只改代码不改文档。
