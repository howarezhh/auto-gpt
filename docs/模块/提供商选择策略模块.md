# 提供商选择策略模块

摘要：本文记录对外代理请求进入系统后，如何从 API Key 授权范围、模型映射、挂载能力、可用性/熔断、内容可信、容量、路由得分和重试策略中选择最终提供商与挂载模型。关键词：`RouterService`、`RoutePolicyContext`、`RouteCandidate`、`ProxyService`、`ModelMappingService`、`ProviderCapacityService`、`ProviderHealthStateService`、`FixedSuccessResponseService`、`ContentTrustProbeService`、`allowed_provider_ids`、`preferred_provider_ids`、`route_health_gate_mode`、`route_score`、`route_exhausted_retry`。

最后维护时间：2026-06-15

## 模块职责与边界

提供商选择策略模块的职责是为一次正式代理请求选出可尝试的 `Provider + ProviderModel` 候选序列，并在候选失败、候选耗尽或模型映射目标失败时给出可追踪、可重试或可拒绝的处理结果。

本模块不负责提供商配置持久化、模型挂载新增、可用性探针执行、内容防护探针执行、计费结算或请求协议适配的具体实现；但它会读取这些模块沉淀的状态作为路由约束。

任何改动以下代码、配置或跨模块契约时，必须同步检查并更新本文：

- `app/services/router_service.py`
- `app/services/proxy_service.py` 中候选调用、候选耗尽、同提供商重试、模型映射失败重试和 route outage 逻辑
- `app/services/model_mapping_service.py`
- `app/services/api_key_service.py` 与 `app/services/api_key_auth_cache.py` 中 `RoutePolicyContext` 构建逻辑
- `app/services/provider_capacity_service.py`
- `app/services/provider_health_state_service.py`
- `app/services/content_trust_probe_service.py`
- `app/schemas/setting.py` 与 `app/services/setting_service.py` 中路由设置字段
- 影响提供商选择的模型权限、端点协议、能力字段、可用性字段、熔断字段、内容完整性字段、容量字段和请求日志路由指标；当前数据库兼容字段仍命名为 `health_status`

## 决策输入

一次路由决策至少由以下输入共同决定：

- 请求模型：外部请求体中的 `model`，经模型映射后可能变成目标模型。
- 请求形态：非流式或流式、图片输入、工具调用、生图、Chat Completions、Responses、Gemini 原生或 Claude 原生。
- API Key 策略：授权提供商集合、模型白名单、偏好提供商、偏好地区、延迟偏好和成功率偏好。
- 全局路由设置：`trusted_providers_only`、`route_health_gate_mode`、`max_candidate_count`、`route_candidate_expand_count`、候选缓存 TTL、候选耗尽重试窗口。
- Provider 状态：启停、维护模式、熔断、协议类型、内容完整性、信任等级、优先级、容量限制、地区标签。
- ProviderModel 状态：启停、模型别名、协议类型、能力、可用性、熔断、优先级、内容完整性。
- 运行时状态：Redis 中 provider/model 可用性、短窗口成功率/失败率、EWMA 延迟、EWMA 首 token、容量快照。
- 历史指标：`request_logs` 近 5 分钟路由指标，包括成功率、失败率和平均延迟。
- 会话粘性：同一会话最近成功使用的目标模型、提供商和挂载模型。

## 总流程

1. 对外入口完成 Bearer API Key 鉴权，`ApiKeyService` 校验密钥启用、过期、IP/端点限制、用户额度和授权提供商。
2. 鉴权层生成 `RoutePolicyContext`：`allowed_provider_ids` 来自 API Key 绑定，可信策略和可用性门槛来自全局设置，偏好提供商/地区及偏好权重来自 API Key。
3. `ProxyService` 解析请求能力和入口协议，补充内容防护路由策略，并校验请求模型是否在 API Key 模型权限内。
4. `ModelMappingService` 对源模型执行映射选择；若没有可用目标，保留源模型并在 trace 中记录 `model_mapping_no_available_target`。
5. `ProxyService` 检查模型 token 限制、长输出限制、route outage 缓存。
6. `RouterService.async_order_candidates` 加载候选、执行硬过滤、容量过滤、打分和排序。
7. 若有候选，`ProxyService` 按排序依次尝试候选；每次尝试前做余额预检查，并通过 `ProviderCapacityService.async_lease` 获取容量租约。
8. 上游调用成功后执行内容防护、伪成功固定文本检测、日志、计费和运行时可用性更新；失败时记录候选失败并按同提供商重试、候选切换、模型映射 failover 或候选耗尽重试处理。
9. 若无候选，`RouterService.diagnose_candidate_unavailability` 生成结构化诊断，`ProxyService` 按诊断决定是否等待重试、尝试下一个映射目标或返回结构化错误。

## RoutePolicyContext

`RoutePolicyContext` 是跨鉴权、映射、路由和代理执行的策略载体：

| 字段 | 含义 |
| --- | --- |
| `allowed_provider_ids` | API Key 被授权使用的提供商集合；为空时鉴权直接拒绝 |
| `forced_provider_id` | 内部调试或受控链路强制指定的提供商；对外 `/v1/*` 禁止暴露此能力 |
| `preferred_provider_ids` | 偏好提供商，进入打分时加 `preferred_provider_bonus` |
| `preferred_region_tags` | 偏好地区，命中后加地区分 |
| `latency_bias` | 延迟惩罚倍率 |
| `success_rate_bias` | 成功率得分倍率 |
| `require_trusted_provider` | 是否只允许官方/可信提供商 |
| `content_guard_required` | 内容防护路由是否必需 |
| `health_gate_mode` | `permissive`、`healthy_only`、`trusted_healthy` 三档可用性门槛；字段名为兼容历史保留 |

缓存鉴权 `ApiKeyAuthCache` 必须重建同一语义的 `RoutePolicyContext`，避免缓存命中后绕过最新全局可信策略和可用性门槛。

## 模型映射阶段

`ModelMappingService.resolve_for_request` 在候选提供商排序之前执行。当前实现会：

- 跳过未启用映射或无目标的映射。
- 排除本轮 failover 已尝试过的目标模型。
- 校验 API Key 是否允许目标模型。
- 校验目标模型目录是否存在且全局启用。
- 校验目标模型级能力和入口协议是否明显不匹配。
- 调用 `RouterService.diagnose_candidate_unavailability` 预判该目标是否存在最终候选；无最终候选时记录 `target_route_unavailable`。
- 若同一会话最近成功目标仍在可用目标中，优先复用；否则按映射目标配置顺序选择。

映射阶段只选择目标模型；真正的 provider/model 候选排序、容量租约、可用性门槛、内容可信硬排除和上游尝试仍由后续路由阶段执行。若目标模型上游失败且错误可恢复，`ProxyService` 可尝试下一个映射目标。

## 候选硬过滤

`RouterService._candidate_passes_runtime_filters` 是正式候选的硬过滤入口。硬过滤不打分，任何一项不满足都会排除候选。

| 过滤项 | 排除条件 |
| --- | --- |
| 提供商启停 | `provider.enabled` 为假 |
| 提供商熔断 | `provider.circuit_state == "open"` |
| 维护模式 | `provider.maintenance_mode_enabled` 为真 |
| 内容/信任策略 | 提供商被 `blocked`、内容完整性 `blocked`、评分过低，或要求可信但非官方/可信 |
| API Key 授权 | `allowed_provider_ids` 不包含该提供商 |
| 提供商端点协议 | 请求入口或原生协议要求与提供商协议能力不匹配 |
| 挂载启停 | `provider_model.enabled` 为假 |
| 挂载内容策略 | 挂载内容完整性 `blocked` 或评分过低 |
| 模型全局启用 | `provider_model.model_name` 不在启用模型目录中 |
| 请求模型匹配 | 请求指定模型时，挂载模型名不一致 |
| 挂载端点协议 | Chat/Responses/原生协议要求与挂载协议能力不匹配 |
| 可用性门槛 | `healthy_only` 要求 provider 和 model 均为 `healthy`；`trusted_healthy` 还要求官方/可信 |
| 流式能力 | 流式请求但挂载不支持 stream |
| 图片能力 | 图片请求但挂载不支持 vision |
| 工具能力 | 工具请求但挂载不支持 tools |
| 生图能力 | 生图请求但挂载不支持 image generation |
| 能力探针状态 | vision/tools/image generation 最近探针明确失败 |
| 挂载熔断 | 挂载熔断未到恢复探测时间，或 half-open 探针名额未抢到 |

## 端点协议规则

原生协议要求通过 `required_upstream_protocol_type` 下沉到路由层。`gemini` 只允许选择实际原生协议为 `gemini` 的挂载；`claude_messages` 只允许选择实际原生协议为 `claude_messages` 的挂载。

OpenAI 兼容入口请求 Chat/Responses 时，Gemini/Claude 原生挂载可以进入候选，前提是请求入口可由原生适配层转换；后续由协议适配层负责请求体和响应体转换。

OpenAI 兼容挂载若只声明 Chat，则不能承载 Responses；若只声明 Responses，则不能承载 Chat；`both` 可以承载两类入口。

## 内容可信与可用性门槛

内容可信硬排除由 `ContentTrustProbeService.get_trust_decision_for_route` 决定：

- `trust_level == "blocked"`：排除。
- `content_integrity_status == "blocked"`：排除。
- `content_integrity_score <= 20`：排除。
- `require_trusted_provider == true` 且提供商非 `official` / `trusted`：排除。
- 挂载内容完整性 `blocked` 或评分过低：排除。

可用性门槛由 `route_health_gate_mode` 决定：

- `permissive`：不因可用性状态直接排除，仍会在打分中体现可用性差异。
- `healthy_only`：只允许 provider 和 model 有效可用性状态均为 `healthy` / `available`。
- `trusted_healthy`：在 `healthy_only` 基础上要求 provider 为 `official` 或 `trusted`。

有效可用性状态优先读取 `ProviderHealthStateService` 的运行时状态，缺失时回落到数据库字段。API 兼容返回 `db_health`、`runtime_health`、`effective_health`，并新增 `db_availability`、`runtime_availability`、`effective_availability`、`availability_status`。

## 伪成功固定文本检测

部分中转站在模型不可用时会以 HTTP 200 返回固定失败文本，例如“当前模型暂不可用，请稍后再试。”。这类响应不能记录为正常成功，也不能等下一次请求才生效。

- `FixedSuccessResponseService` 按 provider/model 缓存最近两条成功响应的归一化文本、请求指纹、响应指纹和摘要。
- 当相邻两条不同请求的响应文本相似度达到 `0.95` 或以上时，记录 `fixed_success_response_detected`。
- 非流式响应在返回用户前命中时，`ProxyService` 将当前候选视为可重试上游故障，写入 `health_status='unhealthy'`、`circuit_state='open'`、`last_error='fixed_success_response_detected'`，并立即切换下一个候选。
- 流式响应若在首段缓冲期命中，同样在下发前切换候选；若已经下发给下游，只标记该 provider/model 后续不可路由，并在请求日志 trace 中记录 `downstream_already_started=true`。
- 该能力不新增 `provider_models.route_status` 持久化字段；后台展示的 `route_availability_status` 是由启停、可用性、熔断、内容完整性和优先级派生出的展示字段。

## 容量过滤与租约

候选加载阶段会批量读取 provider 容量快照。容量过滤发生在硬过滤之后、排序之前：

- 活跃请求数达到 `max_active_requests` 时排除。
- 流式请求活跃流数达到 `max_active_streams` 时排除。
- 当前秒 QPS 达到 `max_qps` 时排除。
- 当前分钟 RPM 达到 `max_rpm` 时排除。

正式上游调用前必须通过 `ProviderCapacityService.async_lease` 获取租约。即使候选排序时容量可用，执行时仍可能因并发变化被租约拒绝；此时应进入候选失败和后续重试/切换逻辑。

容量状态依赖 Redis。容量服务不可用且不允许本地兜底时，代理返回容量服务不可用错误，而不是把它误判为模型不可用。

## 候选缓存

候选缓存 key 包含以下维度：

- 请求模型。
- vision、stream、tools、image generation 能力要求。
- Chat/Responses 端点要求。
- 原生上游协议要求。
- 内容防护总开关。
- `allowed_provider_ids`、`preferred_provider_ids`、`preferred_region_tags` 摘要。
- 最大候选数、候选扩展数。
- 延迟偏好、成功率偏好。
- 可信提供商要求、内容防护要求、可用性门槛模式。

候选缓存只保存 provider/model ID，命中后仍会重新 hydrate 并再次检查运行时过滤，避免直接复用过期对象。候选缓存 TTL 默认 10 秒，最大 60 秒。

## 打分公式

`RouterService._route_score_breakdown` 对每个候选计算分项：

| 分项 | 规则 |
| --- | --- |
| 可用性分 | `healthy=100`、`degraded=60`、`unknown=55`、`unhealthy=0`；`half_open` 最高 35，`open` 为 0 |
| 模型优先级分 | `max(0, 30 - provider_model.priority)` |
| 提供商优先级分 | `max(0, 20 - provider.priority)` |
| 偏好提供商加分 | provider ID 在 `preferred_provider_ids` 中加 35 |
| 成功率分 | `success_rate * 40 * success_rate_bias` |
| 地区加分 | provider `region_tag` 命中偏好地区加 20 |
| 延迟惩罚 | `min(30, latency_ms / 100) * latency_bias` |
| 流式 TTFB 惩罚 | 流式请求时 `min(25, ewma_ttfb_ms / 100)` |
| 饱和度惩罚 | 基于容量快照最大使用率，最高 40 |
| 近期错误惩罚 | `min(45, failure_rate * 100)` |

最终分数为各正向分相加后减去惩罚项。分数只决定排序，不绕过硬过滤。

## 排序规则

`RouterService._balanced_order` 的稳定排序键为：

1. 路由得分桶降序。
2. 负载因子升序。
3. 偏好提供商加分降序。
4. 原始路由得分降序。
5. 挂载优先级升序。
6. 提供商优先级升序。
7. 提供商 ID 升序。
8. 挂载 ID 升序。

同一会话最近成功使用的 provider/model 若仍满足硬过滤、容量过滤和排除列表，会由近期会话策略优先放到前面；失败后该候选会加入本轮失败集合，避免同轮无限重复尝试。

## 候选数量

最终候选数量由 `max_candidate_count + route_candidate_expand_count` 决定，并受实际候选数限制。默认 `max_candidate_count=10`，`route_candidate_expand_count=5`。扩展候选用于提供切换空间，避免前几个候选临时失败后立刻耗尽。

## 代理执行与失败切换

非流式与流式代理都按候选序列逐个尝试。每个候选执行时：

1. 做账户余额预检查。
2. 获取 provider 容量租约。
3. 按入口协议与挂载协议转发上游。
4. 成功后执行内容防护、usage 提取、日志写入、计费和运行时状态更新。
5. 失败后根据错误类型、状态码、内容防护结果和 retry policy 判断是否同 provider 重试、切换候选或结束。

同一 provider 的即时重试次数由 provider 自身最大重试配置决定，等待策略支持 `Retry-After` 和指数退避抖动。候选失败会记录到 `failed_candidate_keys`，后续候选排序会排除本轮已失败 provider/model。

流式请求一旦已经向下游发送 SSE 数据，内容防护命中或上游错误不能切换到其它 provider 拼接内容，只能发送标准错误事件并以 `[DONE]` 收尾。未发送任何下游数据前，允许按候选切换逻辑更换 provider。

## 候选耗尽与等待重试

无候选或所有候选失败后，`ProxyService` 会区分可恢复与不可恢复：

- 没有任何匹配模型挂载：不可恢复，直接返回模型不可用。
- 硬过滤前存在候选但容量过滤后为 0：可恢复，可等待容量释放。
- 全部失败原因都是授权、模型停用、全局停用、协议不支持、能力不支持等：不可恢复。
- 存在容量满、容量快照不可用、provider/model 熔断、model unhealthy 等：可恢复。
- 上游错误若分类为 recoverable，也可进入 route exhausted retry。

等待重试采用 `(1, 2, 5, 10, 15, 30)` 秒退避并带抖动，若上游错误提供 `Retry-After` 则优先使用。普通模式最大等待窗口由 `route_exhausted_retry_max_wait_seconds` 控制，默认 600 秒，最大 600 秒；`route_exhausted_retry_infinite_enabled` 开启后不受最大窗口限制。

route outage cache 会把同一端点、模型、能力、强制/授权 provider 和内容可信策略下的短期耗尽结果缓存起来，后续同路由请求会先等待缓存中的下一次重试时间，减少重复打穿。

## 诊断输出

无候选诊断必须保留：

- 请求模型、请求能力、端点协议、原生协议要求、可用性门槛。
- provider 总数、扫描数、挂载总数、匹配模型挂载数。
- 容量前候选数和最终候选数。
- `reason_counts` 和样本。
- 协议不匹配时的 required/actual protocol。
- forced provider 不存在、provider 未授权、模型未挂载、能力不支持、容量不足、熔断、内容可信阻断等具体原因。

对外错误详情必须结构化返回端点、能力和诊断样本，禁止只返回泛化 `model_not_available` 让调用方猜测。

## 典型边缘场景

| 场景 | 处理规则 |
| --- | --- |
| API Key 没有授权 provider | 鉴权阶段返回 `no_authorized_provider` |
| API Key 不允许请求模型 | 代理阶段返回 `model_not_allowed` 并写失败日志 |
| 强制 provider 不存在 | 诊断记录 `forced_provider_not_found` |
| 强制 provider 存在但不满足约束 | 只在该 provider 范围内诊断失败原因 |
| 模型目录未启用 | 挂载被 `model_globally_disabled` 排除 |
| 模型未挂载到任何 provider | `matching_model_mount_count=0`，不可恢复 |
| Provider 维护中 | 正式路由排除；自动探针也不得污染状态 |
| Provider 熔断 | provider 级直接排除，等待恢复或人工处理 |
| Model 熔断 | 到恢复探测时间后仅允许抢占一个 half-open 探针名额 |
| 可用性未知 | `permissive` 下可参与但可用性分较低；严格可用性门槛下排除 |
| 内容完整性 blocked | provider 或 model 被硬排除 |
| 只允许可信 provider | 非 official/trusted provider 被硬排除 |
| Chat 请求命中只支持 Responses 的 OpenAI 兼容挂载 | 排除并记录 `chat_not_supported` |
| Gemini/Claude 原生入口命中 OpenAI 兼容挂载 | 原生协议不匹配，排除 |
| OpenAI 兼容入口请求 Gemini/Claude 模型 | 原生挂载可作为候选，由适配层转换 |
| 能力探针明确失败 | 对应能力请求排除该挂载 |
| 所有 provider 容量满 | 可恢复，进入候选耗尽等待重试 |
| Redis 容量服务不可用 | 返回容量服务不可用，不能误判模型不可用 |
| 映射目标全部不可用 | 保留源模型并记录映射不可用 trace |
| 映射目标上游可恢复失败 | 可尝试下一个映射目标 |
| 非流式内容防护命中 | 未成功返回前可切换候选或返回安全错误 |
| 流式已下发后出错 | 不切换 provider，发送 SSE 错误并收尾 |

## 与其它模块的契约

- 提供商管理模块必须维护 provider/model 的启停、优先级、协议、能力、容量、可用性、熔断和内容完整性字段。
- 可用性状态模块必须统一维护 DB 可用性与运行时可用性；路由只读取有效状态，不在普通成功路径任意改写长期状态。
- 内容防护模块必须通过独立内容完整性字段表达可信风险，不得用可用性或熔断字段表达内容污染。
- 计费模块可在候选尝试前做余额预检查，余额不足只影响当前候选或请求，不应污染 provider 可用。
- 请求日志必须记录 route trace、候选、诊断、失败原因和 `trace_id`，供后续运营排查与短窗口指标计算。

## 维护要求

1. 修改候选硬过滤、打分、排序、诊断、模型映射、可用性门槛、容量、内容可信、伪成功响应检测或候选耗尽重试时，必须同步更新本文。
2. 新增影响路由选择的配置项时，必须同时更新 `app/schemas/setting.py`、`app/services/setting_service.py`、管理页面、本文和 `docs/文档索引.md`。
3. 新增诊断原因码时，必须同步补充诊断含义、可恢复性判断和对外错误分类说明。
4. 改动正式代理入口协议、请求能力识别或原生协议适配时，必须同时检查本文与 `docs/模块/提供商原生协议与模型分组.md`。
5. 若实现与本文不一致，必须先判断是代码缺陷还是文档过期；修正时禁止只改代码不改文档。
